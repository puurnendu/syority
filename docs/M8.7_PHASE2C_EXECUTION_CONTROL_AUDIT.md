# M8.7 Phase 2C — Execution Control Architecture Audit

## 1. Constraints & ConstraintLog
- **Prisma Model**: Both `Constraint` and `ConstraintLog` exist in the schema.
- **Service**: `ConstraintService` manages `Constraint` CRUD. `FieldExecutionService.REPORT_DELAY` creates `ConstraintLog`. `WorkflowService.getExecutionCondition` uses `ConstraintLog` to determine the execution condition (`WORKING`, `BLOCKED`, `QA_HOLD`, etc.).
- **Execution Gate**: Currently, there is NO hard execution gate in `FieldExecutionService.executeActivityAction` that prevents an Activity from being started if a `ConstraintLog` is open. The condition is surfaced to the UI (via Lookahead and Board APIs) but not strictly enforced on mutation.

## 2. Permits (Permit)
- **Prisma Model**: `Permit` model exists but is completely isolated. It lacks `organization_id` and `site_id`, making it incompatible with the standard multi-tenant architecture.
- **Service**: No dedicated `PermitService` exists.
- **Execution Gate**: Permits are entirely detached from execution gates. Activity execution does not currently verify if a required Permit is issued or valid.

## 3. Safety (SafetyLog, SafetyIncident)
- **Prisma Model**: `SafetyLog`, `SafetyIncident`, and `SafetyPhoto` exist and are tied to the `Event` entity using snake_case conventions.
- **Service**: `SafetyService` exists and provides daily shift-based metrics (TRIR, LTI, manpower, manhours) and logs incidents.
- **Execution Gate**: Safety incidents and logs are standalone. They do not block Workpack or Activity execution, which is expected, but they lack direct integration into the Field Execution Cockpit for quick reporting by supervisors.

## 4. PunchListItem
- **Prisma Model**: `PunchListItem` exists with a relationship to `Workpack`.
- **Service**: `PunchListService` manages CRUD and provides `validateClosureEligibility` (checks for open Category A items).
- **Execution Gate**: Correctly integrated into the completion gates. Both `JobCompletionService.createCertificate` and `WorkflowService.complete` block the transition to `completed` if there are any open Category A punch items.

## 5. FieldExecutionService Execution Gates
- **Current State**: `FieldExecutionService.executeActivityAction` enforces a foundational state machine gate: an Activity can only undergo mutations (START, UPDATE_PROGRESS, COMPLETE) if the parent `Workpack` is in the `issued` or `in_execution` status.
- **Gaps**: It does not evaluate activity-level dependencies, missing permits, or critical execution constraints (holds/blocks).

## 6. Workpack Completion/Closeout Logic
- **Current State**: `WorkflowService.complete` acts as the definitive gatekeeper for the `completed` status. It validates three rules:
  1. All mandatory QA hold points (Clearances) are cleared.
  2. No open Category A punch items exist.
  3. All physical blinds inserted for the workpack are removed.
- **Verdict**: The completion logic is mature and strictly enforced.

## 7. Activity Prerequisites / Dependencies
- **Current State**: Not formally evaluated during the `START` action. While sequence numbers and CPM dates exist, backend enforcement of predecessor relationships (e.g., scaffolding must be complete before piping starts) is absent.

## 8. Summary of Findings
The foundational execution constraints (status-based gates, QA holds, punch items, blinds) are robust. However, **Active Execution Controls** (Permits, Dependencies, and delay-based Constraints) are missing from the `FieldExecutionService` mutation gates. Permits also require a schema upgrade for multi-tenancy.
