# M8.9 ARCHITECTURE LOCK

**Date:** 2026-08-31
**Phase:** 0 - Architecture Reconciliation Complete
**Status:** LOCKED

This document serves as the authoritative blueprint and rulebook for the M8.9 Scenario Planning implementation, having been reconciled against the M8.8 production baseline.

## 1. Scenario Lifecycle & State Machine
The `ScheduleScenario` model (which already exists from M8.8 as `schedule_scenarios` with a `snapshot_json` field) will be extended. The lifecycle is:
- **`draft`**: Being actively edited (overrides being applied).
- **`calculating`**: `scheduleEngine.ts` / `ResourceConstraintService` is currently resolving the delta.
- **`ready`**: Calculation is complete, ready for comparison.
- **`proposed`**: Attached to a `ScheduleChangeRequest` for promotion.
- **`applied`**: The Change Request was approved, and these scenario deltas were applied to live Activities.
- **`rejected`**: The Change Request was denied.
- **`archived`**: Hidden from active view.

## 2. Delta Data Model
To prevent data explosion, we will avoid cloning live `Activity` rows. We will introduce a new model attached to the existing `ScheduleScenario`:

```prisma
model ScenarioActivityOverride {
  id               String   @id @default(uuid()) @db.Uuid
  scenario_id      String   @db.Uuid
  activity_id      String   @db.Uuid
  
  // Delta fields (null means no override, inherit from base)
  duration_hours   Decimal? @db.Decimal(8,2)
  planned_start    DateTime? @db.Date
  planned_end      DateTime? @db.Date
  is_active        Boolean  @default(true) // Ability to simulate deletion

  // Constraints/Logic Overrides
  early_start_constraint DateTime?
  
  scenario         ScheduleScenario @relation(fields: [scenario_id], references: [id], onDelete: Cascade)
  activity         Activity         @relation(fields: [activity_id], references: [id])
  
  @@unique([scenario_id, activity_id])
}
```
*Note: The existing `snapshot_json` in `ScheduleScenario` can continue to store the post-calculation snapshot for fast UI rendering.*

## 3. Base Schedule / Version Semantics
Every scenario must be mathematically reproducible. Therefore, a scenario must declare exactly what it is branching from.
- We will add `base_baseline_id String? @db.Uuid` to `ScheduleScenario`, mapping it to `ScheduleBaseline`.
- If the baseline is changed, the scenario calculations will reflect the new base + the saved deltas.

## 4. Effective Value Resolution
When the UI or calculation engine reads a scenario, `ScenarioDomainService` will dynamically merge:
`Effective Activity = Base Activity Data (from Baseline) + ScenarioActivityOverride`
This resolution happens purely in memory (TypeScript level) before feeding into the engine.

## 5. Relationship Override Semantics
Initially, we will NOT support relationship (Predecessor/Successor) overrides in M8.9 Phase 1 unless explicitly requested, as modifying the CPM graph structure complicates resolution exponentially. We will focus on duration and constraint adjustments. If relationship overrides are required later, a `ScenarioRelationshipOverride` delta model will be created.

## 6. Calculation Pipeline
1. `ScenarioDomainService.resolveEffectiveSchedule(scenarioId)`
2. Feed virtual array of `EffectiveActivity[]` into `scheduleEngine.ts`.
3. Receive new Early/Late/Float dates.
4. Pass updated virtual array to `ResourceConstraintService`.
5. Receive resource allocations/leveling.
6. Calculate SHI score using M8.8 Health logic.
7. Save the final calculated array as JSON into `ScheduleScenario.snapshot_json` for O(1) reads by the dashboard.

## 7. Scenario Isolation
- The database enforces isolation via the delta tables. Live `Activity` records are strictly read-only during scenario execution.
- Calculations run entirely on in-memory clones derived from the Effective Value Resolution.

## 8. Promotion Path
- A scenario in `ready` state can be submitted to M8.8 Change Control.
- `ScheduleChangeRequest` will receive a new `source_scenario_id` field.
- When the CR is `APPROVED`, the M8.8 apply mechanism reads the `ScenarioActivityOverride` records and patches the live `Activity` table in a single Prisma transaction, generating standard `AuditLog` entries.
- The scenario is marked `applied`.

## 9. Transaction Boundaries
- All overrides (saving duration/date tweaks) are standard transactions.
- Promotion (Live Application) MUST be wrapped in a strict `$transaction(async (tx) => { ... })` ensuring atomicity across `Activity`, `ScheduleChangeRequest`, and `AuditLog`.

## 10. Tenant & Event Isolation
- `ScenarioActivityOverride` intrinsically inherits `organization_id` via its parent `ScheduleScenario`.
- All API routes (`/api/events/:id/scenarios`) will be wrapped with:
  1. `withTenantGuard(request)`
  2. `guardApi('nav.schedule')`
  3. `validateEventOwnership(eventId, session.organizationId)`

## 11. Audit Requirements
- The promotion of a scenario to live generates standard `AuditLog` entries just like manual edits, ensuring full compliance.
- The scenario itself acts as a historical audit of "what was simulated".

## 12. Concurrency Rules
- While a scenario is `calculating`, the UI must block further delta mutations (Pessimistic lock on the scenario).
- If the live schedule changes significantly, the scenario's baseline reference ensures it remains locked to a known mathematical state, avoiding race conditions.

## 13. Performance Strategy
- **N+1 Avoidance:** Resolving effective activities will execute exactly 2 queries: `SELECT * FROM BaselineActivity WHERE baseline_id = X` and `SELECT * FROM ScenarioActivityOverride WHERE scenario_id = Y`. The merge happens in memory (O(n)).
- **Result Caching:** The output of `scheduleEngine.ts` is saved to `snapshot_json` so the comparison dashboard doesn't re-run CPM on every render.

## 14. Rollback Strategy
- Since live `Activity` records are untouched until promotion, "rollback" of a scenario simply involves deleting or archiving the scenario. 
- Post-promotion rollback relies on M8.8 Baseline restoration capabilities.

## 15. Reproducibility
Because the scenario specifies `base_baseline_id` and strict `ScenarioActivityOverride` deltas, feeding those two deterministic datasets back into `scheduleEngine.ts` will always yield identical results.
