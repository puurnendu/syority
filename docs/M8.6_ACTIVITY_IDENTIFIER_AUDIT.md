# M8.6 Activity Identifier Audit

## 1. Terminology & Intended Architecture

Based on the definitive business requirement, SYORITY maintains four distinct concepts:

| Field | Current Meaning | Intended Meaning | Used By |
|------|-----------------|------------------|---------|
| **Activity Code** | Often absent on Activity model; templates injected this string into `activity_number`. | Complete standardized work definition (e.g. `ISO.BLINDING`). Used to resolve library defaults. | Planners, Template Engine, Resource Assignment |
| **Activity Number** | Often conflated with Activity Code or left blank/defaulted to sequences. Unique per org. | Execution identifier: `<EQUIPMENT_TAG>-<SERIAL_NUMBER>` (e.g. `31-E-116-0005`). | SYORITY/HMEL Execution |
| **Activity ID** | Generated via `activityIdGenerator.ts` as `{tag}_{serial}` per event. | Scheduling-system identifier (Primavera P6). May include P6 specific suffixes. | P6/Scheduling Exports |
| **Equipment Tag** | Equipment identifier on the Workpack. | The primary source prefix for the Activity Number. | Workpack / Activity Number Generator |

## 2. Existing Code & Configurations

**Numbering Configuration:**
- `activity_id_increment` exists on the `Organization` model in Prisma.
- `src/lib/activityIdGenerator.ts` contains `getActivityIdIncrement(orgId)` which retrieves this setting (defaults to 3).
- **Current problem:** `activityIdGenerator.ts` uses this increment to generate `activity_id` formatted as `{equipmentTag}_{serial}` and scopes uniqueness to the `event_id`. This logic actually aligns closely with the intended **Activity Number** logic, but operates on the wrong field and wrong scope.

**P6 Mapping (`app/api/workpacks/[id]/export/primavera/route.ts`):**
- P6 `activity_code` is currently mapped as: `a.activity_number ?? a.activity_id ?? null`. This incorrectly collapses Number and ID.
- P6 Activity ID generation should not overwrite the Activity Number.

**MS Project Mapping (`app/api/export/generate/route.ts` & `app/api/workpacks/[id]/export/ms-project/route.ts`):**
- Injected as `<ExtendedAttribute>` under specific FieldIDs. (e.g. 188743731 or 188743739).
- `UID`/`ID` are MS Project task sequence IDs. `Name` falls back to `activity_number`.

**Database Constraint:**
- `@@unique([organization_id, activity_number], name: "org_activity_number")`
- This constraint is **correct**. Since Activity Number is `<EQUIPMENT_TAG>-<SERIAL_NUMBER>` and equipment tags are unique within the site/tenant, this constraint accurately guarantees tenant-wide uniqueness for the Activity Number without needing to change the schema.

## 3. Findings & Conclusions
- The existing increment configuration (`activity_id_increment`) should be used for Activity Number generation.
- The `activityIdGenerator.ts` logic needs to be refactored into `activityNumberGenerator.ts` to assign `activity_number` using hyphens (`-`) and zero-padding (e.g. `0005`), scoped to the `organization_id` instead of `event_id`.
- The P6 export logic needs to decouple Activity Code, Activity Number, and Activity ID into their distinct fields.
