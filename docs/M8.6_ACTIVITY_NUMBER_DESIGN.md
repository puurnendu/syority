# M8.6 Activity Number Design

## 1. Objective

Implement a robust, concurrent-safe Activity Number generation system that respects the definitive identifier architecture:
`ACTIVITY NUMBER = EQUIPMENT TAG + "-" + INCREMENTAL SERIAL NUMBER`

This design rectifies the previous conflation of `Activity Code`, `Activity ID`, and `Activity Number`.

## 2. Numbering Logic

### Source Data
- **Equipment Tag:** Extracted directly from the Workpack's associated Equipment/Asset (`workpack.asset.tag_number`).
- **Increment Strategy:** Configured globally per organization on the `organization.activity_id_increment` setting (defaults to 3 if unset).

### Scope
- Uniqueness is scoped to the `organization_id` level, bounded by the `Equipment Tag`.
- Concurrency logic must guarantee that multiple simultaneous Workpacks for the same Equipment (e.g. Workpack 1: Inspection, Workpack 2: Repair) correctly receive consecutive serial numbers without duplication.
- E.g. `31-E-116-0005`, `31-E-116-0010`.

### Zero-Padding Convention
- 4-digit zero-padding will be strictly used, as it provides sufficient depth for complex equipment scopes (up to 9999 activities per equipment) while matching typical industrial ERP conventions (e.g., `0005`, `0010`).

## 3. Implementation Details

1. **New Service Module (`src/lib/activityNumberGenerator.ts`):**
   - Implements `generateNextActivityNumber(orgId, equipmentTag, increment)`.
   - Utilizes Prisma to query the maximum existing serial number for that `equipmentTag` across the `organization_id`.
   - Ensures no duplicates even under race conditions (by relying on the `@@unique([organization_id, activity_number])` database constraint). If a collision occurs upon insertion, a retry wrapper will fetch the next available number.

2. **Template Instantiation Updates (`TemplateLibraryService.ts`):**
   - The transaction block developed in the previous M8.6 step will be adapted.
   - It will resolve the `equipmentTag` from the target Workpack.
   - It will fetch the `activity_id_increment`.
   - It will assign the new `<EQUIPMENT_TAG>-<SERIAL>` pattern sequentially for every template activity.

3. **P6 & Schedule Identifiers:**
   - Leave `activity_id` and `p6_activity_id` untouched during instantiation. These will remain distinct scheduling identifiers populated by schedule integrations, entirely separate from the execution-focused `activity_number`.

4. **Schema Constraint:**
   - The `@@unique([organization_id, activity_number])` constraint stays exactly as-is. It perfectly matches this new organization-wide equipment-prefixed numbering scheme.
