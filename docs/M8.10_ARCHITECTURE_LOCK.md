## 1. Scope Lock

- Dedicated M8.10 seed dataset for functional and browser testing

### Explicitly Out-of-Scope
- Resource rate tables (deferred — see §7 Unresolved Decisions)

- Monte Carlo / probabilistic forecasting (M8.13)
- P6/MSP cost import/export (M8.15)
- ERP/SAP financial integration
- Multi-currency support

## 2. EVM Methodology Lock: Hybrid Physical % Complete

### Locked Decision
The default EV earning method is **Physical % Complete** driven by `Activity.progress_percent`.

```
EV(activity) = BAC(activity) × min(progress_percent / 100, 1.0)
```

### Earning Rules by Activity Type
The earning rules are defined in detail in [M8.10_EV_EARNING_RULES.md](file:///c:/DEV/STO/docs/M8.10_EV_EARNING_RULES.md).

### Future Extensibility
The architecture must allow a future `ev_method` enum field on `Activity` to support alternative earning rules per activity (0/100, 50/50, Weighted Milestone, Level of Effort). This field is **not** part of M8.10 Phase 1 scope.

## 3. Formula Lock

All EVM formulas are locked as specified below. These are designed for industrial turnaround scheduling, not generic project management.

| Metric | Formula | Zero-Division Rule |
|--------|---------|-------------------|
| **PV** | `BAC × (Baseline Planned % Complete at Data Date)` | If no BAC, PV = 0 |
| **EV** | `BAC × min(progress_percent / 100, 1.0)` | If no BAC, EV = 0 |
| **AC** | `Activity.actual_cost` (or `SUM(ProgressLog.actual_cost)`) | If null, AC = 0 |
| **BAC** | `SUM(BaselineActivity.budgeted_cost)` for all activities in the current baseline | — |
| **CV** | `EV − AC` | — |
| **SV** | `EV − PV` | — |
| **CPI** | `EV / AC` | If AC = 0 and EV = 0: CPI = 1.0. If AC = 0 and EV > 0: CPI = null (display "∞") |
| **SPI** | `EV / PV` | If PV = 0 and EV = 0: SPI = 1.0. If PV = 0 and EV > 0: SPI = null (display "∞") |
| **EAC** | `AC + ((BAC − EV) / CPI)` | If CPI = null or CPI = 0: EAC = null (display "N/A") |
| **ETC** | `EAC − AC` | If EAC = null: ETC = null |
| **VAC** | `BAC − EAC` | If EAC = null: VAC = null |
| **TCPI** | `(BAC − EV) / (BAC − AC)` | If BAC = AC: TCPI = null (display "N/A") |

### PV Time-Phasing Method (Baseline Planned % Complete)
For any given Data Date `T`, an activity's baseline planned % complete is calculated by linear interpolation:

```
If T < BaselineActivity.planned_start:  planned_pct = 0%
If T >= BaselineActivity.planned_finish: planned_pct = 100%
Otherwise: planned_pct = (T - planned_start) / (planned_finish - planned_start) × 100%
```

This yields: `PV(activity, T) = BaselineActivity.budgeted_cost × planned_pct / 100`

Event-level PV at time T is the sum of all activity PVs.

## 4. Baseline Architecture Lock

### Locked Decision
The M8.8 `ScheduleBaseline` (table: `ScheduleBaseline`) with its child `BaselineActivity` rows serves as the **authoritative EVM cost baseline anchor**. No separate cost baseline table will be created.

### Forensic Verification of Existing Schema

**ScheduleBaseline** (10 columns verified from live DB):
`id`, `organization_id`, `project_id`, `name`, `created_at`, `created_by`, `is_current`, `event_id`, `description`, `snapshot_metadata`

**BaselineActivity** (17 columns verified from live DB):
`id`, `baseline_id`, `activity_id`, `planned_start`, `planned_finish`, `duration`, `budgeted_cost`, `organization_id`, `early_start`, `early_finish`, `late_start`, `late_finish`, `total_float`, `free_float`, `is_critical`, `status`, `progress_percent`

### Key Baseline Rules
1. The EVM baseline is always the `ScheduleBaseline` with `is_current = true` for the given `event_id`.
2. `BaselineActivity.budgeted_cost` is the per-activity BAC. This field **already exists** in the live DB.
3. Baselines are **strictly immutable** once created. BAC cannot be retrospectively edited.
4. When a new baseline is activated (`is_current` flips), the PV curve redraws from the new baseline's dates and costs. Historical EVM snapshots remain intact.
5. Multiple baselines may coexist for comparison purposes (Target vs Current).
6. M8.11 Scope Change will be the only mechanism to alter BAC going forward — by creating a new baseline that includes the expanded scope.

## 5. Scenario EVM Integration Lock

### Locked Decision
Scenario EVM is a **read-only, projected calculation** with **zero mutation** of live cost or activity records.

### Architecture
- The `EvmCalculationService` will accept an optional `scenarioId` parameter.
- When provided, it merges live `Activity` state with `ScenarioActivityOverride` values **in memory** to produce a projected EVM curve.
- The projected curve is returned to the client as ephemeral JSON — it is never persisted.
- The `ScenarioActivityOverride` table (8 columns verified: `id`, `scenario_id`, `activity_id`, `duration_hours`, `planned_start`, `planned_end`, `is_active`, `early_start_constraint`) does **not** need a `cost_override` column in M8.10 Phase 1.
  - Rationale: Scenario cost impact is derived from the duration override × resource rates (future) or simply from the shifted PV curve. Adding explicit cost override is deferred to M8.11+.

### EVM Contexts
| Context | Source of BAC | Source of Progress | Source of Dates | Mutation? |
|---------|-------------|-------------------|----------------|-----------|
| **Live EVM** | Current `BaselineActivity.budgeted_cost` | Current `Activity.progress_percent` | Current `Activity` dates | None |
| **Scenario EVM** | Current `BaselineActivity.budgeted_cost` | Current `Activity.progress_percent` | Merged `Activity` + `ScenarioActivityOverride` dates | None (in-memory only) |
| **Historical Baseline Comparison** | `BaselineActivity(n).budgeted_cost` | `BaselineActivity(n).progress_percent` | `BaselineActivity(n)` dates | None |

## 6. Time-Phased Architecture Lock

### Locked Decision: Hybrid (Option C)
Activity-level totals are stored on existing fields. Event-level and Workpack-level aggregate curves are persisted in a new `EvmSnapshot` table to avoid real-time recomputation over large activity sets.

### New Model: `EvmSnapshot`
```
EvmSnapshot {
  id              UUID PK
  organization_id UUID NOT NULL (tenant isolation)
  event_id        UUID NOT NULL (FK → events)
  snapshot_date   TIMESTAMP NOT NULL (data date when this snapshot was taken)
  snapshot_type   TEXT NOT NULL ('daily' | 'manual' | 'baseline_change')
  curve_data      JSONB NOT NULL  -- { dates: [...], pv: [...], ev: [...], ac: [...] }
  summary         JSONB NOT NULL  -- { bac, pv, ev, ac, cpi, spi, eac, etc, vac, tcpi }
  created_at      TIMESTAMP NOT NULL
}
```

### Snapshot Generation Strategy
- **Trigger 1:** Nightly cron job at a configurable time (default: 02:00 local).
- **Trigger 2:** On-demand via API call (e.g., when a planner clicks "Refresh EVM").
- **Trigger 3:** Automatically after a `ScheduleBaseline` is activated.
- Snapshots are append-only — old snapshots are never modified.

### S-Curve API Contract
```
GET /api/events/[eventId]/evm/s-curve?from=YYYY-MM-DD&to=YYYY-MM-DD
Response: { dates: string[], pv: number[], ev: number[], ac: number[], eac_projection: number[] }
```

## 8. Seed Data Requirements Lock

A new seed script `prisma/seed-evm-demo.ts` must create:
1. An Event with `budget_cost` and `budget_manhours` populated.
2. 15–25 Activities across 3–5 Workpacks with realistic `budgeted_cost` values (range: $5,000–$150,000).
3. A `ScheduleBaseline` capturing all activities with their `budgeted_cost`, `planned_start`, and `planned_finish`.
4. `ProgressLog` entries simulating 7–10 days of execution with `actual_cost`, `manhours_actual`, and `progress_percent` increments.
5. Activities in various states: not_started, in_progress (partial %), and complete.
6. At least 2 activities with cost overrun (AC > BAC portion) and 2 under budget.
7. Resource assignments with `planned_hours` and `actual_hours`.
8. At least 1 M8.9 Scenario with overrides affecting critical-path activities.
