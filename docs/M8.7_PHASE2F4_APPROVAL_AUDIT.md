# M8.7 Phase 2F.4 - Approval & Audit Hardening

## Overview
Phase 2F hardens the `ResourceLevelingApplyService` to guarantee true atomic transactionality.

## Transaction Architecture
The core acceptance criterion is that **0 schedule changes, 0 CPM changes, and 0 audit changes** occur if any part of the apply process fails.

```
BEGIN TRANSACTION
  Validate Event/Tenant
  Validate Snapshot (Drift Detection)
  Update Activities (New Dates)
  Recalculate CPM Schedule
  Write Audit Logs
COMMIT
```

## Snapshot Drift Protection
To prevent stale date application, the simulation state (`current_start`, `current_end`) is verified against the database. Any discrepancy throws an immediate `409 Conflict`, leaving the database completely untouched.

## Audit Logging
Successful operations log `RESOURCE_LEVELING_APPLIED` containing:
- Before state (`planned_start`, `planned_end`, `original_float`)
- After state (`proposed_start`, `proposed_end`, `remaining_float`, `float_consumed`)
- The `simulation_id` for tracing.
