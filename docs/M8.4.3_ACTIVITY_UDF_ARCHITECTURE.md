## SYORITY Schema Compatibility

**[FACT]** SYORITY already has a complete UDF framework:

- **ActivityUdfDefinition**: name, code, type, is_mandatory, sort_order
- **ActivityUdfOption**: value, label, code_value (for select/enum UDFs)
- **ActivityUdfValue**: value_string, value_number, value_date, value_boolean
- **ActivityLibraryUdfDefault**: Links UDF defaults to Activity Library items

> **[RECOMMENDATION]** NO SCHEMA CHANGE NEEDED for UDFs. The existing framework supports all 4 genuine UDFs. Implementation only requires DATA POPULATION (creating UDF definitions and linking to Activity Library items).

### Execution Window (WINDOW)

- **M8.4.2 Candidate**: UDF_WINDOW

- **Unit**: —
- **Source**: Section E
- **Required**: Yes
- **Re-evaluated Verdict**: Activity Code
- **Schema Change Needed**: No
- **Reasoning**: Window is a CLASSIFICATION dimension, not a data capture field. It should be an Activity Code (P6 Activity Code) or a native field — NOT a UDF. SYORITY already has Activity.window (String).

### Estimated Man Hours (EST_MANHRS)

- **M8.4.2 Candidate**: UDF_EST_MANHRS
- **Data Type**: decimal
- **Unit**: hrs
- **Source**: Calculated
- **Required**: Yes
- **Re-evaluated Verdict**: Calculated Field
- **Schema Change Needed**: No
- **Reasoning**: This is Σ(resource.planned_hours × resource.headcount). Should be calculated from ActivityResource records, not stored as independent UDF. Storing it creates data sync risk.
