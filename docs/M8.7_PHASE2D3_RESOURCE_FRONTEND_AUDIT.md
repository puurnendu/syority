# M8.7 Phase 2D.3 — Resource Planning Frontend Architecture Audit

## 1. Existing Planner UI & Event Context
- **Entry Point**: The primary Planner Workspace is located at `app/(dashboard)/planner-workspace/page.tsx`.
- **Event Context**: The workspace utilizes `useWorkspaceStore` (`src/stores/useWorkspaceStore.ts`) to manage the `selectedEventId` and `selectedEventName`. The `selectedEventId` is the authoritative source for Event context.
- **Layout Structure**: 
  - The UI uses a CSS Grid layout with resizable panels (Tree, Workpack Grid, Activity Grid, Inspector, Bottom Panel).
  - The `WorkspaceToolbar.tsx` handles view switching and event context display.
  - Keyboard shortcuts (`Alt+1` to `Alt+0`) and a dropdown menu switch the `activeView` (e.g., `hierarchy`, `workpacks`, `activities`, `schedule`, `resources`, etc.).

## 2. Recommended Integration Point
The Resource Planning Dashboard should be conditionally rendered in the center pane of the `PlannerWorkspacePage` when `activeView === 'resources'`. This replaces the stacked `WorkpackGrid` and `ActivityGrid` while the user is analyzing resources, keeping the side panels (Tree/Inspector) available if needed.

## 3. Existing Resource Histogram UI
- **Legacy Histogram**: Located at `src/components/Schedule/ResourceHistogram.tsx`.
- **Legacy API**: Fetches from `app/api/schedule/resource-histogram/route.ts`.
- **Finding**: The legacy histogram uses a Discipline-based aggregation, not the new ResourceType-based Demand vs Capacity engine. **Constraint**: This must not be touched or modified. The new Phase 2D.3 UI will be completely independent and use `/api/events/[eventId]/resource-loading`.

## 4. Reusable Components & Structure
- Components should be placed in `src/components/planner-workspace/resources/` (or `src/components/resources/`).
- The Dashboard should be styled using existing Tailwind conventions (e.g., `border-gray-300`, `bg-white`, standard text sizes).

## 5. Routing & Tenant Handling
- The new frontend components will not fetch data with bare URLs; they will append `?eventId=${selectedEventId}`.
- Tenant isolation (`organization_id`) is strictly handled by the backend `withTenantGuard` mechanism. The frontend does not and should not deal with `organization_id`.
- Handlers should cleanly catch 401/403/500 errors and display standard error states.

## 6. Architecture Decisions
1. **ResourcePlanningDashboard**: The main component rendered when `activeView === 'resources'`.
2. **ShiftConfiguration**: A small modal or section within the dashboard to manage `ShiftDefinition` records.
3. **ResourceCapacityEditor**: A panel or modal for planners to enter capacity rules by `ResourceType`, `Contractor`, `Date`, and `Shift`.
4. **Demand vs Capacity Chart**: A stacked bar or line chart showing the aggregated limits from `GET /api/events/[eventId]/resource-loading`.
5. **Loading Matrix**: A data table showing tabular details for Dates, Demand, Capacity, and Variance.

**Conclusion**: The architecture is fully compatible with the requirements. Implementation can proceed without altering existing grids or legacy histograms.
