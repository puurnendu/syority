# M8.7 Phase 2D — Resource Planning Implementation Plan

## 1. Objective
Implement Resource Planning capabilities (Manpower, Equipment, Calendars, and Availability) extending the existing planning, scheduling, and execution architecture, strictly avoiding duplicate systems.

## 2. Scope of Work

### Phase 2D.1: Schema Enhancements
1. **Define `ShiftDefinition` Model**:
   - Linked to `Event` or `ScheduleCalendar`.
   - Defines `shift_name`, `start_time`, `end_time`.
2. **Define `ResourceCapacity` Model**:
   - Tracks maximum available headcount/equipment per `ResourceType` per day/shift.
   - Links to `Contractor` to manage supplier commitments.
3. **Database Migration**:
   - Generate and apply Prisma migrations for the new models.

### Phase 2D.2: API & Service Layer (Backend)
1. **Capacity Management API**:
   - Endpoints to set, update, and retrieve `ResourceCapacity` for an `Event`.
2. **Shift Management API**:
   - Endpoints to configure `ShiftDefinition` for an `Event`.
3. **Resource Histogram Engine**:
   - Service method to aggregate `ActivityResource` demand over time and compare it against `ResourceCapacity` supply.
   - Handle overlap, float analysis, and over-allocation detection.

### Phase 2D.3: Client Layer (Frontend)
1. **Resource Availability Matrix**:
   - A grid UI for Planners to input contractor supply commitments (Dates on X-axis, ResourceTypes on Y-axis).
2. **Shift Configuration Panel**:
   - UI within Event Settings to define shifts.
3. **Resource Histogram Widget**:
   - Visual chart integrating with the existing Planner Workspace / Gantt to show Demand vs. Capacity (Over/Under allocation).

## 3. Constraints & Invariants
- **Tenant Isolation**: All new models must include `organization_id` and enforce RLS/Service-level boundary checks.
- **Authoritative Event**: `ResourceCapacity` and `ShiftDefinition` must strictly belong to the `Event` hierarchy.
- **No Duplication**: `ActivityResource` remains the absolute source of truth for Demand. Do not create separate "Task Resources".

## 4. Rollout Strategy
- Step 1: Execute Prisma schema modifications.
- Step 2: Build and test backend APIs for Capacity and Shifts.
- Step 3: Implement Histogram calculation logic.
- Step 4: Develop Frontend visual matrices and widgets.

## 5. Review & Approval
Please review this Implementation Plan and the associated Architecture Audit. Upon approval, we will proceed with creating the Prisma schema modifications (Phase 2D.1).
