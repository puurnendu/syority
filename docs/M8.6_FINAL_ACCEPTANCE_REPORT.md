## 2. Resolution of Audit Findings

### 2.1 Finding A1 — Service-Level Tenant Guard in `setAttributeValue()`
- **Defect:** `AssetRegisterService.setAttributeValue()` lacked an independent `assertAssetOwnership()` guard, relying exclusively on API-level checks.
- **Remediation:** Added `await AssetRegisterService.assertAssetOwnership(assetId, ctx.organization_id)` at the entry point of `setAttributeValue()` and `batchSetAttributeValues()`.
- **Runtime Verification:** Executed Test `SEC-02`. A direct service call with mismatched `assetId` and `organization_id` is blocked with `"Asset not found"` and performs 0 database writes.

### 2.2 Finding B1 — Transaction-Scoped Audit Error Propagation
- **Defect:** `AuditService.log()` caught errors and silently swallowed them, meaning a failure in audit logging inside `prisma.$transaction()` would allow other operations to commit while the audit log was lost.
- **Remediation:** Updated `AuditService.log()` in `src/lib/audit.ts` to re-throw errors when `db !== prisma` (inside a transaction context), while maintaining non-fatal logging for normal operations.
- **Runtime Verification:** Executed Test `TX-01`. When audit logging failed inside a transaction, all prior operations (`AssetAttributeValue` updates and `AssetAttributeHistory` decisions) rolled back atomically with no partial state.

### 2.3 Finding F1 — Canonical Bidirectional PDF Technical Data Mapping
- **Defect:** PDF Three-Tier resolver produced flat attribute codes (e.g. `shell_design_press_barg: 10`), while the existing PDF template expected the legacy nested structure (`shell_side.design_pressure_kg_cm2`), causing values to render as dashes (`—`).
- **Remediation:** Implemented `AssetExtractionMapper.toLegacyEquipmentTechnicalData(attributes, assetCoreData, nozzlesList)` in `src/core/asset-register/AssetExtractionMapper.ts`. Updated `PdfService.ts` Tier 1 (Snapshot) and Tier 2 (Live AR) resolution blocks to map flat attributes into nested `{ equipment, dimensions, tube_bundle, shell_side, tube_side, materials, nozzles, design_codes }`.
- **Runtime Verification:** Executed Tests `PDF-01` and `PDF-02`. Live AR and Snapshot data both resolved into full nested structures with valid engineering numbers (`equipment.tema_designation="BEM"`, `shell_side.design_pressure=16.5`) with zero dash replacements.

### 2.4 Finding D1 — Clear Separation of Extract Status & Trigger
- **Defect:** `POST /api/assets/[assetId]/extract` only returned status information, creating a semantic mismatch with `POST`.
- **Remediation:** Refactored `app/api/assets/[assetId]/extract/route.ts` to provide:
  - `GET`: Status endpoint returning current attribute values and pending AI extractions.
  - `POST`: Extraction trigger endpoint that reads linked plant documents, runs Vision AI, normalizes through `AssetExtractionMapper`, and batch-writes as `ai_candidate`.

### 2.5 Finding A2 — Database-Level Tenant Scoping in `compareWithLive()`
- **Defect:** `WorkpackAssetSnapshotService.compareWithLive()` verified workpack ownership but omitted `organization_id` in the subsequent `assetAttributeValue.findMany` query.
- **Remediation:** Added `organization_id: organizationId` to the `liveAttributes` query.

### 2.6 Finding A3 — Workpack Relationship Tenant Scoping in Snapshot API
- **Defect:** `GET /api/assets/[assetId]/snapshot` queried snapshots by `asset_id` without filtering by workpack organization.
- **Remediation:** Scoped `GET` with `workpack: { organization_id: orgId }` and added workpack tenant ownership validation on `POST`.

## 5. AI Governance & Data Lifecycle Proof

### Architectural Invariant: AI data NEVER automatically becomes `VERIFIED`

```
┌────────────────────────┐
│  AI Document Analysis  │ (Vision AI / PDF Text)
└───────────┬────────────┘
            │
            ▼
┌────────────────────────┐
│ AssetExtractionMapper  │ (Normalizes & Flattens to EAV)
└───────────┬────────────┘
            │
            ▼
┌────────────────────────┐
│ AssetAttributeValue    │ (status: "ai_candidate")
│ AssetAttributeHistory  │ (action: "ai_extracted")
└───────────┬────────────┘
            │
            ▼
┌────────────────────────┐
│   Planner Review UI    │ (getPendingAiExtractions queue)
└───────────┬────────────┘
            │
       ┌────┴───────────────────────────┐
       ▼                                ▼
┌──────────────┐                 ┌──────────────┐
│    ACCEPT    │                 │    MODIFY    │
└──────┬───────┘                 └──────┬───────┘
       │                                │
       ▼                                ▼
┌───────────────────────────────────────────────┐
│              reviewAiExtraction()             │
│            (Atomic $transaction)              │
│  - Supercede old value (if exists)            │
│  - Set value status: "verified"               │
│  - Record history: "ai_accepted"/"ai_modified"│
│  - Link FK: refers_to_history_id              │
│  - Write AuditLog                             │
└───────────────────────────────────────────────┘
```

**Codebase Proof:**
1. `AssetRegisterService.ts:273`: `const status = isAi ? ATTRIBUTE_STATUSES.AI_CANDIDATE : ATTRIBUTE_STATUSES.UNVERIFIED;`
2. `AssetRegisterService.ts:250-269`: AI Protection Rule — If an attribute is already `VERIFIED`, subsequent AI extractions CANNOT overwrite it. An `ai_extracted` history row is created for planner review, preserving the active verified value.
3. Repositories grep audit: 0 direct writes of `status: 'verified'` outside human review methods (`reviewAiExtraction` and `verifyAttribute`).

## 6. History Immutability & Foreign Key Protection

1. **Zero Database Mutations:**
   - `grep -rE "assetAttributeHistory\.(update|delete|updateMany|deleteMany)"` → 0 matches across the repository.
   - `grep -rE "workpackAssetSnapshot\.(update|delete|updateMany|deleteMany)"` → 0 matches across the repository.
2. **Self-Referencing Foreign Key:**
   - Schema: `refers_to_history AssetAttributeHistory? @relation("HistoryDecisionLink", fields: [refers_to_history_id], references: [id], onDelete: Restrict)`
   - PostgreSQL Constraint: `asset_attribute_history_refers_to_fkey` with `ON DELETE RESTRICT ON UPDATE CASCADE`.
   - Guaranteed: Decision rows cannot be orphaned, and original extraction rows cannot be deleted while referenced.
