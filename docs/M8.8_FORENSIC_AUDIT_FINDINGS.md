```
grep "ScheduleControlDashboard" across entire codebase:
→ Only 1 result: the export declaration at L121
→ Zero imports anywhere

Compare with M8.7:
ResourcePlanningDashboard imported at app/(dashboard)/planner-workspace/page.tsx L27
Rendered at L300
```
**Remediation:** Import and render `ScheduleControlDashboard` in the planner workspace page alongside `ResourcePlanningDashboard`.

### F-006 [P1] No Database Uniqueness Constraint on is_current Baseline

**File:** `prisma/schema.prisma` L1391-1411 (ScheduleBaseline model)  
**Root Cause:** The `is_current` field is a simple `Boolean @default(false)` with no unique partial index. The service uses a sequential `updateMany(is_current: false)` then `update(is_current: true)` without a database-level constraint. Two concurrent baseline assignments can result in TWO `is_current = true` baselines for the same event.  
**Evidence:** Test D-03 created two baselines with `is_current: true` simultaneously — database accepted both.  
**Impact:** Data integrity: multiple "current" baselines cause undefined behavior in variance and SHI calculations.  
**Remediation:** Add a partial unique index: `@@unique([event_id, is_current], where: { is_current: true })` or use a filtered unique index at PostgreSQL level.

### F-007 [P2] No Explicit "review" Status Transition

**File:** `ScheduleChangeControlService.ts` L174  
**Root Cause:** The `reviewChangeRequest` method accepts CRs in status `proposed` OR `review`, but there is no method to transition a CR from `proposed` to `review`. The status jumps directly from `proposed` → `approved`/`rejected`.  
**Impact:** The "review" status defined in the schema and guarded in the code is unreachable. The Change Control panel UI shows a "review" status with a color (#f59e0b) but no CR can ever be in that state.  
**Remediation:** Either add a `submitForReview()` method or remove "review" from the schema/UI.

### F-009 [P2] Concurrent Baseline Assignment Race Condition

**File:** `ScheduleBaselineService.ts` L262-289  
**Root Cause:** `assignBaseline` uses sequential `updateMany` (clear all is_current) then `update` (set new is_current) WITHOUT a database-level uniqueness constraint. Two concurrent calls can interleave.  
**Impact:** Concurrent baseline assignments can leave 2 active baselines. This is the application-level manifestation of F-006.  
**Remediation:** Same as F-006 — add database constraint. Also consider using `$transaction` with `serializable` isolation.

### F-010 [P3] ActivityRelationship Query Not Event-Scoped

**File:** `CriticalPathIntelligenceService.ts` L144-150  
**Root Cause:** `findMany({ where: { organization_id } })` fetches ALL relationships for the entire organization, not filtered by event. The service then post-filters by activity membership.  
**Impact:** Performance degradation for organizations with many events. No security impact (org-scoped). For 10 events with 500 activities each, this fetches 5000 relationships instead of 500.  
**Remediation:** Add event-scoped activity ID filter or join through activities table.
