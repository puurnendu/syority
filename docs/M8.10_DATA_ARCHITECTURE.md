# M8.10 Data & Baseline Architecture

## Phase 0E — Time-Phased Cost Architecture
To plot S-Curves (PV, EV, AC), STO requires time-phased arrays of financial data.

### Architectural Options Evaluated
- **Option A:** Dynamic calculation (No new tables). Fetch `BaselineActivity`, calculate linear spread between `planned_start` and `planned_end`, sum across all activities in RAM.
- **Option B:** Static Time-Phased Buckets (`TimePhasedCost` table). Nightly cron job calculates PV/EV/AC per day/shift and saves to DB.
- **Option C:** Hybrid. Store Activity-level totals, but persist Event-level and Workpack-level aggregate curves in a `CostCurveSnapshot` table.

### Recommendation: OPTION A (Dynamic via ClickHouse / OLAP) transitioning to OPTION C
- Given the current PostgreSQL architecture, running daily spreads over 50,000 activities dynamically in Node.js will cause severe memory bloat.
- **Proposed M8.10 Solution:** Introduce an `EventCostSnapshot` (Option C) table that stores JSON time-series arrays for `[dates]`, `[pv]`, `[ev]`, `[ac]`. This snapshot is regenerated incrementally or nightly.

## Phase 0F — Baseline Architecture Integration
- **Interaction with M8.8/M8.9:** The existing `ScheduleBaseline` and `BaselineActivity` are perfectly suited to serve as the EVM Cost Baseline, as they already capture `budgeted_cost`, `planned_start`, and `planned_finish`.
- **Answers to Constraints:**
  1. *What becomes the baseline?* The `ScheduleBaseline` marked `is_current = true`.
  2. *Can ScheduleBaseline contain cost?* Yes, it already has `budgeted_cost`.
  3. *Immutable?* Yes. Baselines must remain strictly immutable.
  4. *New Baseline?* The S-Curve redraws PV based on the newly activated baseline.
  5. *Multiple baselines?* Yes, allow comparison of PV(Target) vs PV(Current).

## Phase 0G — Scenario / M8.9 Integration (Mandatory)
M8.9 Scenario Planning must be protected, but integrated.

### Scenario EVM Capabilities
- `ScenarioActivityOverride` will eventually need a `cost_override` field to simulate *"What if we crash this activity? Duration drops, Cost increases."*
- **EVM Contexts:** The system must evaluate EVM in three contexts without mutating live data:
  1. **Live EVM:** Current `Activity` vs Current `ScheduleBaseline`.
  2. **Baseline EVM:** Historical `ScheduleBaseline(n)` vs `ScheduleBaseline(n-1)`.
  3. **Scenario EVM:** Live `Activity` + `ScenarioActivityOverride` vs Current `ScheduleBaseline`. (Used to visualize how an M8.9 Scenario *recovers* a slipping EVM S-Curve).

### Recommendation
Add a `calculateScenarioEVM()` function to the `ScenarioCalculationService` that dynamically projects the EAC and forecasted S-curve based on the scenario's overrides, overlaying it on the Live EVM chart.
