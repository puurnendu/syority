# M8.4.8 — Quantity Model Validation

> **M8.4.8** — Adversarial Validation — Generated: 2026-08-18T07:30:48.043Z
> Classification: FACT | INFERENCE | RECOMMENDATION | FINDING | DEFECT
> This analysis does NOT accept previous conclusions at face value.



## Quantity Lifecycle

```
Template → Planned Qty → Actual Qty → Remaining → Progress %
```

## Validation Against XER Evidence

**[FACT]** P6 XER contains NO quantity-type UDFs.
All XER UDFs are text/float for identification purposes (MSP Activity ID, Activity No, Critical Path).

**[FACT]** Quantities originate from iPlan, stored in:
- `Operation_CustomNumber1` → Scaffolding Volume (m³)
- `Operation_CustomNumber2` → Painting Area (m²)
- `Operation_CustomNumber3` → Insulation Area (m²)

These are NEVER exported to P6. They are planning quantities only.

## Where Should Quantity Be Stored?

| Option | Model | Pros | Cons |
|---|---|---|---|
| A. ActivityUdfValue | UDF system | Flexible, extensible, already exists | Extra joins, no time-series |
| B. ProgressLog | Progress tracking | Time-series, daily tracking | Mixes quantity with progress |
| C. Both | UDF for planned, ProgressLog for actual | Best of both | Most complex |

### Recommended Architecture (Option C)

```
PLANNED quantity:
  ActivityUdfValue (udf_definition for "Scaffolding Volume")
    value_number = 500 (m³)

ACTUAL quantity (daily):
  ProgressLog
    quantity_actual = 120 (cumulative on this day)
    quantity_unit = "m³"

REMAINING:
  Computed: Planned - Last(Actual) = 500 - 120 = 380

PROGRESS %:
  Computed: Last(Actual) / Planned × 100 = 24%
```

### Is `ProgressLog.quantity_actual` + `ProgressLog.quantity_unit` Sufficient?

**[FINDING]** Almost. Two concerns:

1. **Cumulative vs Incremental**: Is quantity_actual the CUMULATIVE total or the DAY's increment?
   - **[RECOMMENDATION]**: Cumulative. The daily increment can be computed from consecutive logs.
   - This matches how progress_percent works (always cumulative).

2. **Multiple quantities per activity**: An activity might have BOTH scaffolding AND painting quantities.
   - **[FINDING]**: This is rare. In practice, quantities are associated with specific activities (scaffolding → PREP.SCAFFOLDING).
   - If needed, use multiple ActivityUdfValues for planned, and multiple ProgressLog entries (one per UDF) for actual.
   - **[RECOMMENDATION]**: Add `udf_definition_id` (optional) to ProgressLog to link quantity to its UDF.

### Proposed Schema Addition

```prisma
model ProgressLog {
  // existing fields...
  quantity_actual    Decimal?  @db.Decimal(12, 2)  // Cumulative actual
  quantity_unit      String?                       // m³, m², inch-dia
  udf_definition_id String?   @db.Uuid           // Links to which UDF this quantity tracks
}
```

### Verdict: READY (with udf_definition_id addition)

The quantity model is sound. Add `udf_definition_id` to ProgressLog for multi-quantity scenarios.
This increases the P0 field count from 7 to 8.
