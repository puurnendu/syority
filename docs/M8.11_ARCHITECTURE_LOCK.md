```sql
CREATE TABLE "discovery_work" (
    "id"                UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    "title"             TEXT NOT NULL,

    --        opportunity, engineering_change, regulatory

    "estimated_hours"   INTEGER DEFAULT 0,
    "estimated_cost"    FLOAT DEFAULT 0,
    "attachments"       JSONB DEFAULT '[]',
    "status"            TEXT NOT NULL DEFAULT 'discovered',

    "assessed_by"       UUID,
    "assessed_at"       TIMESTAMP(3),
    "assessment_notes"  TEXT,
    "scope_change_id"   UUID,           -- Link to created scope change

        FOREIGN KEY ("event_id") REFERENCES "events"("id") ON DELETE RESTRICT,

CREATE INDEX "discovery_work_event_status_idx" ON "discovery_work"("event_id", "status");
```

```sql
CREATE TABLE "schedule_scope_changes" (
    "id"                UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    "cost_impact"           FLOAT DEFAULT 0,

    "reviewed_by"       UUID,
    "reviewed_at"       TIMESTAMP(3),
    "review_notes"      TEXT,
    "approved_by"       UUID,

    "applied_by"        UUID,

CREATE INDEX "scope_changes_org_idx" ON "schedule_scope_changes"("organization_id");
CREATE UNIQUE INDEX "scope_changes_number_idx" ON "schedule_scope_changes"("organization_id", "change_number");
```

## 2. State Machine

### 2.1 Discovery Work Lifecycle

```
DISCOVERED ──→ ASSESSED ──→ CONVERTED ──→ CLOSED
                  │                          ↑
                  └──→ REJECTED ─────────────┘
```

### 2.2 Scope Change Lifecycle

```
DRAFT ──→ ANALYZING ──→ PROPOSED ──→ APPROVED ──→ APPLYING ──→ APPLIED
                           │
                           └──→ REJECTED
```

### 2.3 Integration with M8.8 Schedule Change Request

When a `ScheduleScopeChange` reaches `APPROVED`:
1. System generates a `ScheduleChangeRequest` with `change_type = 'scope_addition'`
2. The M8.8 lifecycle takes over: proposed → review → approved → applied
3. On `APPLIED`, the scope change status transitions to `APPLIED`
4. New Workpack + Activities are created in the transaction

## 6. Immutability Rules

| Rule | Enforcement |
|------|------------|
| Discovery cannot mutate live Activity data | Service-level: DiscoveryWorkService has NO write access to Activity table |
| Scope Change proposal cannot mutate live schedule | Service-level: ScopeChangeProposalService reads only |
| Impact analysis is read-only projection | ScopeChangeImpactService reads baseline/activity data, writes to impact_analysis JSONB only |
| Only APPLIED status creates Workpack/Activity | ScopeChangeApplicationService validates status === 'approved' before any writes |
| Audit trail is mandatory | Every status transition creates AuditLog entry |
| Organization_id required on all tables | Schema-enforced NOT NULL constraint |
