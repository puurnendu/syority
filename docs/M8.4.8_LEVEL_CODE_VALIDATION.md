## Architecture Under Test

```

        ↓
Canonical SYORITY Code (e.g. DISMANTLE.TB_REMOVAL)
        ↓
Activity Family (e.g. DISMANTLE)
```

## Critical Finding: Level Codes Are NOT Activity Names

**[FINDING]** The current M8.4.7 architecture partially confuses Level Code with Activity Name.

Example — the canonical code `REPAIR.WELDING` is being treated as both:
1. A **classification** (Level Code) — grouping all welding activities
2. An **activity name** — the individual "Welding repair" activity

This is correct **by design** for SYORITY's knowledge bank. But validation reveals:

### A Welding workpack contains MULTIPLE distinct activities:
```
1. Hold Point — Fit-up of joint & Fit-up Inspection by AI    (INSP activity)
2. Welding of joints as per IAN                               (REPAIR.WELDING)
3. Hold Point — Welding inspection and DPT of welded joints   (INSP.NDT)
4. Hold Point — NDT post welding                              (INSP.NDT)
```

**[FACT]** The Level Code `PIP.Wel` is assigned to ALL of these — not just the actual welding.
This means Level Code is a **workpack-phase classifier**, not an activity identifier.

## Conclusion

**[FACT]** The 3-level architecture is CORRECT but must be used carefully:
- Level Code = **Workpack Phase Classifier** (what stage of work)
- Canonical Code = **Activity Classification** (what type of work)
- Activity Name = **Specific description** (what exactly to do)

**Level Code ≠ Activity Name.** This distinction must be preserved.

### Recommendation

1. Document clearly: Level Code is for GROUPING and REPORTING, not for IDENTITY
2. A single Level Code (e.g. EE.TR) maps to MULTIPLE template activities
3. The canonical code (ELECTRICAL.TRANSFORMER) maps to the FAMILY, not the individual activity
4. Individual activities within a template are identified by `sequence_number + description`

### Verdict: READY (with documented caveat)
