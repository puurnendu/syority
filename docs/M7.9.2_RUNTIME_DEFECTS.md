# M7.9.2 — Runtime Defects & Fixes

This document records the runtime defects, validation exceptions, and database schema mismatches discovered during M7.9.2 QA testing, along with the surgical fixes implemented to resolve them.

---

## 1. Missing Database Primary Keys (UUIDs)
*   **Symptom:** `Argument id is missing.` when performing `create` or `createMany` operations on models like `Activity`, `Workpack`, `SafetyLog`, `SafetyIncident`, and `line_lists`.
*   **Root Cause:** The PostgreSQL database schema defines primary keys as `@id @db.Uuid` without `@default(uuid())`. This requires the API layer to generate and supply the UUID on creation, which was missing in several controller/service files.
*   **Surgical Fixes:**
    *   **Activities:** Injected `id: crypto.randomUUID()` in `app/api/activities/route.ts` inside `prisma.activity.create`.
    *   **Workpacks:** Injected `id: crypto.randomUUID()` in `src/modules/Workpack/Services/WorkpackService.ts` inside `prisma.workpack.create`.
    *   **SafetyLogs:** Injected `id: crypto.randomUUID()` in `app/api/events/[eventId]/safety/route.ts` and `app/api/events/[eventId]/safety/incidents/route.ts`.
    *   **SafetyIncidents:** Injected `id: crypto.randomUUID()` in `app/api/events/[eventId]/safety/incidents/route.ts`.
    *   **LineLists & Joints:** Injected `id: crypto.randomUUID()` to both `prisma.line_lists.create` and the mapped arrays inside `prisma.joint_masters.createMany` inside `app/api/line-lists/route.ts`.

## 2. Missing Schema Columns in Database
*   **Symptom:** `The column readiness_score of relation Workpack does not exist in the current database.`
*   **Root Cause:** Fields like `readiness_score` and `compliance_score` were added to the `Workpack` and `WorkpackInstantiation` models in `schema.prisma`, but they were never compiled into any migration files inside `prisma/migrations`.
*   **Surgical Fixes:**
    *   Executed `npx prisma db push` on the host to synchronize the database schema with the current `schema.prisma` definitions.
    *   Created `scratch/db_query.js` to run a pg-based database check and verify the column insertions.

---

## 3. Invalid Model Fields (Case-Sensitivity and Mismatches)
*   **Symptom:** `Unknown argument project_id. Did you mean p6_object_id?` in Activity creation.
*   **Root Cause:** The activity route was attempting to pass `project_id: body.project_id`, but the field on the `Activity` model is named `event_id` in `schema.prisma`.
*   **Surgical Fix:** Replaced `project_id` with `event_id` in `app/api/activities/route.ts` lines 34-40.

---

## 4. Case-Sensitive Relation Includes
*   **Symptom:** `Unknown field organization for include statement on model WorkpackMaterial.` and `Unknown field form_template for include statement on model form_instances.`
*   **Root Cause:** Prisma relations are case-sensitive. The models define relations as `Organization` and `FormTemplate` (capitalized), but the code was querying them as `organization` and `form_template` (lowercase).
*   **Surgical Fixes:**
    *   Corrected `organization` to `Organization` in `src/modules/Workpack/Services/WorkpackService.ts` line 176.
    *   Corrected `form_template` to `FormTemplate` in `src/modules/Workpack/Services/PdfService.ts` line 984.

---

## 5. Non-existent PDF Include Relation
*   **Symptom:** `Unknown field item_catalog for include statement on model workpack_material_lines.` in `PdfService.generateWorkpackPdf`.
*   **Root Cause:** The query tried to join `item_catalog` to get details, but no such relation exists on the `workpack_material_lines` model in the current schema. All material properties are saved directly as columns on the model.
*   **Surgical Fix:** Removed `include: { item_catalog: ... }` from the `workpack_material_lines` query inside `src/modules/Workpack/Services/PdfService.ts` (lines 967-981).

---

## 6. Incorrect HoldPoint Relation Include & Filter Mismatch
*   **Symptom:** `Unknown field qa_clearances for include statement on model Activity.` followed by `TypeError: Cannot read properties of undefined (reading 'length')` in Hold Point list.
*   **Root Cause:** The relation name defined on `Activity` is `qa_clearance_records`, but the Hold Point GET handler was including `qa_clearances` and accessing it as `a.qa_clearances.length`.
*   **Surgical Fix:** Replaced `qa_clearances` with `qa_clearance_records` in both the `include` statement and the `filter` counter inside `app/api/workpacks/[id]/hold-points/route.ts`.

---

## 7. Required Fields in Safety Modules
*   **Symptom:** `Argument updated_at is missing.` on safety logs and incidents creations.
*   **Root Cause:** `updated_at` is marked as required on `SafetyLog` and `SafetyIncident` tables, but does not use `@updatedAt` or `@default(now())` in `schema.prisma`.
*   **Surgical Fix:** Injected `updated_at: new Date()` in all create/upsert data objects in `app/api/events/[eventId]/safety/route.ts` and `app/api/events/[eventId]/safety/incidents/route.ts`.

---

## 8. Missing Status Code Propagation in Tenant Guard
*   **Symptom:** Tenant Isolation checks returned HTTP 500 instead of HTTP 403 Forbidden.
*   **Root Cause:** `assertTenantAccess` was throwing an error with `statusCode: 403`, but the route catch block was ignoring it and returning a default `500` status code.
*   **Surgical Fix:** Updated the catch block in `app/api/workpacks/[id]/route.ts` to check and propagate `(error as any).statusCode || 500` as the HTTP status.

---

## 9. Non-existent raw table query in Tenant Onboarding
*   **Symptom:** `relation "schedule_calendars" does not exist` when provisioning a tenant.
*   **Root Cause:** The tenant provisioning service was running a raw query `INSERT INTO "schedule_calendars"`, but the table name in the schema is `"ScheduleCalendar"`. The raw query failure aborted the transaction block.
*   **Surgical Fix:** Replaced the raw SQL insert with standard Prisma Client `tx.scheduleCalendar.create` in `src/core/Platform/TenantProvisioningService.ts` lines 593-614.
