# M8.5 — Decision Register

> Every architectural decision with classification and evidence.

## D001: ActivityLibrary as Activity Code Storage

| Attribute | Value |
|---|---|
| Decision | Use existing `ActivityLibrary` model for the Activity Code Knowledge Bank |
| Classification | FACT |
| Evidence | `ActivityLibrary` already has `activity_code`, `name`, `work_category`, `phase`, `level_code`, `duration_hours`, `hold_point_type` |
| Alternative | New `ActivityCode` model — REJECTED (unnecessary duplication) |
| Risk | LOW — additive change only (add `library_scope`, make `organization_id` nullable) |

## D002: PLATFORM Scope via Nullable organization_id

| Attribute | Value |
|---|---|
| Decision | PLATFORM-scope codes have `organization_id = null`, `library_scope = 'PLATFORM'` |
| Classification | INFERENCE |
| Evidence | `WorkType` already uses `organization_id: String? @db.Uuid /// null = platform-level` |
| Alternative | Separate `system_activity_codes` table — REJECTED (fragments the query path) |
| Risk | LOW — follows established pattern |

## D003: Template Conditionality as String Enum + Expression

| Attribute | Value |
|---|---|
| Decision | Add `conditionality` (MANDATORY/OPTIONAL/CONDITIONAL) and `condition_expression` (String) to template activities |
| Classification | RECOMMENDATION |
| Evidence | M8.4.9 corpus shows 3 clear states: mandatory, optional (scaffolding), conditional (tube plug if needed) |
| Alternative | Boolean `is_conditional` + `condition` field — REJECTED (doesn't distinguish OPTIONAL from CONDITIONAL) |
| Alternative | Rules engine with JSON expression — REJECTED (over-engineering without evidence) |
| Risk | LOW — `condition_expression` is human-readable planner guidance, not executable code |

## D004: Relationship Instantiation (D1 Fix)

| Attribute | Value |
|---|---|
| Decision | During template instantiation, read `workpack_template_logic_links` and create `ActivityRelationship` records |
| Classification | DEFECT FIX (FACT) |
| Evidence | Current code stores logic_links in `equipment_technical_data` JSON but never creates `ActivityRelationship` records. CPM engine requires `ActivityRelationship` records. |
| Risk | LOW — additive; existing instantiated workpacks without relationships are unaffected |

## D005: Resource Auto-Population (D2 Fix)

| Attribute | Value |
|---|---|
| Decision | During template instantiation, query `activity_code_default_resources` and create `ActivityResource` records |
| Classification | DEFECT FIX (RECOMMENDATION) |
| Evidence | `activity_code_default_resources` table exists but is never read during instantiation |
| Risk | LOW — creates resources that planner can modify; no data loss risk |

## D006: DPR = Reporting View, Not Separate Model

| Attribute | Value |
|---|---|
| Decision | DPR columns map to Activity completion status and UDF quantities — no separate DPR schema |
| Classification | FACT |
| Evidence | DPR workbook columns (Scaffolding, Blinding, Bundle Pullout, etc.) are all Activity Codes. Summary rows (TOTAL/COMPLETED/BALANCE) are COUNT queries. |
| Alternative | Separate `dpr_line_items` table — REJECTED (duplicates execution data, creates sync burden) |
| Risk | NONE — uses existing data |

## D007: UDF Rollup via Existing RollupEngine

| Attribute | Value |
|---|---|
| Decision | Use existing `RollupEngine.computeEventRollups()` and `UDFRollupProviders` for hierarchical aggregation |
| Classification | FACT |
| Evidence | `UDFRollupProviders.ts` already implements SUM/AVG/MIN/MAX/COUNT across Equipment → System → Unit → Event |
| Alternative | New aggregation engine — REJECTED (would duplicate existing capability) |
| Risk | NONE — existing, tested infrastructure |

## D008: Export Activity Codes as P6 UDFs
