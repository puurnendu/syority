## ANSWERS TO 25 REQUIRED QUESTIONS

### 1. What exactly does the HMEL workpack contain?
**[FACT]** Section E activity tables with 14 columns: Window, Op Number, Description, Contractor, Duration, Predecessors, Details, Manpower, Est Man Hours, Equipment Resources, Rigging Plan Req, Scaffolding m3, Painting m2, Insulation m2. Plus QA in Sections G/H, Materials in J, Blinds in K.

### 2. What exactly does iPlan add or transform?
**[FACT]** iPlan adds: Level Code (CustomDropDownList1), P6 Activity Codes, scheduling metadata, cross-workpack dependencies, resource assignments, and generates the P6/XER export.

### 3. What exactly does P6 contain?
**[FACT]** 6,210 activities, 15 Activity Code Types (1,201 values), 7,508 predecessor links, 8,709 resource assignments, 6 UDF types (12,954 values), 41 Level Code values.

### 4. What exactly is the native iPlan Level Code?
**[FACT]** An equipment-prefixed activity classification code (e.g., Ex.RTub = Exchanger Retubing, PIP.Wel = Piping Welding, AFC.BLD = Air Fin Cooler Blinded). Stored as Operation_CustomDropDownList1 in iPlan, exported as iPlan_Level Code Activity Code Type in P6.

### 5. Where do the normalized SYORITY Level Codes come from?
**[FACT]** They were PROPOSED in M8.4.3 as a SYORITY-internal canonical taxonomy. They do NOT exist in iPlan or P6.

### 6. How should native and canonical Level Codes coexist?
**[RECOMMENDATION]** Store BOTH: native_level_code (preserves P6 fidelity) and activity_code (canonical Family.Type for cross-equipment reporting).

### 7-8. Activity Family / Activity Type / Execution Phase?
**[RECOMMENDATION]** Three-level architecture: Native Code → Canonical Code (Family.Type) → Family. Phase is INDEPENDENT (7 values).

### 9-10. Real UDFs? Which are quantities?
**[FACT]** Scaffolding (m3), Painting (m2), Insulation (m2) are true quantities. Rigging Plan Req is boolean. Man-hours is calculated. Duration is a native field.

### 11-13. Planned/Actual/Progress quantities?
**[RECOMMENDATION]** Planned: ActivityUdfValue.value_number. Actual: ProgressLog.quantity_actual (NEW). Progress: actual/planned. Time-series via ProgressLog.

### 14-15. QA in progress and management reporting?
**[RECOMMENDATION]** Track QA (AI and TS) as separate progress dimensions. Use duration-weighted progress for physical work. QA clearance is a count-based KPI.

### 16-17. Equipment and Level Code reporting?
**[RECOMMENDATION]** Equipment Tag/Type → Workpack → Activities with Level Code and quantity dimensions. Canonical Level Codes enable cross-equipment aggregation.

### 18. Template Library?
**[RECOMMENDATION]** Existing TemplateFamily → WorkpackTemplate → TemplateActivity is correct. Enrich templates with Level Code, QA AI/TS, and UDF definitions.

### 19-21. P6 export?
**[RECOMMENDATION]** Output adapter. SYORITY maps Activity Codes to P6 Activity Code Types. Native Level Code enables direct P6 export without transformation.

### 22-23. What is missing?
**[FACT]** 5-6 schema field additions: native_level_code, hold_point_ai, hold_point_ts, quantity_actual (on ProgressLog), quantity_unit, condition_expression. Plus extending window to 7 phases.

### 24. M8.5 priorities?
**[RECOMMENDATION]** 1. Schema additions (P0). 2. Activity Library population (41 items). 3. Template population. 4. Planning UI for cross-WP dependencies.

### 25. What must NOT be implemented yet?
**[RECOMMENDATION]** Rules engine for conditional activities. Full P6 XER import. AI-generated activity suggestions.
