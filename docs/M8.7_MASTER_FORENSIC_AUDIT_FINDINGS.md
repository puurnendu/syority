## P1 — HIGH FINDINGS

### P1-F001: UI Dashboard receives empty data — API response key mismatch

**Severity:** P1 — HIGH  
**Phase:** 2D  
**Status:** 🔴 FAILED  
**File:** `src/components/planner-workspace/resources/ResourcePlanningDashboard.tsx` (line 79)  
**API:** `app/api/events/[eventId]/resource-loading/route.ts` (line 21)

**Defect:** The API route wraps the response as `{ data: [...] }` but the Dashboard reads `dataLoading.results`. Since `dataLoading.results` is always `undefined`, the fallback `|| []` sets `loadingResults` to an empty array.

**Impact:** The entire Resource Planning Dashboard renders NO data for:
- Demand vs Capacity Histogram
- Resource Loading Matrix
- Resource Heatmap
- Resource Trend Panel
- Resource Availability Matrix (derives resource types from results)

**Evidence:**
- `resource-loading/route.ts` line 21: `return NextResponse.json({ data });`
- `ResourcePlanningDashboard.tsx` line 79: `setLoadingResults(dataLoading.results || []);`
- Correct accessor should be: `dataLoading.data || []`

**Reproduction:** Open Resource Planning Dashboard with any event that has ActivityResource data. Observe: all visualizations show empty state.

**Recommended Fix:** Change line 79 to `setLoadingResults(dataLoading.data || []);`

### P1-F002: Shifts data never populated in Dashboard

**Severity:** P1 — HIGH  
**Phase:** 2D  
**Status:** 🔴 FAILED  
**File:** `src/components/planner-workspace/resources/ResourcePlanningDashboard.tsx` (line 104)  
**API:** `app/api/events/[eventId]/shifts/route.ts` (line 11)

**Defect:** The shifts API route returns `{ data: shifts }` but the Dashboard reads `sh.items || sh`. Neither accessor returns an array — `sh.items` is undefined, and `sh` is the wrapper object `{ data: [...] }`, not the array itself.

**Impact:** `shifts` state will be the raw JSON object `{data: [...]}` instead of an array, causing rendering issues in ShiftConfigurationPanel and ResourceLoadingMatrix.

**Evidence:**
- `shifts/route.ts` line 11: `return NextResponse.json({ data: shifts });`
- `Dashboard.tsx` line 103-104: `const sh = await resShifts.json(); setShifts(sh.items || sh);`
- Correct accessor: `sh.data || []`

**Recommended Fix:** Change line 104 to `setShifts(sh.data || []);`

## P2 — MEDIUM FINDINGS

### P2-F001: ResourceScenarioComparisonService uses hardcoded heuristic values

**Severity:** P2 — MEDIUM  
**Phase:** 2I  
**Status:** 🔵 STRUCTURALLY VERIFIED  
**File:** `src/core/resources/ResourceScenarioComparisonService.ts` (lines 93-94)

**Defect:** `max_deficit_improvement` and `resource_utilization_improvement` use hardcoded formulas:
```typescript
const max_deficit_improvement = constraints_resolved > 0 ? (constraints_resolved * 2) : 0;
const resource_utilization_improvement = constraints_resolved > 0 ? 5.0 : 0.0;
```
These are not actual calculations based on demand/capacity analysis.

**Impact:** Scenario comparison reports provide inaccurate improvement metrics. Planners may make suboptimal decisions based on misleading data.

**Recommended Fix:** Compute actual before/after deficit and utilization from demand data.

### P2-F003: Forecast status thresholds are coarse

**Severity:** P2 — MEDIUM  
**Phase:** 2I  
**Status:** 🔵 STRUCTURALLY VERIFIED  
**File:** `src/core/resources/ResourceForecastService.ts` (lines 112-114)

**Defect:** The forecast status classification is:
- `CRITICAL`: util > 100 OR any deficit
- `AT_RISK`: util >= 90
- `WATCH`: util >= 80

This means ANY resource with even a 0.01 unit deficit on any single day across the entire forecast window is immediately classified as CRITICAL. This is overly aggressive and may create noise.

**Impact:** Users may experience alert fatigue if many resources have minor, non-blocking deficits.

### P3-F002: No soft-delete filtering on `deleteShift`

**Severity:** P3 — LOW  
**Phase:** 2D  
**Status:** 🔵 STRUCTURALLY VERIFIED  
**File:** `src/core/resources/ResourcePlanningService.ts` (lines 53-68)

**Defect:** `deleteShift` performs a hard `prisma.shiftDefinition.delete()` rather than setting `deleted_at`. While other M8.7 models use hard deletes too (consistency), the schema has `deleted_at DateTime?` on ShiftDefinition, suggesting soft delete was intended.

**Impact:** Deleted shifts cannot be recovered. Low severity because capacity records would prevent accidental deletion of in-use shifts.
