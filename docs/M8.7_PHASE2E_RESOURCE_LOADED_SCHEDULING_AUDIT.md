# M8.7 Phase 2E — Resource-Loaded Scheduling & Leveling Architecture Audit

## 1. Executive Summary

This architecture audit establishes the integration strategy for adding **Resource-Loaded Scheduling and Leveling** (Phase 2E) to the STO Execution platform without duplicating existing scheduling or resource models. 

It evaluates the existing Scheduling Engine (`src/lib/scheduleEngine.ts`), the newly introduced Resource Planning layer (Phase 2D), and defines how constraints and over-allocations can be surfaced and fed back into scheduling logic as leveling recommendations.

## 2. Current Architecture State

### 2.1 Scheduling Engine (`src/lib/scheduleEngine.ts`)
The platform already utilizes a pure deterministic scheduling service implementing the Critical Path Method (CPM).
- **Core Algorithms:** Kahn’s Algorithm for Topological Sort, Cycle Detection, Forward Pass, Backward Pass.
- **Key Metrics Calculated:** Early Start/Finish, Late Start/Finish, Total Float, Free Float, and Critical Path identification.
- **Constraints/Dependencies:** Supports FS, SS, FF, SF relationships with lags.
- **Dates Base:** Mutates `planned_start` and `planned_end` based on durations (`duration_hours`) and a configurable working hours calendar.

### 2.2 Resource Planning (Phase 2D)
- **Demand:** Mastered in `ActivityResource`. Daily demand is calculated by taking `headcount * crew_size` or `quantity` and spreading it uniformly across `duration_hours` (bucketed into 10-hour days).
- **Supply:** Mastered in `ResourceCapacity`, stratified by `Event`, `ResourceType`, `Contractor`, and `ShiftDefinition`.
- **Loading:** `ResourcePlanningService` aggregates Daily Aggregate supply vs demand.

### 2.3 Proposed Integration Pipeline

The architecture successfully supports the targeted unidirectional flow with a feedback loop:
```
                 ┌──────────────────┐
                 │ Schedule Engine  │ (src/lib/scheduleEngine.ts)
                 │ Dates/Logic/CPM  │
                 └────────┬─────────┘
                          │
                          ▼
                     Activity
                          │
                 ┌────────┴────────┐
                 ▼                 ▼
          Dependencies       ActivityResource
                                   │
                                   ▼
                         Resource Planning
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
             ResourceCapacity               Resource Loading
                    │                             │
                    └──────────────┬──────────────┘
                                   ▼
                         Over-allocation
                         / Constraint Signal
```
**Conclusion:** We do not need a second Activity model or second scheduling engine. A new `ResourceConstraintService` can sit atop this pipeline to generate constraints.

## 3. Resource Constraint Classification

The platform should formalize constraints via an interface (e.g., `ResourceConstraintService`) that returns typed warning/blocking objects. We will not create new database entities to store point-in-time constraints; they will be calculated dynamically.

- **Hard Constraints:** Required equipment capacity = 0, unavailable resource types on a specific date. 
- **Soft Constraints:** Demand exceeds Capacity (e.g., 20 Welders required, 15 Available).
- **Informational:** 90% utilization threshold reached.

## 4. Resource Leveling Strategy

Because the scheduler uses standard Forward/Backward pass algorithms, it supports programmatic date movement.

**Candidate Leveling Algorithms (Heuristic approach):**
1. Identify periods of over-allocation (Demand > Capacity).
2. For each over-allocated period, retrieve activities driving the demand.
3. **Sort candidates for delay** by Total Float (highest float moves first).
4. If an activity has sufficient Total Float, its `planned_start` is deferred, removing demand from the over-allocated date.
5. If an activity is Critical (Float = 0), it is **flagged for planner intervention** rather than silently delayed (which would extend project end date).

## 5. Critical Path & Float Interaction
- **Critical Activity:** `is_critical = true`. Leveling algorithms must not auto-shift these unless a "Leveling extends project" setting is enabled. Over-allocation on a critical path must trigger a Hard/Soft constraint warning.
- **Non-Critical Activity:** Float > 0. Leveling will consume free float, then total float.
- **Resource-Constrained Critical Activity:** Requires manual intervention to increase `ResourceCapacity`.

## 6. Shift Interaction
Currently, `Activity` is NOT shift-bound. `ResourceCapacity` IS shift-bound.
**Recommendation:** 
Do not automatically bind `Activity` to `shift_id`. The platform aggregates shift capacity into a Daily Total for variance checking against Daily Demand. If intra-day shift leveling is required in the future, we should implement a `ShiftDefinition` assignment at the `Calendar` level rather than directly on `Activity`. For Phase 2E, we maintain Daily Aggregate comparisons.

## 7. Capacity Planning Modes
- **Demand-Driven View:** (What resources do I need?) Fully supported by Phase 2D.
- **Supply-Driven View:** (What work can I execute with these resources?) Supported via the proposed Leveling heuristic. By setting the capacity limits, the leveling algorithm outputs what subset of activities can run on those dates.

## 8. Legacy Histogram Audit
- **Files:** `app/api/schedule/resource-histogram/route.ts` & `src/components/Schedule/ResourceHistogram.tsx`
- **Current State:** Aggregates `Activity.manpower_count` or `ActivityResource` against `discipline_id` using a hardcoded 10-hour day logic. It does not check capacity, only demand.
- **Action:** Retain for backward compatibility in Phase 2E. Do not modify. It provides a simple organizational discipline view, whereas the new Resource Planning UI provides the rigorous Demand vs Capacity variance checking.

## 9. API Architecture
Existing APIs (`/api/events/[eventId]/resource-loading`) are sufficient for read-only viewing.
For Leveling, a new endpoint should be proposed:
- `POST /api/events/[eventId]/schedule/level-resources`
Returns: A simulation payload containing proposed Activity date shifts and resolved constraints. Planners can review and apply the shifts.

## 10. Performance Audit
- **Risks:** The `calculateSchedule` and `getDemandVsCapacity` functions both load large numbers of `Activity` records into Node.js memory. For 5,000+ activities, O(n) or O(n^2) loops could block the event loop.
- **Recommendation:** Do not introduce materialized views yet. However, the `ResourceConstraintService` must run in a background worker (like `scheduleRecalculateWorker.ts`) if leveling thousands of tasks, rather than a synchronous API response.

## 11. Proposed Next Steps (Implementation Boundary)
1. Build `ResourceConstraintService` to identify Hard/Soft constraints based on Phase 2D outputs.
2. Build `ResourceLevelingService` containing the Float-based shifting heuristic.
3. Build Planner UI to preview and accept Leveling recommendations.

Do not alter `scheduleEngine.ts` core CPM logic. Treat it as a stateless dependency.
