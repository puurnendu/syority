# M8.7 Phase 2 — Field Execution Architecture Audit

## Executive Summary
This document provides a Step 0 architecture audit of the field execution system within the STO (Shutdown, Turnaround, and Outages) application. It establishes the authoritative execution workflow, evaluating the current implementation to prevent duplication and ensure adherence to the M8.6/M8.7 architectural invariant: **Event remains the authoritative entity, Workpack is the execution container, and Activity is the executable unit.**

## Audit Findings: Current State

### 1. Core Execution Models (`schema.prisma`)
- **`Activity`**: Well-established. Tracks `status`, `progress_percent`, `actual_start`, `actual_end`.
- **`ProgressLog`**: Already implemented and robust. Links to `activity_id`, captures `log_date`, `progress_percent`, `logged_by`, and `remarks`. Used as the immutable ledger for progress.
- **`SafetyLog`**: Tracks `log_date`, `shift` (day/night), manpower, and safety incidents per `event_id`.
- **`shift_reports`**: Primarily used for generating WhatsApp text summaries (`report_text`, `activities_completed`), not as the core relational shift entity.
- **`JointIntegrityItem` / `Blind`**: Both correctly link to `workpack_id` (mandatory) and `activity_id` (optional). 
- **`Permit`, `ConstraintLog`, `PunchListItem`**: Pre-existing models linking to `workpack_id` and optionally `activity_id`.

### 2. Services & APIs (`FieldExecutionService.ts`)
- **Implementation Status**: Partially implemented and highly functional.
- **`getExecutionBoard`**: Retrieves activities for execution, now correctly gated by `issued` or `in_execution` workpack status (M8.7 Phase 1).
- **`executeActivityAction`**: Handles `START`, `UPDATE_PROGRESS`, `COMPLETE`, and `REPORT_DELAY`. Critically, it correctly inserts into `ProgressLog` for immutable tracking rather than just overwriting `Activity` fields. It calls `syncWorkpackProgress` to roll up progress to the Workpack.
- **Security/Tenant Isolation**: Enforced via `withTenantGuard` and `organization_id` filters in all prisma queries.

### 3. UI Layer
- **`/execution` (ExecutionCockpit)**: Currently serves as the primary field view. It supports Board, Manpower, Delays, Handover, and Report tabs.
- **`/shift-reports`**: Used for End-of-Shift summaries.

## Analysis & Answers to Core Questions

### A. Is the current `/execution` architecture suitable to become the primary field execution workspace?
**Yes.** The `ExecutionCockpit` and `FieldExecutionService` form a solid, correct foundation. It correctly uses `ProgressLog` for progress tracking. We do **not** need to redesign the execution workspace; it just needs strict state enforcement and integration with other execution dimensions (joints, blinds).

### B. What is the minimum change required to make Activity Progress + Shift Execution production-ready?
1. **Strict State Enforcement**: `executeActivityAction` must explicitly reject updates if the parent Workpack is not `issued` or `in_execution`.
2. **Shift Context Formalization**: `SafetyLog` is the closest to an "Active Shift" model (tracking manpower/shift). We need a unified "Active Shift Context" (e.g., Event X, Shift Day, Date) that ties `ProgressLog`, `SafetyLog`, and `shift_reports` together.

### C. How should Joint Integrity and Blind/Isolation execution attach to the existing model?
- Do **not** create a separate progress mechanism.
- `JointIntegrityItem` and `Blind` must be executed as *sub-items* of their parent `Activity`.
- **Workflow**: A user opens an Activity (e.g., "Install Spool"), and the UI surfaces the associated Joints. Executing the Joints (torquing/tensioning) drives the Activity's QA clearance.

### D. What execution gates should be enforced now versus deferred?
- **Enforced Now**: Workpack state (`issued`/`in_execution`). Activity sequence/pre-requisites (basic).
- **Deferred to Later Phase**: Deep Permit-to-Work (PTW) electronic signatures and strict Punchlist clearance blocks. (Keep these informational in Phase 2).

### E. Recommended Phase 2 Implementation Order

**Phase 2A: Core Activity Execution Hardening & Shift Context**
- Harden `/api/execution/activity-action` to enforce Workpack `issued` status.
- Formalize "Active Shift" state using `SafetyLog` as the anchor.
- Verify `syncWorkpackProgress` accurately calculates weighted progress.

**Phase 2B: Sub-Item Execution (Joints & Blinds)**
- Implement Joint Execution API (update torque/tension status on `JointIntegrityItem`).
- Implement Blind Isolation Execution API (install/remove blinds on `Blind`).
- Update `ExecutionCockpit` to surface sub-items in a side-panel when an Activity is selected.

**Phase 2C: Execution Gates & Delay Management**
- Connect `ConstraintLog` directly to Activity blocking. If a Constraint is logged against an activity, the activity status is locked until resolved.
- Implement Permit association visibility.

## Files to Modify (No Duplication)
- **Do NOT Duplicate**: `Activity`, `ProgressLog`, `Workpack`, `Event`.
- **Modify**:
  - `src/core/execution/FieldExecutionService.ts` (State enforcement, Shift context)
  - `app/api/execution/activity-action/route.ts` (Guardrails)
  - `src/components/execution/ExecutionCockpit.tsx` (Add Joints/Blinds sub-item views)
  - `prisma/schema.prisma` (Minor tweaks if required for Shift context, but prefer existing `SafetyLog`)

## Architectural Risks & Blockers
1. **Progress Rollup Complexity**: Weighted progress calculations in `syncWorkpackProgress` must exactly match the Planning module's expectations, or we will see plan-vs-actual drift.
2. **Offline Mode**: Field execution often requires offline mobile support. The current API assumes constant connectivity. (Risk noted for future PWA phase).

> [!IMPORTANT]
> The current execution architecture is structurally sound. Phase 2 should focus on hardening, gating, and adding sub-item (Joint/Blind) execution to the existing `Activity` model.
