## KEY FINDINGS

### 1. Activity Library: 42 items, not 302
**[FACT → RECOMMENDATION]**

The M8.4.2 figure of 302 candidates was inflated by PDF extraction artifacts, quantity variations, and incomplete normalization. Systematic deduplication yields **~42 unique Activity Library items** organized into **10 Activity Families**.

### 2. Activity Code: Family.Type (2-level)
**[RECOMMENDATION]** (HIGH confidence)

The correct Activity Code structure is `Family.Type` (e.g., `PREP.SCAFFOLDING`, `REPAIR.WELDING`).

Equipment Type should NOT be embedded in the Activity Code because:
- Equipment Type is already a property of the Workpack and Template
- Embedding it prevents cross-equipment reuse ("Scaffolding" is the same regardless of equipment)
- P6 uses separate Activity Code dimensions — equipment would be a redundant dimension

The existing `ActivityLibrary.activity_code` (String) field is sufficient.

### 3. UDFs: 4 genuine UDFs, not 9
**[FACT → RECOMMENDATION]**

Of the 9 M8.4.2 candidates:
- 4 are genuine UDFs: **Rigging Plan Req** (boolean), **Scaffolding m³** (decimal), **Painting m²** (decimal), **Insulation m²** (decimal)
- 5 are better modeled as: Activity Code (Window), Calculated Field (Man Hours), Native Field (QA Type), Resource Assignment (QA Duration), Discipline FK (QA Discipline)

The existing `ActivityUdfDefinition` + `ActivityUdfValue` + `ActivityLibraryUdfDefault` framework is sufficient. No schema change needed.

### 4. Hold Point vs Witness Point: Existing field, enforce values
**[FACT]** The corpus explicitly distinguishes Hold Points (157, blocking) from Witness Points (16, advisory).

**[RECOMMENDATION]** Use the existing `Activity.hold_point_type` (String) field with enforced values: `HOLD` | `WITNESS` | `null`. The existing `qa_clearance_records` model provides the clearance workflow. No schema change needed.

### 5. Execution Phase ≠ Activity Family: Two separate dimensions
**[FACT]** Window (PreSD/OP/SD/IR/PostSD) and Activity Family (PREP/ISO/CLEAN/...) correlate but do NOT map 1:1. Example: "De-blinding" is Family=ISO but Phase=PostSD.

**[RECOMMENDATION]** Model as two separate dimensions:
- `Activity.window` → Execution Phase (scheduling/progress)
- `ActivityLibrary.work_category` → Activity Family (work classification)

Both fields already exist. No schema change needed.

### 6. Cross-Workpack Dependencies: Not in corpus
**[FACT]** Zero (0) cross-workpack predecessor references found in 27 analyzed workpacks. All predecessors are intra-workpack.

**[INFERENCE]** Cross-WP dependencies exist in practice (shared isolation, piping→equipment) but are modeled at the P6/event level, not within workpack PDFs.

**[FACT]** `ActivityRelationship` has no workpack constraint — cross-WP relationships are already structurally supported.

### 7. Template Hierarchy: Equipment Type × Job Type = Template
**[FACT]** Same equipment type has different scope profiles (HE Gasket vs HE Retubing).

**[FACT]** The existing `TemplateFamily` → `workpack_templates` → `workpack_template_activities` hierarchy correctly models Equipment × Job Type.

### 8. Management Progress: Duration-weighted
**[RECOMMENDATION]** Use `Σ(progress × duration) / Σ(duration)` to prevent QA activities (2-hour inspection) from distorting progress vs major activities (160-hour retubing).

## FINAL DECISION

# 🟡 DOMAIN MODEL MOSTLY READY — SPECIFIC QUESTIONS REQUIRE USER/iPLAN CONFIRMATION

### Why not 🟢?

1. **P6 integration mapping has 6 UNKNOWNS** (duration unit, calendar, Activity Codes, UDFs, WBS structure, cross-WP handling) that cannot be resolved from the corpus alone — they require iPlan/P6 administrator input.

2. **Corpus is from a single TA event at a single site** — while the template standardization is 100% consistent across all 319 workpacks, there is no evidence that other HMEL sites or other TA events use the same iPlan template.

3. **Conditional activity rule modeling** has two viable options (is_optional workaround vs new field) — this is a product decision, not a technical one.

### What IS ready:

- Activity Library architecture (42 items, Family.Type codes)
- UDF framework (4 genuine UDFs in existing schema)
- Template hierarchy (Equipment × Job Type in existing schema)
- QA Hold/Witness model (existing field with enum enforcement)
- Resource model (existing ActivityResource)
- Management reporting model (duration-weighted progress)

### What needs confirmation before M8.5:

1. Duration unit → Ask iPlan planner
2. P6 Activity Code configuration → Ask P6 admin
3. Conditional activity rule approach → Product Owner decision
