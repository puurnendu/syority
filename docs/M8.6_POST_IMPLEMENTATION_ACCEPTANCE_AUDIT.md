## D. PARTIAL IMPLEMENTATIONS

### D1. Tenant Isolation Gap on Read Paths

The existing `GET /api/assets/[assetId]/route.ts` (pre-M8.6) at L13-14 queries with:
```typescript
prisma.asset.findFirst({
  where: { id: assetId, organization_id: orgId, deleted_at: null }
})
```

The new M8.6 routes (attributes, history, verify, review) pass `assetId` directly to the service layer without org filtering. A user from Tenant A with valid authentication can call:

```
GET /api/assets/{TENANT_B_ASSET_ID}/attributes
GET /api/assets/{TENANT_B_ASSET_ID}/history
POST /api/assets/{TENANT_B_ASSET_ID}/attributes/{code}/review
```

...and access Tenant B's data.

### D2. ReviewService Not Integrated

The plan (Phase 4.1) explicitly requires modifying [`ReviewService.ts`](file:///C:/DEV/STO/src/core/digital-plant/ReviewService.ts) to route planner accept/reject through `AssetRegisterService`. This was NOT done. When a planner reviews AI extraction through the existing review workflow, NO `AssetAttributeHistory` rows are created. The M8.6 review path only works through the NEW review API endpoint.

### D3. Missing Transaction Boundaries

`AssetRegisterService.reviewAiExtraction()` performs:
1. `recordSuperseded()` — history INSERT
2. `assetAttributeValue.upsert()` — value write
3. `recordAiDecision()` — history INSERT
4. `AuditService.log()` — audit INSERT

These 4 operations run as separate Prisma calls without `$transaction`. If step 2 succeeds but step 3 fails, the value is updated but the decision history row is missing — leaving the system believing the AI extraction is still "pending".

### D4. Definition Lookup Not Scoped

[`AssetRegisterService.setAttributeValue()` L199-L201](file:///C:/DEV/STO/src/core/asset-register/AssetRegisterService.ts#L199-L201):
```typescript
const definition = await prisma.assetAttributeDefinition.findFirst({
  where: { code, is_active: true },
});
```
This does NOT filter by `organization_id`. A tenant-scoped definition from Org A could be matched when Org B calls the API.
