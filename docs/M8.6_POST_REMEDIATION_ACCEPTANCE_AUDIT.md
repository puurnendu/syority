> [!WARNING]
> **FINDING-A1 (MEDIUM):** `setAttributeValue()` does NOT call `assertAssetOwnership()`. It trusts the caller to provide the correct `assetId`. In the `upsert` update path (L294-306), the unique constraint `asset_attr_unique` is `(asset_id, definition_id)`, which has NO org scope. If a caller provides a `ctx.organization_id` that doesn't match the asset, the definition lookup will still succeed for platform-scope definitions (`organization_id: null`), and the upsert could modify a row belonging to a foreign tenant's asset.
>
> **Mitigating factor:** All current API-layer callers verify asset ownership before calling. The method is only called via `batchSetAttributeValues`, which is only invoked from:
> - `PUT /api/assets/[assetId]/attributes` — has asset ownership check (L54-58)
> - `extract-technical-data/route.ts` — uses workpack's `organization_id`
> - `ReviewService.approveCandidate/mergeCandidate` — provides `input.organizationId`
>
> **Risk:** A future internal caller (background job, migration script) that calls `setAttributeValue` directly without ownership verification could write to another tenant's asset. Defense-in-depth is incomplete for this method.

> [!WARNING]
> **FINDING-B1 (MEDIUM):** `AuditService.log()` (audit.ts L63-82) wraps the `create` call in a try/catch that **silently swallows errors** (L79-82: `catch (error) { console.error(...) }`). When called inside a `$transaction`, if the audit log INSERT fails, the error is caught by the try/catch BEFORE it can propagate to the transaction wrapper. This means the transaction will NOT rollback — the superseded/value update/decision history will commit, but the audit log will be missing.

### F.3 Data structure concern

> [!WARNING]
> **FINDING-F1 (MEDIUM):** In Tier 1 (L1122-1127), snapshot attributes are stored as flat codes like `shell_design_press_barg`, but the template reads nested sections like `data.shell_side` and `data.equipment`. The initialization creates empty section objects (`{ equipment: {}, dimensions: {}, ... }`), but flat codes are placed directly on `techData` (L1125: `techData[attr.code] = val`), NOT into the section objects. Additionally, `snapshot.asset_data_json` is spread into the result (L1127), which contains asset core columns (tag_number, name, etc.), not the nested equipment structure.
>
> The same concern applies to Tier 2 (L1133-1136): attribute codes are placed flat on `techData`, not in section objects.
>
> The template at L1377-1381 reads `data.equipment`, `data.dimensions`, etc. — these will be the empty objects from initialization.
>
> **Impact:** Tier 1 and Tier 2 may produce empty equipment sections in PDFs. Tier 3 (legacy JSON) has the nested structure and would display correctly.
