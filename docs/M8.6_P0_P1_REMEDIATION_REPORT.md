## P0 Defects — RESOLVED

### P0-001 / P0-005 — Tenant Isolation

| Layer | Fix | Files |
|-------|-----|-------|
| **Service-level** | All `AssetRegisterService` methods now require `organizationId` and scope every Prisma query with `organization_id`. `assertAssetOwnership()` is the shared guard. | `AssetRegisterService.ts` |
| **Service-level** | `AssetAttributeHistoryService` reads scoped by `organizationId` | `AssetAttributeHistoryService.ts` |
| **Service-level** | `AssetRelationshipService.getRelationships()` and `deleteRelationship()` scoped by `organizationId` | `AssetRelationshipService.ts` |
| **Service-level** | `WorkpackAssetSnapshotService` reads verify `Workpack.organization_id`, `createSnapshot` validates asset belongs to same org | `WorkpackAssetSnapshotService.ts` |
| **API-level** | All 5 asset attribute routes enforce `orgScope()` + `Asset.organization_id` ownership check before calling any service method | `attributes/route.ts`, `verify/route.ts`, `[code]/history/route.ts`, `[code]/review/route.ts`, `history/route.ts` |

**Defense-in-depth:** Both API-level ownership guards AND service-level query scoping are enforced. Neither layer is sufficient alone.

### P0-002 — Transaction Safety (reviewAiExtraction)

The three-step mutation sequence (supersede → value update → decision record) is now wrapped
in `prisma.$transaction()`. All participating services (`AssetAttributeHistoryService`,
`AuditService`) accept an optional `db: PrismaTransactionClient` parameter (default: `prisma`).

**Shared type:** `PrismaTransactionClient` in `src/lib/prismaTypes.ts`.

### P0-003 — AssetExtractionMapper (Single Source of Truth)

Created `src/core/asset-register/AssetExtractionMapper.ts` with:
- `normalizeAiResponse()` — AI field name normalization
- `flattenExtractedData()` — nested JSON → flat EAV attributes
- `fromAiResponse()` — combined canonical entry point
- `fromExtractedAttributes()` — Digital Plant flat format → EAV

**Consumers:**
- `extract-technical-data/route.ts` — replaced 130 lines of inline mapper code
- `ReviewService.approveCandidate()` — uses `fromExtractedAttributes()`
- `ReviewService.mergeCandidate()` — uses `fromExtractedAttributes()`

### P0-004 — History Immutability FK

Added self-referencing FK `refers_to_history_id` on `AssetAttributeHistory` with
`ON DELETE RESTRICT` to enforce immutability at the database level.

**Migration:** `prisma/migrations/20250821_m86_add_history_refers_fk/migration.sql`

## P1 Defects — RESOLVED

### P1-001 — ReviewService Integration (Digital Plant → Asset Register Bridge)

`ReviewService.approveCandidate()` and `mergeCandidate()` now write technical attributes
to the Asset Register as `ai_candidate` status values. These must go through
`reviewAiExtraction()` for verification — **AI data is never auto-verified**.

Bridge failures are caught with try/catch and logged as non-fatal warnings to avoid
breaking the primary candidate approval flow.

### P1-002 — PDF Three-Tier Resolution

`PdfService.generateWorkpackPdf()` now resolves equipment technical data using three tiers:

| Tier | Condition | Source |
|------|-----------|--------|
| 1 | Issued/completed workpack | Frozen `WorkpackAssetSnapshot.attributes_json` |
| 2 | Draft/review workpack with linked asset | Live verified `AssetRegisterService.getCurrentVerifiedAssetData()` |
| 3 | Fallback | Legacy `workpack.equipment_technical_data` JSON |

Data resolution is performed **before** the HTML template literal (async-safe).
The workpack query now includes `asset_snapshots` (latest, descending).

### P1-003 — Missing API Endpoints

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/api/assets/[assetId]/audit` | GET | Asset-specific audit log |
| `/api/assets/[assetId]/snapshot` | GET/POST | Snapshot list and creation |
| `/api/assets/[assetId]/extract` | POST | Extraction status and pending AI extractions |
| `/api/admin/audit` | GET | Organization-wide audit log |
| `/api/assets/search` | GET | Unified search with full-text + attribute filters |

All endpoints enforce `orgScope()` + asset ownership checks.

### P1-004 — Unified Asset Register Search

`AssetRegisterService.searchAssets()` supports:
- Full-text search on `tag_number`, `name`, `description`
- Asset type and system filters
- EAV attribute-level filters with comparison operators (`eq`, `gt`, `gte`, `lt`, `lte`)

Exposed via `GET /api/assets/search`.

### P1-005 — Asset Route Enhancement

`GET /api/assets/[assetId]` now includes `attribute_values` with definition details
(code, name, unit, group_name, data_type) in the response.

### P1-006 — Definition POST + Tenant Scoping

`POST /api/asset-attribute-definitions` creates tenant-scoped definitions with
`scope: 'TENANT'` and `organization_id`. Handles unique constraint violations (409).

`GET` definitions scoped with `OR: [{ organization_id: null }, { organization_id: orgId }]`
to include both platform and tenant definitions.
