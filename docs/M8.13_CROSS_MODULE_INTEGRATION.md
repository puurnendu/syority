# M8.13 Cross-Module Integration

## Module Interaction Map

### M8.10 EVM ↔ M8.13 Progress

#### Current State

```
Activity.progress_percent → EvmCalculationService.calculateEv()
    ↓
EV = BAC × min(progress / 100, 1.0)
    ↓
SPI = ΣEV / ΣPV
CPI = ΣEV / ΣAC
    ↓
EAC = BAC / CPI
```

**Finding**: M8.10 reads `Activity.progress_percent` directly. It does NOT use any aggregated progress value.

**Question**: Should M8.13 become the authoritative physical-progress provider for EVM?

**Answer**: **NO** — EVM should continue reading `Activity.progress_percent` directly because:
1. EVM uses **per-activity** progress with **per-activity BAC** (cost-weighted)
2. M8.13 would aggregate to event/workpack level (duration-weighted)
3. These are different mathematical operations that should not be conflated
4. EVM earning rules (milestone: 0/100, LOE, normal) are activity-specific

**However**, M8.13 should:
- Provide the "physical progress" KPI that appears alongside EVM SPI
- Ensure `Activity.progress_percent` is the single input to both systems
- Eliminate the duplicate SPI calculation in `portfolio-stats`

**Circular Dependency Risk**: NONE — both systems READ from Activity.progress_percent (write is upstream)

### M8.12 Material ↔ M8.13 Progress

#### Current Integration

```
MaterialSupplyRecord → workpack_material_lines (qty updates)
    ↓
MaterialReadinessService.calculateLineReadiness()
    ↓
MaterialConstraint.constraint_date
    ↓
MaterialScheduleIntegrationService.applyConstraints()
    ↓
Activity.planned_start (adjusted pre-CPM)
    ↓
calculateSchedule() (CPM engine)
    ↓
Activity.early_start/finish, float, critical path
```

**Does material readiness affect progress?**

| Impact | Current | Correct? |
|--------|---------|----------|
| Material → planned dates | ✅ Yes (constraint injection) | ✅ Correct |
| Material → forecast dates | ✅ Yes (via CPM propagation) | ✅ Correct |
| Material → actual progress | ❌ No | ✅ Correct (progress is actual work done) |
| Material → activity status | ❌ No (could block) | ⚠️ Consider adding "material_blocked" status |
| Material → balance work | ❌ Not directly | ✅ Correct (balance = 100% - actual progress) |

**Integration is logically correct.** Material readiness affects WHEN work CAN happen (dates), not WHETHER work HAS happened (progress).

### M8.11 Scope Change ↔ M8.13 Progress

#### Critical Question: Scope Change → Progress Denominator

**Scenario**: 200 activities exist, 100 are complete (50% progress). M8.11 adds 20 new activities.

**Current behavior:**
```
Before scope change: progress = 100/200 × duration_weighting
After scope change:  progress = 100/220 × duration_weighting
                     (progress drops from ~50% to ~45%)
```

**Is this correct?** YES — the overall turnaround has more work, so progress should decrease.

**But the following must be reportable:**
- Original scope progress: 100/200
- Total scope progress: 100/220
- Scope change impact on progress: -5%

**M8.13 must support:**
1. **Total progress** — all activities regardless of when added
2. **Original scope progress** — activities existing at baseline creation
3. **Scope change contribution** — progress of activities added after baseline

**Implementation**: Tag activities with `baseline_id` at baseline creation time. Activities without a baseline tag are "post-baseline" additions.

### M8.9 Scenario ↔ M8.13 Progress

#### Current State

Scenarios are READ-ONLY projections. `ScenarioCalculationService` runs CPM on effective activities (live + overrides) without mutating live data.

**M8.13 should expose progress in four dimensions:**

| Dimension | Source | Mutating? |
|-----------|--------|-----------|
| **Current** | Live `Activity.progress_percent` | Read-only |
| **Baseline** | `BaselineActivity.planned_*` at snapshot time | Read-only (frozen) |
| **Forecast** | `ScheduleForecastService` projected remaining duration | Read-only (computed) |
| **Scenario** | `EvmScenarioProjection` projected progress | Read-only (virtual) |

**Integration**: Scenario projections should be available as an overlay in M8.13 dashboards, showing "if we apply Scenario X, projected progress by date Y would be Z%".

## Operational Workflow Audit

### Actual Implemented Sequence

```
1. Event Created (Event model)
    ↓
2. Shutdown Scope Defined (ShutdownScope → ScopeItem)
    ↓
3. Workpacks Created from Scope Items (WorkpackInstantiation)
    ↓
4. Activities Created from Templates (Activity, links to ActivityLibrary)
    ↓
5. Relationships Created (ActivityRelationship)
    ↓
6. Resources Assigned (ActivityResource)
    ↓
7. Materials Assigned (workpack_material_lines)
    ↓
8. Schedule Calculated (scheduleEngine.calculateSchedule)
    ↓ (writes planned_start/end, early_start/finish, float, critical)
9. Baseline Created (ScheduleBaseline + BaselineActivity)
    ↓
10. Materials Supply Tracked (MaterialSupplyRecord)
    ↓
11. Material Constraints Evaluated (MaterialReadinessService)
    ↓ (constraint injection into planned_start)
12. Schedule Recalculated (if constraints changed)
    ↓
13. Execution Begins — Progress Recorded
    ↓ (Activity.progress_percent updated)
14. ProgressLog Created (audit trail)
    ↓
15. EVM Snapshot Taken (manual or triggered)
    ↓ (EvmSnapshotService.takeSnapshot)
    ↓
16. Scope Changes Discovered (DiscoveryWork)
    ↓
17. Scope Change Proposed (ScheduleScopeChange → ScheduleScopeChangeItem)
    ↓
18. Scope Change Applied (ScopeChangeApplicationService — creates activities)
    ↓ (no automatic re-baselining, no progress recalculation)
    ↓
19. Scenario Analysis (read-only projection)
    ↓
20. Management Dashboard Viewed
    ↓ (multiple dashboards, multiple calculations)
```

### Missing Links Identified

| Gap | Description | Risk |
|-----|-------------|------|
| Step 13→14 | ProgressLog not always created on progress change | Incomplete audit trail |
| Step 13→Workpack | Workpack.overall_progress not auto-synced | Stale dashboard data |
| Step 18→9 | No automatic re-baselining after scope change | EVM variance distorted |
| Step 13→15 | EVM snapshot not triggered by progress change | Stale EVM data |
| Step 20 | No common calculation service | Inconsistent KPIs |
