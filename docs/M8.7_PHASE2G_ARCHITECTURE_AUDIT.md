# M8.7 Phase 2G - Architecture Audit

## 1. Goal
Evaluate the existing production architecture of the Resource Leveling and Scheduling engines prior to embarking on Phase 2G: Advanced Multi-Resource/Priority Leveling. The goal is to identify systemic risks, duplications, hidden mutation paths, and inconsistencies that must be addressed or documented.

## 2. File & Component Review

### 2.1 Prisma Schema (`prisma/schema.prisma`)
- **Strengths:** 
  - `ActivityResource` is correctly linked to `Activity`, `ResourceType`, and `Contractor`.
  - `ResourceCapacity` correctly tracks time-phased capacity limits, shift, resource type, and contractor.
  - `ActivityRelationship` and `Activity` are solid for CPM calculation.
- **Identified Defects/Gaps:**
  - `Activity` models lack a `shift_id` field. Currently, the `ResourcePlanningService` ignores shift capacities for demand aggregation (`if (res.shift !== null) continue;`) because activities aren't explicitly assigned to shifts in a way the planner engine can detect easily. *Resolution:* Phase 2G will introduce shift-level simulation where applicable, or we must document that demand remains daily aggregated unless an activity is shift-bound.
  - No persistent `Simulation` or `Scenario` tables exist. *Resolution:* Following invariant 2G rule, scenarios will remain ephemeral in-memory/API payloads to avoid database bloat unless strictly required later.

### 2.2 Schedule Engine (`src/lib/scheduleEngine.ts`)
- **Strengths:** 
  - Pure deterministic, purely topological Kahn's algorithm implementation.
  - Correct float calculations, cycle detection, and backward/forward passes.
- **Identified Defects/Gaps:** 
  - Float exhaustion is currently calculated using a uniform `working_hours_per_day` parameter (default 10). This works well, but advanced scheduling might demand shift-aware float (e.g., Night vs Day shifts). *Resolution:* Documented. For Phase 2G, we will maintain the existing float math but expose explicit project-end date impacts.

### 2.3 Resource Planning Service (`src/core/resources/ResourcePlanningService.ts`)
- **Strengths:**
  - Single source of truth for Demand vs Capacity aggregation.
- **Identified Defects/Gaps:**
  - Assumes a flat 10-hour work day (`HOURS_PER_DAY = 10;`) hardcoded inside the demand iteration loop.
  - Silently discards shift-based capacities during daily variance aggregations. *Resolution:* Needs a more nuanced approach in 2G.2 (Shift Capacity Imbalance detection).

### 2.4 Resource Constraint Service (`src/core/resources/ResourceConstraintService.ts`)
- **Strengths:**
  - Categorizes 'hard', 'soft', and 'info' constraints cleanly.
  - Identifies affected vs critical activities.
- **Identified Defects/Gaps:**
  - Missing constraint types (e.g., `MULTI_RESOURCE_CONFLICT`, `FLOAT_RISK`, `PROJECT_END_DATE_RISK`). *Resolution:* Phase 2G.2 will expand this taxonomy massively.

### 2.5 Resource Leveling Service (`src/core/resources/ResourceLevelingService.ts`)
- **Strengths:**
  - Safely simulates date shifts.
  - Employs deterministic sorting (float + penalty + Activity ID).
- **Identified Defects/Gaps:**
  - Currently loops constraints and resolves them 1 by 1 linearly. It does not look at Multi-Resource conflicts (e.g., if Activity A uses Cranes AND Welders).
  - Uses an expensive inner loop (recalculates CPM for every single day shifted). *Resolution:* Needs an optimization pass in Phase 2G.4 to batch shifts or optimize multi-resource resolution scoring.

### 2.6 Resource Leveling Apply Service (`src/core/resources/ResourceLevelingApplyService.ts`)
- **Strengths:**
  - Fully transactional.
  - Includes robust Snapshot Drift protection (throws `409 Conflict`).
- **Identified Defects/Gaps:**
  - No defects found. The transaction boundary safely encompasses schedule recalculation and audit logs.

## 3. Systemic Conclusion
The foundation is rock solid. The segregation of concerns (Planning -> Constraint -> Leveling -> Apply) is strictly observed. The only architectural modifications required for Phase 2G are:
1. Enhancing the constraint taxonomy.
2. Building the `ResourceConflictService` to rank multi-resource constraints.
3. Expanding the simulation memory payload to hold Scenario metadata.
4. UI Enhancements for planner visualizations.

No duplicate engines, tables, or destructive mutation paths were found. The system is ready for Phase 2G.
