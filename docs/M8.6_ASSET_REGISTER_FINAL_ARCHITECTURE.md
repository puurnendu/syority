|------|------------|

## FINAL BUSINESS RULE CLARIFICATIONS

> [!IMPORTANT]
> The following 10 business rules are **authoritative** and supersede any conflicting detail in the original architecture. All affected sections below have been updated accordingly.

### BRC-1: AI DATA → PLANNER VERIFICATION → MASTER DATA

AI is the **initial data population** mechanism. The flow is:

```
SOURCE DOCUMENT → AI EXTRACTION → AI-EXTRACTED DATA → PLANNER REVIEW → VERIFIED ASSET MASTER
```

**Critical rules:**
- The original AI-extracted value **MUST NOT be erased** when a planner modifies it
- The original AI extraction remains **permanently accessible** as historical/reference information
- The system must show both CURRENT verified value AND full HISTORY including AI values
- If AI extracts a new value later, it **MUST NOT overwrite** an existing planner-verified value
- New AI extractions become **candidate/review records** until a planner explicitly accepts them
- Field-level "History / Source / Audit" must be available on the Technical Data page

### BRC-2: ONE PRIMARY EQUIPMENT PER WORKPACK

```
ONE WORKPACK = ONE PRIMARY EQUIPMENT / ASSET
```

- WP-001 → 31-E-116 Heat Exchanger
- WP-002 → 31-V-201 Vessel
- WP-003 → 31-E-117 Heat Exchanger

Workpack is NOT a multi-equipment container. It remains the planning and execution package for **one primary Asset**.

### BRC-3: EXECUTION VIEWS FOR MULTI-EQUIPMENT TEAMS

Execution teams that work across multiple equipment use **Execution Views / Team Work Queues**, NOT merged Workpacks.

### BRC-4: FOUR STRICT DATA TYPES

| Type | Purpose | Example | Is Master? |
|------|---------|---------|-----------|
| **A. Asset Master Data** | Permanent equipment identity and technical information | 31-E-116, Tube OD = 25.4 mm | ✅ YES |

### BRC-5: TWO-LEVEL AUDIT ARCHITECTURE

**Level A — Entity / Local History:**
Every important entity exposes its own history (Asset, Workpack, Activity, Document, Blind, etc.)

**Level B — Global / Admin Audit:**
Consolidated audit stream across the entire organization with filtering by user, date/time, organization, entity type, entity ID, action, module, field, old value, new value.

### BRC-6: AI EXTRACTION HISTORY IS IMMUTABLE REFERENCE EVIDENCE

For every AI-derived field, retain permanently:
- AI model, extraction job, source document, document revision, page, source region
- Extracted value, confidence, extraction timestamp, extraction status
- Planner decision, decision timestamp, planner identity, final accepted value

Viewable from the Asset Technical Data page without navigation away.

## 2. DECISION 1 — ASSET VS LINE IDENTITY

### Decision: LINE REMAINS A SEPARATE ENTITY

**Rationale:**

The existing `line_lists` model ([schema.prisma L2213–L2258](file:///C:/DEV/STO/prisma/schema.prisma#L2213-L2258)) is a **physically and logically different** engineering object from equipment. Lines have:
- `from_asset_id` / `from_nozzle_id` / `to_asset_id` / `to_nozzle_id` — Lines are *connections between* equipment, not equipment themselves
- `pipe_class`, `insulation_type`, `heat_tracing` — piping-specific attributes
- `joint_masters[]` — flanged joints along the line
- `nominal_size_inches`, `fluid_service_code`, `sequence_number` — piping nomenclature

Forcing lines into the `Asset` model would create:
1. Hundreds of null columns (lines have no `manufacturer`, `serial_number`, `weight_empty_kg`)
2. Broken `from_asset_id`/`to_asset_id` self-referencing semantics
3. Confusion between "I am equipment" and "I connect equipment"

### Implementation: Unified Search, Separate Tables

The Asset Register UI will provide a **unified search** that queries both `Asset` and `line_lists`:

```
User searches: "6"-P-221"
→ Search queries both Asset.tag_number AND line_lists.line_number
→ Results displayed in same list with a type indicator: ⚙ Equipment | ═ Line
→ Clicking a line opens a Line Detail view within the Asset Register UI
```

### Data Model

```
Asset (equipment)                    line_lists (piping)
├── tag_number: "31-E-116"           ├── line_number: "6"-P-221"
├── asset_type: "heat_exchanger"     ├── pipe_class: "A1A"
├── nozzles[]                        ├── from_asset_id → Asset
├── asset_lines[] ←────────────────→ ├── to_asset_id → Asset
└── ...                              └── joint_masters[]
```

**No new models needed.** The existing `asset_lines` join table ([L1678](file:///C:/DEV/STO/prisma/schema.prisma#L1678-L1687)) already provides the M:M relationship with `connection_type`.

### Changes Required

| Change | Scope |
|--------|-------|
| Add Line search to Asset Register API | API route modification |
| Add Line Detail view to Asset Register UI | New tab/page |
| Unify hierarchy tree to show Lines under System | UI modification |

## 3. DECISION 2 — ASSET ATTRIBUTE ARCHITECTURE

### Decision: EAV (Entity-Attribute-Value) WITH EQUIPMENT TYPE SCOPING

Following the proven `ActivityUdfDefinition → ActivityUdfValue` pattern ([schema.prisma L270–L332](file:///C:/DEV/STO/prisma/schema.prisma#L270-L332)), but purpose-built for Asset Register.

### New Models

#### AssetAttributeDefinition

Defines what attributes exist for each equipment type. Managed at organization level with platform-level defaults.

```prisma
model AssetAttributeDefinition {
  id                 String   @id @default(uuid()) @db.Uuid
  organization_id    String?  @db.Uuid          /// null = PLATFORM scope
  code               String                     /// "tube_od_mm", "shell_id_mm", "flow_rate_m3h"
  name               String                     /// "Tube OD", "Shell ID", "Flow Rate"
  description        String?
  data_type          String                     /// string, number, boolean, date, select
  unit               String?                    /// "mm", "barg", "°C", "kg", "m³/h"
  equipment_types    String[] @default([])      /// ["heat_exchanger", "vessel"] — empty = all
  group_name         String?                    /// "Dimensions", "Design Conditions", "Materials"
  group_sort_order   Int      @default(0)
  sort_order         Int      @default(0)
  is_required        Boolean  @default(false)
  is_design_basis    Boolean  @default(false)   /// True = part of design basis (versioned)
  validation_rule    Json?                      /// { min: 0, max: 1000, regex: "..." }
  select_options     Json?                      /// ["RF", "FF", "RTJ"] for data_type=select
  scope              String   @default("TENANT") /// PLATFORM | TENANT
  is_active          Boolean  @default(true)
  created_by         String?  @db.Uuid
  created_at         DateTime @default(now())
  updated_at         DateTime @updatedAt

  values             AssetAttributeValue[]
  history            AssetAttributeHistory[]

  @@unique([organization_id, code], name: "org_attr_code")
  @@index([organization_id, is_active])
  @@map("asset_attribute_definitions")
}
```

#### AssetAttributeValue — REVISED (BRC-1, BRC-6, BRC-8)

Stores the **current** value for a specific asset + attribute combination. Always exactly **one row** per asset+definition pair. This is the row that `getCurrentVerifiedAssetData()` reads.

```prisma
model AssetAttributeValue {
  id                  String   @id @default(uuid()) @db.Uuid
  organization_id     String   @db.Uuid
  asset_id            String   @db.Uuid
  definition_id       String   @db.Uuid

  /// Multi-type value storage (same pattern as ActivityUdfValue)
  value_string        String?
  value_number        Float?
  value_boolean       Boolean?
  value_date          DateTime? @db.Date

  /// ── PROVENANCE ──────────────────────────────
  source_type         String    @default("manual")  /// manual, ai_extraction, excel_import, document, field_survey, legacy_migration
  source_document_id  String?   @db.Uuid            /// FK to PlantDocument
  source_doc_revision String?                        /// Document revision at time of extraction
  source_page         Int?                           /// Page number in source document
  source_region       String?                        /// Bounding box or location hint

  /// AI extraction provenance (null if manual entry)
  ai_model            String?                        /// "gemini-2.5-pro"
  ai_confidence       Float?                         /// 0.0–1.0
  extraction_job_id   String?   @db.Uuid             /// FK to AiExtractionJob

  /// ── VERIFICATION ────────────────────────────
  status              String    @default("unverified")  /// unverified, ai_candidate, verified
  entered_by          String?   @db.Uuid
  entered_at          DateTime  @default(now())
  verified_by         String?   @db.Uuid
  verified_at         DateTime?
  verification_notes  String?

  /// ── METADATA ────────────────────────────────
  created_at          DateTime  @default(now())
  updated_at          DateTime  @updatedAt

  asset               Asset                    @relation(fields: [asset_id], references: [id], onDelete: Cascade)
  definition          AssetAttributeDefinition @relation(fields: [definition_id], references: [id])
  history             AssetAttributeHistory[]

  @@unique([asset_id, definition_id], name: "asset_attr_unique")
  @@index([asset_id, status])
  @@index([definition_id])
  @@map("asset_attribute_values")
}
```

#### AssetAttributeHistory — NEW (replaces AssetAttributeAudit)

**Genuinely immutable, append-only** history of every value that an attribute has ever held, including AI extractions and every planner decision. This is the table that powers field-level "History / Source / Audit".

> [!IMPORTANT]
> **Renamed from `AssetAttributeAudit` to `AssetAttributeHistory`** to clarify its purpose: this is the **full value history** (including permanently preserved AI extractions), not merely a change log.

> [!CAUTION]
> **STRICT APPEND-ONLY RULE:** No row in `AssetAttributeHistory` is EVER updated or deleted. Every event — AI extraction, planner acceptance, planner modification, planner rejection, manual entry, verification — is a **separate immutable row**. Planner decisions about AI extractions are linked via `refers_to_history_id`, never written onto the original AI extraction row.

```prisma
model AssetAttributeHistory {
  id                  String   @id @default(uuid()) @db.Uuid
  organization_id     String   @db.Uuid
  asset_id            String   @db.Uuid
  definition_id       String   @db.Uuid
  value_id            String?  @db.Uuid          /// FK to AssetAttributeValue (which current row this history belongs to)

  /// ── THE VALUE RECORDED BY THIS EVENT ────────
  value_string        String?
  value_number        Float?
  value_boolean       Boolean?
  value_date          DateTime? @db.Date

  /// ── FULL PROVENANCE (preserved immutably) ───
  source_type         String                     /// manual, ai_extraction, excel_import, document, field_survey, legacy_migration
  source_document_id  String?   @db.Uuid         /// FK to PlantDocument
  source_doc_revision String?
  source_page         Int?
  source_region       String?

  /// AI provenance (populated only for action=ai_extracted)
  ai_model            String?
  ai_confidence       Float?
  extraction_job_id   String?   @db.Uuid

  /// ── WHAT HAPPENED ───────────────────────────
  action              String                     /// ai_extracted, ai_accepted, ai_modified, ai_rejected, manual_entered, verified, superseded
  status_at_time      String                     /// The status this value had: ai_candidate, unverified, verified

  /// ── EVENT LINKAGE ───────────────────────────
  refers_to_history_id  String?  @db.Uuid        /// For decision events: FK to the original ai_extracted history row being decided upon

  /// ── WHO AND WHY ─────────────────────────────
  performed_by        String   @db.Uuid          /// User who performed this action
  performed_at        DateTime @default(now())
  reason              String?                    /// "Corrected per nameplate data", "Vendor drawing is preliminary"

  /// ── METADATA ────────────────────────────────
  created_at          DateTime @default(now())

  asset               Asset                    @relation(fields: [asset_id], references: [id], onDelete: Cascade)
  definition          AssetAttributeDefinition @relation(fields: [definition_id], references: [id])
  attribute_value     AssetAttributeValue?     @relation(fields: [value_id], references: [id])

  @@index([asset_id, definition_id, performed_at])
  @@index([asset_id, performed_at])
  @@index([organization_id, performed_at])
  @@index([refers_to_history_id])
  @@map("asset_attribute_history")
}
```

### Action Types

| Action | Meaning | Who | Modifies AssetAttributeValue? |
|--------|---------|-----|------------------------------|
| `ai_extracted` | AI extracted a value from a document | System | Yes (if no verified value exists) or No (if verified exists) |
| `ai_accepted` | Planner accepted an AI value as-is | Planner | Yes (promotes to verified) |
| `ai_modified` | Planner corrected an AI value and verified | Planner | Yes (writes corrected value as verified) |
| `ai_rejected` | Planner rejected an AI value | Planner | No |
| `manual_entered` | User manually entered a value | User | Yes |
| `verified` | User verified an existing unverified value | Planner | Yes (status → verified) |
| `superseded` | A new value replaced this one | System | No (records what was replaced) |

### Complete AI → Planner → Master Flow Example

Every step below is an **INSERT** into `AssetAttributeHistory`. No row is ever updated.

```
Step 1: AI EXTRACTION (first time — no existing value)
──────────────────────────────────────────────────────
AI extracts Tube OD = 25.0 mm from Datasheet Rev.3

→ AssetAttributeValue CREATED:
    value_number = 25.0
    status = "ai_candidate"
    source_type = "ai_extraction"
    ai_model = "gemini-2.5-pro"
    ai_confidence = 0.94
    source_document_id = (Datasheet Rev.3)

→ AssetAttributeHistory ROW #1 INSERTED:         ← id = "hist-001"
    action = "ai_extracted"
    value_number = 25.0
    status_at_time = "ai_candidate"
    source_type = "ai_extraction"
    ai_model = "gemini-2.5-pro"
    ai_confidence = 0.94
    source_document_id = (Datasheet Rev.3)
    refers_to_history_id = null                   ← this IS the original event
    performed_by = system_user
    performed_at = 2026-08-21 09:00:00


Step 2: PLANNER REVIEWS AND MODIFIES
─────────────────────────────────────
Planner changes value from 25.0 to 25.4 mm and verifies

→ AssetAttributeValue UPDATED:
    value_number = 25.4          ← planner's corrected value
    status = "verified"
    source_type = "manual"
    verified_by = planner_user
    verified_at = 2026-08-21 09:15:00

→ AssetAttributeHistory ROW #2 INSERTED:         ← SEPARATE row, decision event
    action = "ai_modified"
    value_number = 25.4          ← the planner's corrected value
    status_at_time = "verified"
    source_type = "manual"
    refers_to_history_id = "hist-001"             ← links to the AI extraction being decided
    performed_by = planner_user
    performed_at = 2026-08-21 09:15:00
    reason = "Corrected per nameplate inspection"

NOTE: Row #1 (the AI extraction) is UNTOUCHED. No fields were updated on it.
      It remains permanently accessible as reference evidence.
      Row #2 links to Row #1 via refers_to_history_id.


Step 3: LATER — AI EXTRACTS NEW VALUE FROM DIFFERENT DOCUMENT
─────────────────────────────────────────────────────────────
AI extracts Tube OD = 25.5 mm from a new Vendor Drawing Rev.1

→ AssetAttributeValue is NOT updated (status = "verified", AI cannot overwrite)

→ AssetAttributeHistory ROW #3 INSERTED:         ← id = "hist-003"
    action = "ai_extracted"
    value_number = 25.5
    status_at_time = "ai_candidate"
    source_type = "ai_extraction"
    ai_model = "gemini-2.5-pro"
    ai_confidence = 0.88
    source_document_id = (Vendor Drawing Rev.1)
    refers_to_history_id = null                   ← this IS the original event
    performed_by = system_user
    performed_at = 2026-08-21 14:00:00

The planner sees a notification: "New AI extraction differs from verified value"
The planner can accept, reject, or modify from the Technical Data page.


Step 4: PLANNER REJECTS THE NEW AI VALUE
────────────────────────────────────────
→ AssetAttributeValue remains unchanged (25.4 mm, verified)

→ AssetAttributeHistory ROW #4 INSERTED:         ← SEPARATE row, decision event
    action = "ai_rejected"
    value_number = 25.5          ← the AI value that was rejected
    status_at_time = "ai_candidate"
    refers_to_history_id = "hist-003"             ← links to the AI extraction being rejected
    performed_by = planner_user
    performed_at = 2026-08-21 15:00:00
    reason = "Vendor drawing is preliminary; nameplate value is authoritative"

NOTE: Row #3 (the AI extraction) is UNTOUCHED. No fields were updated on it.
      Row #4 is a separate event recording the planner's rejection decision.


Step 5 (alternative): PLANNER ACCEPTS AN AI VALUE
──────────────────────────────────────────────────
If instead the planner accepted 25.5 mm:

→ AssetAttributeHistory ROW #4A INSERTED (supersede old value):
    action = "superseded"
    value_number = 25.4          ← the old verified value being replaced
    status_at_time = "verified"
    refers_to_history_id = null
    performed_by = planner_user
    performed_at = 2026-08-21 15:00:00

→ AssetAttributeHistory ROW #4B INSERTED (acceptance decision):
    action = "ai_accepted"
    value_number = 25.5          ← the accepted AI value
    status_at_time = "verified"
    refers_to_history_id = "hist-003"             ← links to the AI extraction being accepted
    performed_by = planner_user
    performed_at = 2026-08-21 15:00:00
    reason = "Vendor drawing Rev.1 supersedes nameplate"

→ AssetAttributeValue UPDATED:
    value_number = 25.5
    status = "verified"
    verified_by = planner_user
    verified_at = 2026-08-21 15:00:00
```

### Append-Only Guarantee

| Operation | Allowed? | Explanation |
|-----------|----------|-------------|
| INSERT new history row | ✅ Always | Every event is a new row |
| UPDATE existing history row | ❌ Never | Rows are immutable once created |
| DELETE history row | ❌ Never | History is permanent evidence |
| Link decision to AI extraction | ✅ Via `refers_to_history_id` | The AI row itself is never modified |

Every `AssetAttributeValue` row records its **current** provenance. Every **historical** provenance is preserved immutably in `AssetAttributeHistory`.

```

│                                                             │

│  STATUS:         verified                                   │
│                                                             │
│  CURRENT PROVENANCE:                                        │

│    verified_at:         2026-08-21 09:15:00                  │
│                                                             │
├─────────────────────────────────────────────────────────────┤
```

## 5. DECISION 4 — VERSIONING

### Decision: B — ATTRIBUTE-LEVEL VERSIONING VIA AssetAttributeHistory

### Rationale

Asset-level versioning (Option A) would create massive JSON snapshots for every minor field change. Attribute-level versioning via `AssetAttributeHistory` provides:
- Precise "who changed what, when, why" per field
- No wasted storage for unchanged fields
- Easy "show me the history of design_pressure" queries
- **Permanent preservation of AI extraction values** (BRC-1, BRC-6)

### Verification Lifecycle

```
                ┌──────────────┐
                │  UNVERIFIED  │  ← Manual entry without review
                └──────┬───────┘
                       │ AI extraction
                       ▼
                ┌──────────────┐
                │ AI_CANDIDATE │  ← AI-proposed value, awaiting planner review
                └──────┬───────┘
                       │ Planner accepts/modifies/verifies
                       ▼
                ┌──────────────┐
                │   VERIFIED   │  ← Current approved master value
                └──────────────┘
```

### Rules — REVISED (BRC-1, BRC-6, R2.1 consistency)

| Rule | Implementation |
|------|---------------|
| AI extraction → `ai_candidate` status on AssetAttributeValue | ExtractionService sets status (only if no verified value exists) |
| AI extraction → `ai_extracted` row in AssetAttributeHistory | **Always INSERTED — immutable evidence** |
| Manual entry → `unverified` status | API sets status + `manual_entered` history row |
| Planner accepts AI value as-is | **Separate** `ai_accepted` history row with `refers_to_history_id` pointing to the AI extraction row |
| Planner modifies AI value | **Separate** `ai_modified` history row with the corrected value + `refers_to_history_id` |
| Planner rejects AI value | **Separate** `ai_rejected` history row with `refers_to_history_id` — **NO UPDATE** to original AI row |
| Planner clicks "Verify" (non-AI value) | `verified` history row INSERTED |
| **AI NEVER overwrites `verified` value** | API enforces: AI inserts `ai_extracted` history row only; AssetAttributeValue untouched |
| **No row in AssetAttributeHistory is EVER updated** | All rows are INSERT-only; decisions are separate rows linked via `refers_to_history_id` |
| **No row in AssetAttributeHistory is EVER deleted** | Append-only table; permanent evidence |
| Display always shows `verified` first, with "View History" action | UI enforces |
| AI extractions pending review shown as notifications | Check: `ai_extracted` rows with no corresponding `ai_accepted`/`ai_modified`/`ai_rejected` row |

### How "Current Verified" Works — CLARIFIED

The `AssetAttributeValue` table always holds **exactly one row** per asset+definition — the **current** value. The `status` field indicates trust level.

**When an AI extraction arrives for an attribute that already has a `verified` value:**

1. The `AssetAttributeValue` row is **NOT modified** (verified value is protected)
2. A new `AssetAttributeHistory` row is **INSERTED** with `action='ai_extracted'`
3. The UI detects pending AI extractions by querying for `ai_extracted` rows with no corresponding decision row
4. The planner can then accept, modify, or reject — each producing a **new** history row

**When a planner accepts/modifies an AI value:**

1. A `superseded` history row is INSERTED preserving the old verified value
2. A `ai_accepted` or `ai_modified` history row is INSERTED with `refers_to_history_id` pointing to the AI extraction
3. The `AssetAttributeValue` row is updated with the new/accepted value
4. The original `ai_extracted` history row remains **completely untouched**

**When a planner rejects an AI value:**

1. A `ai_rejected` history row is INSERTED with `refers_to_history_id` pointing to the AI extraction
2. No other rows are modified

**Result:**
- `SELECT * FROM asset_attribute_values WHERE asset_id = X` → all current values
- `SELECT * FROM asset_attribute_history WHERE asset_id = X AND definition_id = Y ORDER BY performed_at` → complete field history with all AI extractions preserved

## 8. DECISION 7 — WORKPACK SNAPSHOT — REVISED (BRC-2, BRC-4, BRC-9)

### Decision: ONE PRIMARY ASSET SNAPSHOT PER WORKPACK REVISION

Because the business rule is **ONE WORKPACK = ONE PRIMARY ASSET**, the snapshot model is simplified:

### New Model: WorkpackAssetSnapshot

```prisma
model WorkpackAssetSnapshot {
  id                 String   @id @default(uuid()) @db.Uuid
  workpack_id        String   @db.Uuid
  asset_id           String   @db.Uuid
  snapshot_revision  String                    /// "R0", "R1" — matches WorkpackVersion revision
  asset_data_json    Json                      /// Full Asset core columns at snapshot time
  attributes_json    Json                      /// All AssetAttributeValue rows at snapshot time (verified values only)
  nozzles_json       Json?                     /// Nozzle data at snapshot time
  lines_json         Json?                     /// Connected lines at snapshot time
  documents_json     Json?                     /// Document references at snapshot time
  snapshotted_by     String   @db.Uuid
  snapshotted_at     DateTime @default(now())

  workpack           Workpack @relation(fields: [workpack_id], references: [id])
  asset              Asset    @relation(fields: [asset_id], references: [id])

  @@unique([workpack_id, snapshot_revision], name: "wp_asset_snapshot_rev")
  @@index([workpack_id])
  @@map("workpack_asset_snapshots")
}
```

### Uniqueness — SIMPLIFIED

The unique constraint is `[workpack_id, snapshot_revision]` — not `[workpack_id, asset_id, snapshot_revision]`.

Because one Workpack has exactly one primary asset (`Workpack.asset_id`), there is no need for a composite key including `asset_id`. The `asset_id` is included for referential integrity and query convenience, not uniqueness.

### Lifecycle

```
Workpack Status     Asset Data Source               Snapshot Action
───────────────     ────────────────               ───────────────
DRAFT               Live getCurrentVerifiedData()   No snapshot
PENDING_APPROVAL    Live getCurrentVerifiedData()   No snapshot
ISSUED              → Snapshot created →             CREATE WorkpackAssetSnapshot
IN_PROGRESS         Read from Snapshot               No change
COMPLETED           Read from Snapshot               No change
CLOSED              Read from Snapshot               No change
RE-ISSUED           → New snapshot →                 NEW snapshot_revision row
```

### Rules

| Rule | Enforcement |
|------|------------|
| Draft Workpack always sees current Asset data | Query `getCurrentVerifiedAssetData()` |
| Issued Workpack is frozen | `WorkpackAssetSnapshot` created at status transition to `issued` |
| Asset data change after issue does NOT affect Workpack | Snapshot is immutable |
| PdfService for issued Workpack reads snapshot | Conditional: if snapshot exists, use it; else live |
| Re-issue creates new snapshot | New `snapshot_revision` row (old snapshot preserved) |
| Snapshot stores verified values with provenance | `attributes_json` includes source and verification info |

### Multi-Equipment for Execution Teams — NOT Via Snapshot

Teams that need to see multiple equipment use **Execution Views** (BRC-3), not multi-asset Workpacks. The snapshot remains 1:1 with the Workpack's primary asset.

### Integration with Existing WorkpackVersionService

The existing [`WorkpackVersionService.autoSnapshot()`](file:///C:/DEV/STO/src/modules/Workpack/Services/WorkpackVersionService.ts#L10-L46) already creates `WorkpackVersion` records. The new `WorkpackAssetSnapshot` will be created **alongside** the `WorkpackVersion` during the issue workflow transition.


### Key Principle: AI History is NEVER Modified

Every AI extraction creates an `AssetAttributeHistory` row that is **immutable**. No field on an AI extraction row is ever updated — not even to record a planner decision. Planner decisions are always recorded as **separate rows** linked via `refers_to_history_id`. The extracted value, confidence, source document, and AI model remain exactly as they were at extraction time.

### Derived Registers

Derived registers are **query views** over existing data, not separate data stores:

| Register | Source Tables | Query |
|----------|-------------|-------|
| **Blind Register** | `Blind` + `system_blinds` | All blinds for a site/unit/system |
| **Nozzle Register** | `nozzles` | All nozzles with asset details |
| **Flange Register** | `joint_masters` | All joints with specifications |
| **Line Register** | `line_lists` | All lines with connected equipment |
| **Equipment Register** | `Asset` + `AssetAttributeValue` | Equipment with type-specific attributes |

### Execution Views — DERIVED OPERATIONAL WORKSPACES (BRC-3, R2.1)

Execution Views are **derived operational workspaces** — not merely read-only screens. They aggregate activities, blinds, and other execution data from multiple Workpacks for discipline-specific teams, and allow teams to **perform execution actions** that write to the underlying execution entities.

> [!IMPORTANT]
> **Read-Write Rule:** Execution Views can READ from and WRITE TO execution entities (`Activity`, `ProgressLog`, `Blind`, `CertificateInstance`, `FormInstance`, `PunchListItem`, etc.). They NEVER write to or modify Asset Master Data (`Asset`, `AssetAttributeValue`, `AssetAttributeHistory`). Asset Master Data is read-only from the perspective of execution.

| Execution View | Query Source | Team Can Read | Team Can Write To |
|---------------|-------------|---------------|-------------------|
| Inspection | `Activity` + `CertificateInstance` | Activities, checklists, certificates across WPs | `ProgressLog`, `CertificateInstance`, `FormInstance` |
| Blinding | `Blind` + Activities | Blinds, insert/remove status across WPs | `Blind` (insert/remove), `ProgressLog` |
| Scaffolding | `Activity` WHERE scaffolding | Scaffolding requirements across WPs | `ProgressLog`, `FormInstance` |
| NDT | `Activity` + procedures | NDT activities + procedures across WPs | `ProgressLog`, `CertificateInstance` |
| Hot Work | `Activity` + permits | Hot work permits + activities across WPs | `ProgressLog`, `FormInstance` |
| Hydrojetting | `Activity` | Hydrojetting activities across WPs | `ProgressLog` |
| Mechanical | `Activity` | Mechanical activities across WPs | `ProgressLog`, `PunchListItem` |
| Electrical | `Activity` | Electrical activities across WPs | `ProgressLog`, `CertificateInstance` |
| Instrumentation | `Activity` | Instrumentation activities across WPs | `ProgressLog`, `CertificateInstance` |
| Painting | `Activity` | Painting activities across WPs | `ProgressLog` |
| Insulation | `Activity` | Insulation activities across WPs | `ProgressLog` |
| Lifting | `Activity` | Lifting activities across WPs | `ProgressLog`, `FormInstance` |
| Flushing | `Activity` | Flushing activities across WPs | `ProgressLog`, `CertificateInstance` |
| Reinstatement | `Activity` | Reinstatement activities across WPs | `ProgressLog`, `PunchListItem` |

### Write-Through Architecture

```
Execution View (e.g., Blinding Team)
│
├── READS from:  Blind, Activity, Asset (read-only), Workpack (read-only)
│
├── WRITES to:   Blind (insert status, remove status, witness)
│                ProgressLog (progress updates)
│                FormInstance (checklists)
│                AuditLog (automatic)
│
└── NEVER writes to: Asset, AssetAttributeValue, AssetAttributeHistory
```

All writes go through the **existing** API endpoints for the underlying entities. The Execution View UI calls the same APIs that the Workpack detail UI would call — it simply aggregates items from multiple Workpacks into one team-oriented workspace.

### Execution View Data Model

Each execution view row presents:


### API Endpoints

```
GET  /api/registers/[type]?site_id=X&unit_id=Y            ← Derived registers (read-only)
GET  /api/execution-views/[discipline]?site_id=X&event_id=Y   ← Execution views (read: aggregated)
POST /api/activities/[id]/progress                         ← Write: existing Activity API
PUT  /api/blinds/[id]                                      ← Write: existing Blind API
POST /api/certificates/[id]/sign                           ← Write: existing Certificate API
```

Execution Views do NOT have their own write APIs. All mutations go through the existing entity APIs, ensuring data integrity, audit logging, and permission checks are consistently enforced regardless of whether the user accessed the entity through a Workpack detail page or an Execution View.

## 22. EXPLICIT DECISIONS AND RATIONALE

| # | Decision | Option Chosen | Alternatives Rejected | Rationale |
|---|----------|--------------|----------------------|-----------|
| 1 | Line identity | Separate table, unified search | Merge into Asset table | Lines have different structure; null columns; self-referencing breaks |
| 2 | Attribute storage | EAV with definitions | Fixed columns; JSON blob | Per-type configurability without migration |
| 3 | Provenance location | Embedded on value + full history table | Separate provenance table | Current provenance on value for fast reads; full history in dedicated table for completeness |
| 4 | Versioning | Attribute-level via AssetAttributeHistory | Asset-level JSON snapshot | Precise field history; AI preservation; no snapshot bloat |
| 5 | Hierarchy vs Relationships | Separate models | Single polymorphic model | Different concerns; cleaner API |
| 6 | Current value retrieval | One row per asset+def in AssetAttributeValue | Separate current/history tables | Simple; predictable; fast |
| 7 | Workpack snapshot | One primary asset per snapshot per revision | Multi-asset snapshot | Aligns with BRC-2 (one asset per WP); simpler uniqueness |
| 8 | Migration strategy | Phased parallel-write | Big-bang cutover | Safest; no data loss; gradual |
| 9 | AI history preservation | Immutable AssetAttributeHistory rows | Overwrite + audit log | AI extractions are permanent reference evidence (BRC-1, BRC-6) |
| 10 | Multi-equipment teams | Execution Views (derived operational workspaces) | Multi-asset Workpacks | BRC-3: Workpack stays 1:1 with asset; views aggregate; teams write to execution entities |
| 11 | Audit levels | Entity history + Global audit stream | Single audit table | BRC-5: both local drill-down and admin-wide visibility |
| 12 | History model naming | `AssetAttributeHistory` | `AssetAttributeAudit` | "History" better communicates preserved AI values + full timeline |
| 13 | History immutability | Strictly append-only; decisions as separate linked rows | UPDATE planner_decision on AI rows | R2.1: No row is ever modified; `refers_to_history_id` links decisions to extractions |
| 14 | Execution View write model | Write-through to existing entity APIs | Execution View-specific write APIs | R2.1: Consistent audit, permissions, validation regardless of access path |
