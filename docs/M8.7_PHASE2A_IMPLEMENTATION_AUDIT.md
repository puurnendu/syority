# M8.7 Phase 2A — Implementation Audit

## 1. Activity Execution State Hardening
**Current Implementation:**
`FieldExecutionService.executeActivityAction()` currently checks if the `Activity` exists and is not deleted. It does **not** verify the parent Workpack's status before allowing an update.
**Gap:** A user could potentially start an activity for a `draft` or `approved` Workpack directly via API if they know the Activity ID.
**Action Required:** Fetch the `workpack.status` when querying the `existing` activity, and explicitly throw an error if the status is not `issued` or `in_execution`.

## 2. Validate Activity Ownership
**Current Implementation:**
`executeActivityAction()` queries: `where: { id: params.activityId, organization_id: orgId, deleted_at: null }`. 
This correctly enforces tenant isolation (`organization_id`). 
**Gap:** It assumes that if the Activity belongs to the org, the user can modify it. It does not verify the Event or the explicit scope assignment of the Workpack.
**Action Required:** The `Workpack` is already fetched (`include: { workpack: true }`). We must verify that `existing.workpack` is valid, properly scoped to an Event, and the tenant logic is unbroken up the hierarchy.

## 3. ProgressLog Semantics
**Current Implementation:**
When progress is updated, `executeActivityAction()` creates a `ProgressLog` with `progress_percent: newProgress`. 
**Finding:** `ProgressLog.progress_percent` represents the **absolute, cumulative progress** of the Activity at that point in time, *not* incremental progress.
**Gap:** It lacks explicit Shift Context (day/night, exact execution date if logging retroactively).
**Action Required:** Preserve the absolute progress semantic, but expand the API to accept `log_date` and `shift` so `ProgressLog` captures the execution context.

## 4. syncWorkpackProgress() Audit
**Current Implementation:**
It fetches all non-deleted activities for the Workpack: `select: { duration_hours: true, progress_percent: true }`.
It calls `calculateWeightedProgress()`, which computes:
`Sum(progress_percent * duration_hours) / Sum(duration_hours)`
If total duration is 0, it falls back to a simple average: `Sum(progress_percent) / Count(activities)`.
**Gap:** 
- **Cancelled/On-Hold Activities:** It does not filter out `status = 'cancelled'`. A cancelled activity with 0% progress would artificially deflate the Workpack's progress.
- **Zero-Activity Workpacks:** Returns 0 instead of maintaining completion state.
**Action Required:** Exclude cancelled activities from the rollup calculation. Retain the duration-weighted semantic as it aligns with standard planning modules (Earned Value / Duration weighting).

## 5 & 6. Shift Context Formalization
**Current Implementation:**
`ExecutionCockpit` has state for `shiftType` ('day' | 'night'). However, the `/api/execution/activity-action` endpoint ignores this and just uses `new Date()` for the progress entry.
`SafetyLog` is the only model natively storing `shift` alongside `log_date` per `event_id`.
**Gap:** There is no unified Execution Shift Context linking Progress Updates to a specific Shift.
**Action Required:** We do NOT need a new Shift model. 
- Modify `/api/execution/activity-action` to accept `shift` (String: 'day' | 'night') and `execution_date` (Date).
- Ensure `ProgressLog` can store this. (Currently `ProgressLog` has `log_date` but no explicit `shift` string, though we could add a `shift` string to `ProgressLog` or rely on time-of-day. Adding `shift` string to `ProgressLog` is the cleanest minimal schema change, or alternatively just ensuring `log_date` maps to the active shift).
- Actually, adding `shift String?` to `ProgressLog` is a very minor, highly justified schema change to explicitly link progress to the Field Shift without building a complex relational Shift model.

## 7 & 8. Execution Cockpit and Shift Reports
**Current Implementation:**
`ExecutionCockpit` handles direct action submissions without passing shift context. 
`/shift-reports` generates WhatsApp text.
**Action Required:** 
- Enhance `ExecutionCockpit` to explicitly pass `shift` and `execution_date` to `activity-action`.
- Ensure `getExecutionSummary` aggregates based on `execution_date` context so that Field Execution and Shift Reports pull from the exact same source of truth.

## 9. API Contract Updates
`/api/execution/activity-action` will require:
```json
{
  "activityId": "uuid",
  "action": "UPDATE_PROGRESS",
  "progress": 50,
  "notes": "...",
  "execution_date": "2026-10-15",
  "shift": "day"
}
```

## Verdict
**CONDITIONAL PASS for Phase 2A Readiness.**
The architecture is solid, but the execution gates, cancelled activity filtering, and explicit shift context must be implemented before the field system is considered hardened.
