### Most Important Finding

> **Scaffolding (m³), Painting (m²), and Insulation (m²) are NOT P6 UDFs.**

## ANSWERS TO THE 10 FINAL ARCHITECTURE DECISIONS

### A. Activity Library — Canonical Identity
The canonical identity is the **Level Code** (native iPlan code: Ex.RTub, PIP.Wel, etc.). Each Activity Library item maps a native code to a canonical SYORITY code (REPAIR.RETUBING, REPAIR.WELDING).

### B. Activity Code — Canonical Structure
**Three-level**: Native iPlan Code → Canonical SYORITY Code (Family.Type) → Activity Family.

### C. Level Code — Relationship
Native iPlan Level Code is the P6 export dimension. Canonical SYORITY Level Code is the cross-equipment reporting dimension. They coexist.

### D. UDF Definition — Where It Lives
A **UdfDefinition** table/entity that defines: name, unit, data type, applicable activity types, whether progress-driving. Referenced by templates and the planner UI.

### E. UDF Value — Planned Quantity
**ActivityUdfValue.value_number** — entered by planner during workpack creation.

### F. Actual Quantity — Where It Lives
**ProgressLog.quantity_actual** — entered by field supervisor during execution. Time-series capable.

### G. Progress — Calculation
- **Duration-based**: Σ(activity.progress × duration) / Σ(duration)
- **Quantity-based**: actual / planned × 100 (per UDF)
- **QA-based**: cleared_count / total_count (separate KPI)

### H. Reporting Dimensions
13+ dimensions: Event, Unit, System, Equipment Type/Tag, Level Code, Phase, Discipline, Contractor, Job Type, QA AI, QA TS, UDF/Quantity, Workpack Status.

### I. P6 Export
Output adapter generating XML with 13 Activity Code Types. Quantities (scaffolding, painting, insulation) are NOT exported (matching iPlan behavior).

### J. System of Record
**YES** — SYORITY can operate independently of P6. All reporting dimensions, quantities, progress, and QA tracking are natively available.
