# M8.9 PROPOSED BLUEPRINT: Scenario Planning & Schedule Optimization

**Status:** PROPOSED - AWAITING APPROVAL
**Date:** 2026-08-31

## 1. Executive Objective
M8.9 will deliver **What-If Scenario Planning & Schedule Optimization**. 
After M8.7 established resource constraints and M8.8 delivered rigorous schedule control and baselines, the logical next step is empowering turnaround planners to proactively *simulate and resolve* the variances detected in M8.8. M8.9 allows planners to branch the current schedule, run resource-constrained leveling (`ResourceConstraintService`) and CPM calculations (`scheduleEngine.ts`) in an isolated sandbox, compare the health (SHI) of the new scenario against the M8.8 baseline, and promote the winning scenario as the new active baseline via the M8.8 Change Control system.

## 2. Business Problems
- **Reactive Variance:** M8.8 highlights variances and float erosion, but planners have no safe sandbox to test recovery strategies without altering live execution data.
- **Resource Bottlenecks:** Planners need to dynamically test shifting activity logic or increasing shift capacities to resolve resource overloads identified in the SHI.
- **Traceability of Corrective Action:** Currently, if a schedule falls behind, the recovery plan is built externally (e.g., P6) and pushed back. Syority needs native corrective simulation.

## 3. Proposed Feature Set

### M8.9-01: Scenario Sandbox (Branching)
- **User Problem:** Planners need to test logic/resource changes safely.
- **User Workflow:** Planner clicks "Create Scenario" from the M8.8 Schedule Control Dashboard, creating an isolated snapshot of the current event schedule.
- **Inputs:** Event ID, Scenario Name.
- **Outputs:** Scenario ID.
- **Business Rules:** Scenarios do not affect live Workpacks or current Baseline.
- **Dependencies:** M8.8 Baseline infrastructure.
- **Expected UI Location:** Planner Workspace -> Schedule Dashboard -> "Scenarios" Tab.
- **API/Data/Security:** `POST /api/events/:id/scenarios`, strictly tenant isolated.

### M8.9-02: Scenario Optimization (Leveling & CPM)
- **User Problem:** Must calculate the impact of recovery changes.
- **User Workflow:** Inside a scenario, planner alters activity durations or logic, then clicks "Run Optimization."
- **Inputs:** Modified activities within Scenario.
- **Outputs:** New CPM dates and Resource histograms for the scenario.
- **Business Rules:** MUST route strictly through `scheduleEngine.ts` and `ResourceConstraintService`. No duplicate logic.
- **Dependencies:** `scheduleEngine.ts`, `ResourceConstraintService`.

### M8.9-03: Scenario Comparison & SHI Scoring
- **User Problem:** How do I know if this scenario is better than the current plan?
- **User Workflow:** Planner views a side-by-side SHI score (M8.8 Health) of the Scenario vs Current Baseline.
- **Inputs:** Scenario data, Baseline data.
- **Outputs:** Delta SHI, Float Erosion comparison.
- **Business Rules:** Reuses M8.8 Health calculations exactly.

### M8.9-04: Scenario Promotion (Change Control)
- **User Problem:** The winning scenario must become the new plan of record.
- **User Workflow:** Planner clicks "Promote Scenario". A Change Request is generated via M8.8 Change Control.
- **Outputs:** Approved Change Request, new `is_current` Baseline.
- **Business Rules:** Reuses M8.8 Change Control state machine.

## 6. Proposed Data Model
*No schema changes authorized yet.*
- **`ScheduleScenario` (Proposed):** Tracks `event_id`, `name`, `status`. Necessary to group branched data.
- **`ScenarioActivity` (Proposed):** A differential clone of `Activity` containing only the overridden fields (duration, dates, logic) for the scenario. Necessary to prevent duplicating the entire multi-thousand row Workpack graph for every scenario.

## 7. UI/UX
- **Planner Workspace Extension:** Add a new view toggle in the toolbar (Alt+7 for "Scenarios").
- **Layout:** Reuses the CSS grid. Left pane shows Scenario List. Center pane shows a split-screen Gantt/Grid comparing Scenario vs Baseline. Right inspector shows Scenario Impact (Delta SHI).
- **Consistency:** Uses identical components to M8.8 Schedule Control Dashboard.

## 8. API Contract (Proposed)
- `POST /api/events/[eventId]/scenarios` (Create branch, Mutation)
- `GET /api/events/[eventId]/scenarios` (List, Read-only)
- `PUT /api/events/[eventId]/scenarios/[scenarioId]/activities` (Update sandbox data, Mutation)
- `POST /api/events/[eventId]/scenarios/[scenarioId]/optimize` (Run CPM/Leveling, Mutation)
- `POST /api/events/[eventId]/scenarios/[scenarioId]/promote` (Submit CR, Mutation)
*All wrapped in `withTenantGuard` and `guardApi('nav.schedule')`.*

## 9. Calculation Architecture
**CRITICAL:** 
- **CPM & Logic:** Every scenario calculation MUST pass its virtual graph through `src/lib/scheduleEngine.ts`. No new graph algorithms will be written.
- **Resource Constraints:** Every scenario leveling attempt MUST pass through `src/core/resources/ResourceConstraintService.ts`. No parallel leveling logic will be written.
- **Health (SHI):** Must reuse `ScheduleHealthService.calculateSHI()`.

## 10. Security Model
- **Tenant Isolation:** Scenario tables will have `organization_id` and compound indexes.
- **Event Ownership:** Scenarios belong to exactly one `event_id`.
- **RBAC:** Requires `nav.schedule` and `edit.schedule`. 
- **IDOR Protection:** All scenario IDs must be validated against the session tenant before mutation.

## 11. Testing Strategy
- **Schema Tests:** Validate cascading deletes for scenarios.
- **Unit Calculations:** Ensure `scheduleEngine.ts` accepts virtual scenario inputs correctly.
- **Security:** Adversarial cross-tenant scenario access tests.
- **Regression:** Ensure live Event Activities are NEVER modified by a scenario calculation.
- **Browser Acceptance:** Scenario creation, comparison, and promotion flow.

## 12. Acceptance Criteria
- Planner can create 3 distinct scenarios for an event in < 2 seconds each.
- Scenario CPM calculations yield mathematically identical results to live CPM given the same inputs.
- Promoting a scenario correctly generates an M8.8 Change Request.
- Live `Activity` records are mathematically proven untouched until the Change Request is applied.

## 14. Risks
- **Data Contamination:** High risk of scenario data accidentally bleeding into live `Activity` queries if Prisma queries are not strictly scoped.
- **Calculation Duplication:** Risk of bypassing `scheduleEngine.ts` to make virtual updates easier. This is explicitly forbidden.
- **Performance:** Cloning thousands of activities for a scenario could be slow. Mitigation: Use differential/delta storage (`ScenarioActivity` only stores overrides).
