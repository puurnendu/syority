# M8.10 Final Scope Decision & Phase 0 Gate

## 1. Architectural Recommendations
Based on the forensics performed in Phase 0, the following architectural decisions are recommended for M8.10 implementation:

### 1. EVM Methodology
- **Recommended:** Hybrid model. Physical % Complete driven natively by `Activity.progress_percent` is the default mechanism. Future expansion will support Rules of Credit.

### 2. Time-Phased Architecture
- **Recommended:** Option C (Hybrid). The raw database will NOT query 50,000 activities on-the-fly to draw an S-Curve. A new `EventCostSnapshot` (or equivalent OLAP table) will store the pre-calculated `[date, PV, EV, AC]` arrays.

### 3. Baseline Architecture
- **Recommended:** Leverage existing M8.9 `ScheduleBaseline` and `BaselineActivity`. Do not create a separate "Cost Baseline". If the schedule changes, the cost baseline changes with it.

### 4. Scenario Integration
- **Recommended:** `EvmCalculationService` must support a "Scenario Context". It will merge live `Activity` state with `ScenarioActivityOverride` data in-memory to project an EAC curve, without touching the database.

## 5. Implementation Phases
1. **Phase 1: Foundation.** Schema additions (`CostSnapshot`, `Resource.standard_rate`) and mandatory financial seed data generation.
2. **Phase 2: Engine Core.** PV/EV/AC math logic and event-listeners/cron jobs to build the snapshot arrays.
3. **Phase 3: Presentation.** Cost Control Dashboard and API delivery.

## 6. System Implications
- **Security Implications:** Currently, anyone with `nav.schedule` can see the schedule. Financial data is sensitive. We may need to introduce `view:cost` permissions to redact dollar values while keeping hours visible for standard users.
- **Migration Complexity:** Moderate. The schema additions are non-breaking, but generating historical test data for existing events (so S-curves aren't empty) requires a complex seed script.
- **Performance Implications:** High. S-Curves cannot be generated using real-time SQL SUM/GROUP BY over daily boundaries for large events. Batch caching is mandatory.
- **Future Integrations:** The engine must be designed so that M8.11 Scope Change can easily append new BAC onto an actively running EVM baseline without breaking the historical PV curve.

## 7. Unresolved Product Decisions
Before authorizing Phase 1, the product team must decide:
1. **Resource Rates:** Should we implement full Resource Rate tables immediately, or simply allow users to manually type a flat `budgeted_cost` integer into the Activity to unblock EVM?
2. **Overhead Costs:** Does EVM track indirect/overhead costs (scaffolding, facilities) or strictly direct wrench-time activities?
3. **Currency Handling:** Does the platform need multi-currency support for global turnarounds, or is a single tenant-wide currency sufficient?
