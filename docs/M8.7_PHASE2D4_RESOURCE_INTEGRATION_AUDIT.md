# M8.7 Phase 2D.4 — Resource Planning Integration Audit

## 1. Executive Summary

This document serves as the formal end-to-end integration and production hardening audit for the Resource Planning module delivered under M8.7 Phase 2D.1 – 2D.3.

The architecture relies strictly on the STO Execution invariant models without introducing duplicate or overlapping tables for Task, Demand, Equipment, or Shifts.

## 2. End-to-End Tracing & Authoritative Validation

### 2.1 The Demand Trace
**Invariant:** `ActivityResource` remains the single source of truth for resource demand.

*Trace Execution:*
1. **Event** -> `Activity` (Filtered by `event_id`, `deleted_at: null`, `status != cancelled`, and `duration_hours > 0`)
2. **Activity** -> `ActivityResource` 
3. **Calculation:**
   - For `labor`: Demand is calculated as `headcount * crew_size`.
   - For `machine` / `material`: Demand is calculated as `quantity`.
   - Distribution: The daily demand is extrapolated uniformly across the `duration_hours` bucketed into a standard 10-hour working day increment. (e.g., 30 hours = 3 days).
   - Demand shift assignment defaults to `null` (Daily Aggregate), as `Activity` instances are not yet natively bound to a Shift pattern.

### 2.2 The Capacity Trace
**Invariant:** `ResourceCapacity` represents time-phased supply, while `Resource` handles named physical assets.

*Trace Execution:*
1. **Event** -> `ShiftDefinition` (Provides boundary context)
2. **Event** -> `ResourceCapacity` (Time-phased, constrained to `organization_id`)
3. **Aggregation:**
   - Both Shift-assigned capacity and null-shift capacity are properly aggregated on the Daily key (Day + Night = Total Daily Supply).
   - Capacity Upsert is strictly idempotent using composite lookup (`event_id` + `resource_type_id` + `target_date` + `shift_id` + `contractor_id`).

### 2.3 The Dashboard Trace
**Invariant:** The `ResourcePlanningDashboard` is isolated from legacy `ResourceHistogram`.

*Trace Execution:*
1. Backend calculation `getDemandVsCapacity()` groups into `date`, `shift`, `resource_type_id`, and `contractor_id`.
2. Frontend API route `/api/events/[eventId]/resource-loading` receives this output securely.
3. The UI segregates data visually:
   - **Histogram:** Renders Variance & Capacity on an area chart.
   - **Loading Matrix:** Displays demand numbers.
   - **Availability Matrix:** Pivots capacity limits.

## 3. Defect Remediation & Hardening

During the Phase 2D.4 audit, the following vulnerabilities/defects were detected and fixed:

### Defect 1: Cancelled Activity Demand Leak
- **Issue:** The `getDemandVsCapacity` engine fetched activities lacking a `deleted_at` timestamp, but failed to exclude those with `status: 'cancelled'`. This caused artificial demand inflation for aborted scopes of work.
- **Remediation:** Added `status: { not: 'cancelled' }` to the Prisma query filter in `ResourcePlanningService.ts`. Validated via `RES-05` integration test.

### Defect 2: Shift Deletion Integrity
- **Issue:** It was possible to delete a `ShiftDefinition` that was actively referenced by a `ResourceCapacity` record, leading to orphaned capacities.
- **Remediation:** Added a relationship check in `deleteShift` to block deletion if child capacities exist. Validated via `RES-15`.

## 4. Security & Tenant Boundaries
- **Cross-Tenant Protection (RES-11):** Enforced at every service level point. Accessing an `eventId` using another `organizationId` correctly yields an "access denied" error.
- **Foreign Key Poisoning (RES-14):** An attacker cannot assign a `ShiftDefinition` from `Event A` into a `ResourceCapacity` belonging to `Event B`.

## 5. Integration Test Results
The automated validation script `scratch/m87_phase2d4_integration_tests.ts` successfully executed tests RES-01 through RES-16.
- All real data and relationship linkages proved sound.
- Prisma successfully generated schema and runtime artifacts.
- The Next.js production build (`npm run build`) succeeded without regressions to legacy UI components.

## Conclusion
The Resource Planning architecture respects the invariants of the broader STO Execution platform. Phase 2D is production-ready.
