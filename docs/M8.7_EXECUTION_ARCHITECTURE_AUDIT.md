# M8.7 EXECUTION ARCHITECTURE AUDIT

This audit was conducted as Step 0 of M8.7 to ensure no redundant data structures are created and that M8.6 architectural invariants remain protected.

## A. Shutdown/Event Architecture

### Finding: `Event` is Authoritative
- The Prisma schema uses the `Event` model (with `event_type = "turnaround"`) as the authoritative entity for a shutdown.
- All core APIs (`/api/events/*`, `/api/systems/[id]/events`, etc.) query `prisma.event`.
- The `ShutdownScope` model exists, but it is **not** a duplicate of `Event`. Instead, it is a 1:1 extension (`event_id` is unique) that handles scope-specific metadata (e.g., `freeze_date`, `objectives`, `budget_cost`).

### Recommendation
**KEEP `Event` as the authoritative scheduling and lifecycle entity.** Keep `ShutdownScope` as the authoritative container for scope items. The `/shutdowns` and `/events` UIs should be consolidated to avoid confusion, pointing users to the unified `Event` + `ShutdownScope` architecture.

## B. Workpack Lifecycle

### Current Flow (via `WorkflowService.ts`)
```
DRAFT → UNDER_REVIEW → APPROVED → ISSUED → IN_EXECUTION → COMPLETED → CLOSED
```

### Observations:
- **Approval:** `WorkflowService.approve()` correctly locks the workpack (`is_locked = true`) and creates an auto-snapshot (`WorkpackVersionService.autoSnapshot`).
- **Issuing:** `WorkflowService.issue()` simply changes the status from `approved` to `issued`. It currently **does not** explicitly make activities visible to the execution layer or freeze an execution baseline.
- **Immutability:** Engineering data is protected after Approval via `is_locked`, but execution data (progress, joints) remains mutable.

## C. Activity Lifecycle

### Current Flow
```
not_started → in_progress → completed → (on_hold / cancelled)
```

### Observations:
- Activities do not need an `issued` state. The Workpack being `issued` serves as the gateway. 
- Activities sit at `not_started` until actual progress is logged during `in_execution`. 
- **Recommendation:** Do not create duplicate state machines. Keep the current `ActivityStatus` enum as it perfectly supports the Execution Contract.

## E. Proposed Phase 1 Change List

### The Execution Contract
- **Engineering Baseline (Immutable):** Technical Data, Snapshots, Revisions, Scope.
- **Execution Data (Mutable):** `ProgressLog`, Timestamps, Joints (`JointIntegrityItem`), Blinds (`Blind`), Safety, Punchlist, Permits.
- **Handoff:** A Workpack becomes executable only when it transitions to `ISSUED`.

### Implementation Steps (Phase 1)
1. **Unify UI:** Consolidate `/shutdowns` and `/events` in the UI navigation.
2. **Shutdown Scope Management:** Enhance the `/api/shutdown-scope` and UI to allow adding/removing `Workpack`s to an Event's scope (must be at least `approved`).
3. **Enhance `WorkflowService.issue()`:**
   - Add validation: Check if Workpack belongs to a valid Event/Scope.
   - Assert snapshot exists.
   - Emit an `IssueToField` audit log.
4. **Execution Readiness UI:** Create a dashboard at `/events/[eventId]/execution-readiness` detailing Workpacks, their statuses, snapshot existence, and missing constraints.
5. **Execution View Discovery:** Update `/api/execution/board` to only return Activities for Workpacks that are `ISSUED` or `IN_EXECUTION`.
