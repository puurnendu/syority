# M8.7 Phase 2D.2 — Resource Planning API & Service Layer Audit

## Objective
Identify existing resource, shift, calendar, and planning capabilities within the codebase before creating the Resource Planning backend. The goal is to maximize code reuse, prevent duplication, and preserve architectural invariants while rolling out Phase 2D.2 functionality.

## 1. Existing Resource & Capacity Capabilities
- **`ResourceService`** (`src/core/master-data/services/ResourceService.ts`):
  - Exists and provides standard CRUD operations for the `Resource` model (representing named individuals or specific equipment pieces).
  - Handles `organization_id` isolation.
  - **Does NOT** manage `ResourceCapacity` or Event-scoped capacity boundaries.
- **Activity Resource / Demand**:
  - `ActivityResource` is actively used on `Activity` records but there is currently no dedicated `ResourceDemandService`. Demand logic is embedded within existing histogram APIs.

## 2. Existing Shift Capabilities
- **`execution/shifts` API** (`app/api/execution/shifts/route.ts`):
  - This API creates/updates `SafetyLog` records. It logs field execution shifts using simple strings (`shift: 'day'`), rather than the new `ShiftDefinition` model.
  - **Does NOT** manage structural shift patterns or limits required for resource planning.

## 3. Existing Calendar Capabilities
- **Calendars API** (`app/api/settings/calendars/route.ts`):
  - Handles standard site/system working calendars. These are global or site-scoped and act as the working-calendar authority.

## 4. Existing Histogram / Resource Loading Logic
There are two existing histogram APIs:
1. **Org-wide Schedule Histogram** (`app/api/schedule/resource-histogram/route.ts`):
   - Computes daily demand across the org (or filtered by Event).
   - Groups demand by **`Discipline`** (not `ResourceType`).
   - Assumes a hardcoded 10-hour workday.
   - Calculates headcount strictly by looking at `ActivityResource` lengths or falling back to `manpower_count`.
   - **Does NOT** compare demand against `ResourceCapacity`.
2. **Project Histogram** (`app/api/projects/[id]/resource-histogram/route.ts`):
   - Computes weekly demand distribution using `duration_hours`.
   - Again, groups by **`Discipline`** and does not consult `ResourceCapacity` or `ResourceType`.

## 5. Duplicate Functionality Discovered
- The two existing histogram APIs share similar but slightly distinct aggregation logic (daily headcount vs weekly hours). However, both are strictly demand-focused and use `Discipline`.
- **Verdict**: We will NOT duplicate the `ActivityResource` model, nor will we overwrite the existing `Discipline`-based histograms which serve other legacy reporting purposes. Instead, we will build a new deterministic `ResourceType`-based Capacity vs Demand engine.

## 6. Exact APIs and Services to be Reused vs Added

### To be Reused
- **Prisma Schema**: `Event`, `Activity`, `ActivityResource`, `ResourceType`, `Contractor`.
- **Guards**: `withTenantGuard` and `guardApi` for session isolation and permission checks.

### To be Added
1. **`ResourcePlanningService`** (`src/core/resources/ResourcePlanningService.ts`):
   - A dedicated service layer to handle the new `ShiftDefinition`, `ResourceCapacity`, and strict demand aggregation calculations.
2. **Shift API** (`app/api/events/[eventId]/shifts/...`):
   - For managing Event-scoped `ShiftDefinition`s.
3. **Capacity API** (`app/api/events/[eventId]/resource-capacity/...`):
   - For managing Event-scoped `ResourceCapacity` limits mapped to `ResourceType`s.
4. **Demand vs Capacity Engine / API** (`app/api/events/[eventId]/resource-loading`):
   - Calculates the exact overlap between `ActivityResource` demand and `ResourceCapacity` supply on a per-day, per-shift, per-`ResourceType` basis.

## 7. Tenant Isolation & Event Boundary Strategy
- **Tenant Isolation**: Every backend query and mutation must aggressively filter by the session's `organization_id` using existing `withTenantGuard`. Cross-tenant mutations will be rejected outright.
- **Event Boundary**: `ResourceCapacity` and `ShiftDefinition` are structurally tied to an `Event`. Any payload altering these models must verify that the specified `Event` belongs to the authenticated `organization_id`. `ResourceType` and `Contractor` foreign keys must also be validated against the active tenant.
