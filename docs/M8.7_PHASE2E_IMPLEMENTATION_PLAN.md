# M8.7 Phase 2E — Resource-Loaded Scheduling & Leveling Implementation Plan

## Goal
Implement Resource-Loaded Scheduling and Leveling on top of the M8.7 Phase 2D Resource Planning layer and the existing `scheduleEngine.ts`. The implementation will provide constraints detection and leveling recommendations without replacing the existing scheduling CPM engine.

## User Review Required
> [!IMPORTANT]
> The leveling heuristic will only auto-shift non-critical activities (Total Float > 0). Critical activities that are over-allocated will be flagged as constraints for manual planner intervention. Do you agree with this safety boundary?
> 
> The legacy histogram (`app/api/schedule/resource-histogram/route.ts`) will be retained as-is for backward compatibility and won't be modified in this phase.

## Open Questions
> [!WARNING]
> Should the Leveling Recommendation API actually mutate the database dates immediately, or should it return a "simulation" payload of date changes that the frontend can preview and then submit via a separate save endpoint? (This plan assumes a simulation payload).

## Proposed Changes

---

### Constraint Engine

#### [NEW] `src/core/resources/ResourceConstraintService.ts`
- Implement `detectConstraints(eventId)`
- Calls `ResourcePlanningService.getDemandVsCapacity(eventId)`
- Iterates over dates and resources to identify deficits (Demand > Capacity)
- Maps deficits back to the Activities scheduled on those dates that consume the constrained resource.
- Categorizes constraints (Hard: Capacity=0, Soft: Demand>Capacity, Info: Demand approaching Capacity).

---

### Leveling Engine

#### [NEW] `src/core/resources/ResourceLevelingService.ts`
- Implement `generateLevelingRecommendations(eventId)`
- Calls `calculateSchedule` (`scheduleEngine.ts`) to get current Float and Critical Path data.
- Calls `ResourceConstraintService.detectConstraints` to find over-allocations.
- Applies heuristic:
  1. For each over-allocated day, find contributing non-critical activities.
  2. Sort by highest `total_float_days`.
  3. Propose shifting `planned_start` forward for the activity with the most float.
  4. Recalculate simulation state.
  5. Repeat until float is exhausted or deficit is cleared.
- Output is a simulation payload: `[ { activity_id, proposed_start, proposed_end, float_consumed } ]`.

---

### API Layer

#### [NEW] `app/api/events/[eventId]/schedule/constraints/route.ts`
- `GET`: Returns the active constraints detected by `ResourceConstraintService`.

#### [NEW] `app/api/events/[eventId]/schedule/level-resources/route.ts`
- `GET` or `POST` (simulation): Runs `generateLevelingRecommendations` and returns the proposed date shifts for planner review.

---

### Frontend

#### [NEW] `src/components/Schedule/LevelingPreviewModal.tsx`
- A UI component launched from the Planner Workspace to trigger a leveling simulation.
- Displays a table of "Proposed Date Shifts" and "Remaining Constraints".
- Provides an "Accept & Apply" button which will iterate and update the `planned_start` dates of affected activities.

## Verification Plan

### Automated Tests
- Create `scratch/m87_phase2e_leveling_tests.ts` to construct a synthetic CPM network with limited resource capacity.
- Verify that `generateLevelingRecommendations` correctly delays high-float tasks and skips critical-path tasks.
- Verify tenant isolation on the new APIs.

### Manual Verification
- Load an Event in the UI with intentional over-allocation.
- Open the Leveling Preview Modal, verify recommendations, and click "Accept & Apply".
- Verify that the Gantt chart and Resource Histogram reflect the delayed dates and resolved constraints.
