# M8.7 Phase 2H.8 - Leveling Score Audit

## Overview
This document serves as the audit of the scoring mechanics used within the M8.7 Resource-Loaded Scheduling system to prioritize leveling candidates during a What-If simulation. 

It is crucial to clarify that the legacy concept of a raw "Leveling Score" from the old CPM implementation is distinct from the new **Conflict Score**.

## Semantic Distinction

### 1. Legacy Leveling Score (Deprecated in favor of Conflict Score for simulations)
- Previously tied to simple heuristic sorting.
- Lacked multi-resource dimension tracking.

### 2. Conflict Score (Current M8.7 Standard)
- Implemented in `ResourceConflictService.ts`.
- **Purpose**: Generates a deterministic ranking of leveling candidates dynamically for every iteration of the What-If simulation.
- **Directionality**: Unambiguously sorted **DESCENDING**. A *higher* score means the activity is a *better* candidate to be delayed.

## Scoring Formula Breakdown

```typescript
const score = 
  (constrained_resource_count * 100) + 
  total_deficit + 
  (downstream_constraint_count * 10) + 
  float_score;
```

1. **`constrained_resource_count * 100`**: Prioritizes activities that are consuming multiple constrained resources. Delaying a task that bottlenecks 3 resources provides more value than a task bottlenecking 1.
2. **`total_deficit`**: Adds the raw unit deficit size. A task contributing to a 50-man deficit will outscore one contributing to a 5-man deficit.
3. **`downstream_constraint_count * 10`**: Prioritizes tasks that span multiple days of constraints.
4. **`float_score`**: Represents `total_float_days`. Because the list is sorted descending, higher float directly adds to the score, making high-float tasks the preferred candidates for delay.

### Near-Critical Protection (The Float Penalty)
If an activity has `total_float_days <= 2`, it is deemed "near-critical".
```typescript
if (float_available <= 2) {
   float_score -= 1000;
}
```
This massively penalizes the score, dropping it to the bottom of the candidate pool and protecting it from being delayed unless absolutely no other options exist. 

### Critical & Negative Float Protection
```typescript
if (act.is_critical || act.total_float_days <= 0) {
  continue; // Excluded completely
}
```
Tasks with zero or negative float are completely filtered out of the scoring pipeline. They cannot be scored, cannot be ranked, and will never be recommended for delay.

## Determinism
To prevent unstable sorts where two activities have identical scores, the sort explicitly falls back to `activity_id`:
```typescript
candidates.sort((a, b) => {
  if (a.score !== b.score) return b.score - a.score;
  return a.activity_id.localeCompare(b.activity_id);
});
```

## Conclusion
The scoring mechanism unambiguously favors delaying non-critical, high-float activities that contribute the most to multi-resource bottlenecks, while safely isolating and penalizing near-critical activities. The logic operates exactly as intended for Phase 2G/2H.
