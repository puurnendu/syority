# M8.13 Discovery Report
## Enterprise Turnaround Progress Intelligence, Common Data Model & Dashboard Architecture

### Executive Summary

M8.13 is intended to become the **Enterprise Turnaround Progress & Schedule Risk Intelligence** layer for the STO platform. This discovery report documents the findings from a forensic audit of the existing data sources, calculation logic, dashboard architecture, and cross-module integration paths that will underpin M8.13.

### Current Architecture Verdict: 🔴 RED — FUNDAMENTAL INCONSISTENCY

The platform currently has **no single authoritative source** for TA execution progress. Multiple systems calculate progress independently using different methods, resulting in **three distinct implementations of SPI**, **four different progress aggregation methods**, and **zero centralized progress calculation service**.

---

### Key Findings

#### 1. Progress Calculation Fragmentation (CRITICAL)

| Location | Method | Weighting | What It Calculates |
|----------|--------|-----------|-------------------|
| `FieldExecutionService.calculateWeightedProgress()` | Duration-weighted | `progress × duration / Σduration` | Overall TA progress |
| `portfolio-stats API` (L170-174) | Simple average | `Σ(workpack_avg) / workpack_count` | Dashboard avg progress |
| `portfolio-stats API` (L230-263) | Duration-weighted (hours as PV/EV) | `duration × progress / 100` as EV | SPI/CPI |
| `ScheduleHealthService.scoreProgressEarned()` | Duration-weighted | `progress × duration` as numerator | Schedule health SPI |
| `EvmCalculationService.calculateEv()` | Cost-weighted | `BAC × progress / 100` | EVM earned value |
| `WhatsApp approve route` (L56-58) | Simple average | `Σ(progress) / count` | Workpack.overall_progress |
| `WorkpackSummaryBar` (L17-22) | Simple average of stored values | `Σ(overall_progress) / count` | Frontend KPI |
| `ShutdownProviders` (L149) | Simple average | `Σ(progress) / activity_count` | Report unit progress |
| `ContractorProgressProvider` (L177) | Simple average of stored values | `Σ(overall_progress) / workpack_count` | Report contractor progress |

**Impact**: The same turnaround can show different progress percentages depending on which dashboard/report the user is viewing.

#### 2. `Workpack.overall_progress` — Stale Field (HIGH RISK)

- The `overall_progress` field (Workpack model L102) is only reliably written by:
  - `FieldExecutionService.syncWorkpackProgress()` — duration-weighted
  - WhatsApp `approve` route — simple average
- It is **not** automatically synchronized when activity progress changes through normal UI operations
- Multiple report providers (`ShutdownProviders`, `ContractorProgressProvider`, `DisciplineProgressProvider`) read this field
- **Risk**: Stale data displayed in reports after progress updates

#### 3. Dual EVM/SPI Implementation (DUPLICATE-INCONSISTENT)

| System | EV Formula | AC Source | PV Formula |
|--------|-----------|-----------|-----------|
| M8.10 `EvmCalculationService` | `BAC × progress%` | `Activity.actual_cost` | `BAC × linear_interpolation` |
| `portfolio-stats` API | `duration × progress%` | `ProgressLog.manhours_actual` | `duration × time_interpolation` |
| `ScheduleHealthService` | `progress × duration` | N/A | `time_interpolation × duration` |

These three implementations produce **different SPI values** for the same event.

#### 4. No Identical Activity Structure

The current data model lacks:
- A normalized activity classification (beyond free-text `description`)
- An `activity_type_id` or `standard_activity_code` on Activity
- A mapping from `equipment_type → standard_activities`

Existing partial infrastructure:
- `ActivityLibrary.activity_code` — optional, rarely populated
- `Workpack.equipment_type` — free text, no FK
- `TemplateFamily.equipment_type` — free text, no FK to `EquipmentType`
- `WorkType` — structured 2-level taxonomy (Category → Name), but not linked to Activity instances
- `Activity.activity_library_id` — FK to `ActivityLibrary`, but inconsistently populated

#### 5. Progress Denominator Not Scope-Change Aware

When M8.11 scope changes add new activities:
- Activities are created with `progress_percent: 0`
- **No recalculation of overall event progress occurs**
- Dashboard numbers temporarily appear correct (new 0% activities lower average)
- But there is no formal mechanism to distinguish between "original scope progress" and "total scope progress"
- EVM BAC is not automatically adjusted (no baseline re-baselining)

### M8.13 Scope Recommendation

Given the RED verdict, M8.13 must:

1. **Establish a single Progress Calculation Service** (authoritative)
2. **Normalize activity classification** for identical-activity analysis
3. **Create a Common KPI Service** consumed by all dashboards
4. **Introduce an Executive Dashboard layer** above specialist dashboards
5. **Retire or redirect duplicated calculations** to the common service

See `M8.13_ARCHITECTURE_RECOMMENDATION.md` for the proposed architecture.
