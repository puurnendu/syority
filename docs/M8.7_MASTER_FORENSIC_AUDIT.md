## P0 Defects (7 total)

### P0-001: `total_float_days` used in 6+ services; Prisma schema has `total_float`
- **Files**: ResourceConstraintService.ts, ResourceKpiService.ts, ResourceRiskService.ts, ResourceScenarioComparisonService.ts, ResourceConflictService.ts, ResourceLevelingService.ts
- **Root cause**: Schedule engine `calculateSchedule()` outputs `total_float_days` in its result interface. Services copied this field name for Prisma `select` statements where the DB column is `total_float`.
- **Evidence**: Activity model in `schema.prisma` has field `total_float Decimal?`
- **Prisma behavior**: `Unknown field 'total_float_days'` → PrismaClientValidationError
- **Classification**: 🟡 STATIC_PASS (defect identified through static analysis)

### P0-002: Activity `name` field used in Prisma `select`; schema has `description`
- **File**: ResourceConstraintService.ts line 82 `select: { name: true }`
- **Evidence**: Activity model has `description String`; no `name` field exists
- **Prisma behavior**: `Unknown field 'name'` → PrismaClientValidationError
- **Classification**: 🟡 STATIC_PASS

### P0-003: Apply service writes `early_end`/`late_end`; schema has `early_finish`/`late_finish`
- **File**: ResourceLevelingApplyService.ts lines 172-174
- **Evidence**: Schedule engine outputs `early_finish`/`late_finish` (verified in scheduleEngine.ts). Service uses `early_end`/`late_end` which are `undefined`. Then `new Date(undefined)` → `Invalid Date` → Prisma rejects.
- **Classification**: 🟡 STATIC_PASS

### P0-004: Apply service writes `total_float_days`; schema has `total_float`
- **File**: ResourceLevelingApplyService.ts line 175
- **Classification**: 🟡 STATIC_PASS

### P0-005: 5 Phase 2I API routes import from `@/lib/auth/withTenantGuard`
- **Actual path**: `@/lib/withTenantGuard` (no `auth/` subdirectory)
- **Files**: resource-kpis, resource-forecast, resource-risks, resource-heatmap, resource-scenarios/compare
- **Behavior**: `MODULE_NOT_FOUND` at route load time
- **Classification**: 🟡 STATIC_PASS

### P0-006: 5 Phase 2I API routes use fabricated `tenantContext` parameter
- **Actual withTenantGuard signature**: `(req: NextRequest, ctx, session)` with `session.user.organization_id`
- **Used signature**: `{ params, tenantContext }` with `tenantContext.organizationId`
- **Behavior**: `Cannot read properties of undefined (reading 'organizationId')`
- **Classification**: 🟡 STATIC_PASS

### P0-007: Apply CPM recalculation maps relationship fields incorrectly
- **File**: ResourceLevelingApplyService.ts lines 152-157
- **Code**: `type: rel.type, lag_hours: rel.lag_hours`
- **ActivityRelationship schema**: `relationship_type String`, `lag_days Decimal?`
- **ScheduleRelationshipInput**: expects `relationship_type`, `lag_days`
- **Impact**: All relationships treated as FS+0 during post-Apply recalculation → schedule dates WRONG
- **Contrast**: LevelingService (lines 128-133) correctly maps both fields
- **Classification**: 🟡 STATIC_PASS
