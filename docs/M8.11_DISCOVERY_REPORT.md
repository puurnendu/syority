## 1. Current Architecture

The STO platform has **two parallel change control systems** that currently do NOT interact:

### System A: Shutdown Scope Change Control (Pre-Execution)

| Component | Description |
|-----------|-------------|
| **Domain** | Asset-level scope definition before schedule creation |
| **Container** | `ShutdownScope` → `ScopeItem` → `ScopeChangeRequest` |
| **Service** | `ScopeChangeService.ts` (237 lines) |
| **Related** | `ScopeItemService.ts`, `ScopeDeferralService.ts`, `ShutdownScopeService.ts` |
| **APIs** | 30+ endpoints under `/api/shutdown-scope/` |
| **UI** | Full pages under `/shutdown-scope/` with builder, reports, change tracking |
| **Lifecycle** | `pending` → `approved` / `rejected` (auto-applies on approval) |
| **Guard** | `asset.view` / `asset.manage` permissions |

### System B: Schedule Change Control (Post-Baseline, M8.8)

| Component | Description |
|-----------|-------------|
| **Domain** | Schedule-level changes (date shifts, duration, resource, leveling) |
| **Container** | `schedule_change_requests` table (raw SQL, NOT in Prisma schema model) |
| **Service** | `ScheduleChangeControlService.ts` (338 lines) |
| **APIs** | 2 endpoints under `/api/events/[eventId]/schedule/change-requests/` |
| **UI** | Embedded in ScheduleControlDashboard (M8.8) |
| **Lifecycle** | `proposed` → `review` → `approved` / `rejected` → `applied` / `superseded` |
| **Guard** | `nav.schedule` permission |

> **CRITICAL FINDING:** These two systems are **completely independent**. There is NO mechanism for a scope change (System A) to automatically generate a schedule change request (System B), or vice versa. M8.11 must bridge this gap.

## 8. Recommended Architecture

### Strategy: Bridging Layer + New Discovery Entity

Create a **new domain layer** that:

1. Introduces `ScopeDiscovery` entity for newly found work
2. Introduces `ScheduleScopeChange` entity bridging scope with schedule impact
3. Extends existing `schedule_change_requests` with new change_type values
4. Reuses M8.8 `ScheduleChangeControlService` lifecycle for approval/application
5. Provides impact analysis services that READ from (but do NOT mutate) existing engines

```
DISCOVERY → SCOPE CHANGE PROPOSAL → IMPACT ANALYSIS → CHANGE REQUEST → APPROVAL → APPLICATION
```

### New Entities (Proposed)

| Entity | Purpose |
|--------|---------|
| `ScopeDiscovery` | Discovery record for newly found work |
| `ScheduleScopeChange` | Scope change proposal with items and impact |
| `ScheduleScopeChangeItem` | Individual line items within a scope change |
