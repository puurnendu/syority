## Locked Decisions

The following decisions are final and do not require further approval. They are derived from the Phase 0 forensic audit and reconciled across all seven discovery documents.

### LD-1: Scope
M8.10 = Enterprise EVM & Cost Intelligence. Nothing else.

### LD-2: EVM Methodology
Hybrid Physical % Complete. `EV = BAC × min(progress_percent / 100, 1.0)`.

### LD-3: Formula Suite
PV, EV, AC, CV, SV, CPI, SPI, EAC, ETC, VAC, TCPI — all locked with explicit zero-division rules. See [M8.10_ARCHITECTURE_LOCK.md §3](file:///c:/DEV/STO/docs/M8.10_ARCHITECTURE_LOCK.md).

### LD-4: Earning Rules
Normal work = Physical %. Milestones (duration=0) = 0/100. LOE = Duration % (with Phase 1 fallback to Physical %). See [M8.10_EV_EARNING_RULES.md](file:///c:/DEV/STO/docs/M8.10_EV_EARNING_RULES.md).

### LD-5: Baseline Anchor
M8.8 `ScheduleBaseline` (table: `ScheduleBaseline`, `is_current = true`) is the authoritative EVM baseline. `BaselineActivity.budgeted_cost` is the per-activity BAC. No separate cost baseline table.

### LD-6: Scenario EVM
Read-only, projected calculation. Zero mutation of live data. Merges `ScenarioActivityOverride` with live `Activity` in-memory. No `cost_override` column on `ScenarioActivityOverride` in Phase 1.

### LD-7: Cost Data Source
`Activity.budgeted_cost` (BAC), `Activity.actual_cost` (cumulative AC), `ProgressLog.actual_cost` (incremental AC), `Activity.progress_percent` (EV driver). All fields already exist in the live database.

### LD-8: Seed Data
A dedicated `prisma/seed-evm-demo.ts` is mandatory. The current database has 37 activities with zero cost data, zero progress, and zero actual dates. EVM cannot be tested without realistic financial seed data.

### LD-9: Time-Phased Architecture
Hybrid (Option C). New `EvmSnapshot` table with JSONB `curve_data` and `summary` columns. Snapshots generated by cron, on-demand API call, or baseline activation trigger.

### LD-10: Tenant Isolation
All EVM queries enforce `organization_id` and `event_id`. All API routes use `withTenantGuard` + `guardApi('nav.schedule')`. `EvmSnapshot` includes `organization_id`.

### LD-11: Protected Systems
12 files/services explicitly frozen. EVM is implemented as purely additive new files. See [M8.10_ARCHITECTURE_LOCK.md §10](file:///c:/DEV/STO/docs/M8.10_ARCHITECTURE_LOCK.md).

## Unresolved Decisions Requiring Your Approval

These are genuine product-level choices that I cannot resolve from code forensics alone:

### UD-1: Resource Rate Tables — Defer or Implement?
**Context:** The `Resource` table has no `standard_rate` column. EVM currently relies on manually entered `Activity.budgeted_cost`. Adding a `standard_rate` to `Resource` would allow automatic BAC calculation from `planned_hours × rate`, but adds schema complexity.
**Options:**
- **A) Defer (Recommended).** Users manually enter `budgeted_cost` per Activity. Simpler, faster to ship.
- **B) Implement.** Add `standard_rate` to `Resource` and auto-calculate BAC from resource assignments. More powerful but requires UI for rate management.

### UD-2: EVM Permission Granularity
**Context:** Currently anyone with `nav.schedule` permission sees the schedule. Cost data is commercially sensitive. Some organizations restrict cost visibility to PMs and Cost Controllers.
**Options:**
- **A) Reuse `nav.schedule` (Recommended for Phase 1).** All schedule users see cost. Simplest.
- **B) New `nav.cost` permission.** Requires RBAC matrix update, new seed entries, and UI changes in NavBar.

### UD-3: AC Source of Truth
**Context:** Both `Activity.actual_cost` (cumulative) and `ProgressLog.actual_cost` (incremental per shift) exist. They could diverge if not carefully synchronized.
**Options:**
- **A) `Activity.actual_cost` is authoritative (Recommended).** ProgressLog entries are informational/audit. The Activity field is what EVM reads.
- **B) `SUM(ProgressLog.actual_cost)` is authoritative.** Requires aggregation query on every EVM calculation. More granular but slower and relies on complete shift logging.
