# M8.7 Phase 2D — Resource Planning Architecture Audit

## 1. Executive Summary
This audit evaluates the existing Prisma schema and architectural boundaries of the STO platform to support Resource Planning (Manpower, Equipment, Calendars, Availability) for Phase 2D. The core objective is to seamlessly integrate resource modeling into the existing planning and execution architecture without creating redundant or duplicate systems.

## 2. Current Architecture State

### 2.1 Calendars & Working Time
- **Existing Model**: `ScheduleCalendar` handles standard `work_days` (array), `hours_per_day`, and an `exceptions` JSON field.
- **Current Behavior**: `Event` uses `calendar_id` to drive high-level start/end boundaries and basic duration calculations.
- **Architectural Gap**: The system currently lacks discrete "Shift" definitions (e.g., 12hr Day vs 12hr Night, start/end times). This restricts the ability to perform shift-level resource loading or leveling.

### 2.2 Demand Generation (Manpower, Skills, Equipment)
- **Existing Models**: 
  - `ActivityResource` captures the demand side (`resource_type_id`, `planned_hours`, `headcount`, `crew_size`).
  - The `ResourceType2` enum supports `labor`, `material`, and `machine`, allowing both manpower and equipment demand to be modeled uniformly.
  - `ResourceType` acts as the skill/craft catalog (e.g., "Welder", "200T Crane"), associated with a `Discipline`.
- **Architectural Fit**: The demand generation architecture is robust. External imports (P6/MSP) naturally map to `ActivityResource`. **No structural changes are required for Resource Demand.**

### 2.3 Resource Supply & Availability
- **Existing Models**: `Resource` exists for named individuals or specific named equipment, tied to a `Contractor` and `ResourceType`. `SafetyLog` captures daily total `manpower_planned` and `manpower_actual` at the event level.
- **Architectural Gap**: There is no time-phased capacity model. While we know the demand (from `ActivityResource`), we cannot evaluate it against supply (e.g., Contractor X committed to provide 50 Welders on Day 3).
- **Proposed Solution**: We need a capacity ledger—`ResourceCapacity` or `ResourceAvailability`—to track the mobilized supply limit per `ResourceType` per Date/Shift.

### 2.4 Execution & Progress Loop
- **Existing Models**: `ProgressLog` records `manhours_actual`. `ActivityResource` tracks cumulative `actual_hours`.
- **Architectural Fit**: The feedback loop from execution to planning is completely intact. By recording actuals against `Activity`, the system can automatically compute earned value and resource productivity rates. 

## 3. Interaction Mapping

### 3.1 Equipment & Machinery
Equipment is treated identically to labor via the `ActivityResource` table (`resource_type: machine`). Heavy machinery is instantiated in `Resource` (e.g., "Crane 01"), avoiding the need for a separate equipment scheduling module.

### 3.2 Skills & Competency
Skills are fundamentally handled via `ResourceType` (e.g., "Fitter", "Rigger"). For specific personnel tracking, `Resource.craft_code` stores the qualification. This fulfills the competency requirement without building a heavy, standalone Certification matrix for contractor labor.

## 4. Required Schema Extensions

To achieve complete Resource Planning natively, the following targeted additions are required:

1. **`ShiftDefinition` Model**:
   - Purpose: Define shift patterns (e.g., Day, Night) for an `Event` or `ScheduleCalendar`.
   - Interaction: Enables splitting duration and resource capacity across shifts rather than just days.

2. **`ResourceCapacity` Model**:
   - Purpose: Time-phased supply ledger.
   - Fields: `organization_id`, `event_id`, `resource_type_id`, `contractor_id`, `target_date`, `shift_id`, `headcount_limit`.
   - Interaction: Allows resource leveling engines or visual histograms to compare `ActivityResource` (Demand) against `ResourceCapacity` (Supply).

## 5. Conclusion
The existing architecture elegantly supports 80% of Resource Planning. By leveraging `ActivityResource` and `ResourceType`, we avoid duplicating task engines. The introduction of `ShiftDefinition` and `ResourceCapacity` will close the loop, providing the strict supply-side boundaries needed for comprehensive scheduling and leveling, while rigorously maintaining tenant isolation and event boundaries.
