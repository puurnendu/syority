### Analysis

The platform currently uses **Method A (simple activity count)** in most places and **Method B (duration-weighted)** in the Execution Cockpit and Schedule Health. **Method C (cost-weighted)** is used only for EVM.

For an enterprise turnaround:
- Method A is **incorrect** — a 1-hour activity has the same weight as a 500-hour activity
- Method B is **appropriate** for physical progress tracking
- Method C is **appropriate** for earned value management (cost perspective)
- Method D (quantity-weighted) — **not implemented** — would use quantities from material lines
- Method E (discipline/workpack-weighted) — **not implemented**
- Method F (milestone/earning rules) — **partially implemented** in EVM only
- Method G (hybrid) — **not implemented**

### Recommended Enterprise TA Method

**Duration-weighted progress** (Method B) should be the standard for physical progress:

```
Overall Progress = Σ(activity_progress × activity_duration) / Σ(activity_duration)
```

**With the following hierarchy:**

```
Activity Progress (input)
    ↓
Workpack Progress = duration_weighted(activities in workpack)
    ↓
Discipline Progress = duration_weighted(activities in discipline)
    ↓
Unit Progress = duration_weighted(activities in unit)
    ↓
Contractor Progress = duration_weighted(activities by contractor)
    ↓
Event Progress = duration_weighted(all activities in event)
```

**Cost-weighted progress** (Method C) remains appropriate for EVM and should be calculated by the EVM service, not the progress service.

### Progress Dimensions

M8.13 should support four progress dimensions:

| Dimension | Definition | Source |
|-----------|-----------|--------|
| **Planned Progress** | `Σ(planned_% × duration) / Σ(duration)` where planned_% = time interpolation between planned_start and planned_end | BaselineActivity or Activity planned dates |
| **Actual Progress** | `Σ(activity_progress × duration) / Σ(duration)` | Activity.progress_percent |
| **Forecast Progress** | `Σ(forecast_% × duration) / Σ(duration)` where forecast includes remaining work projections | ScheduleForecastService projections |
| **Balance Work** | `100% - Actual Progress` at each level | Derived |

### Scope Change Impact on Progress

When new activities are added via M8.11 scope changes:

1. **Denominator increases** (total duration increases)
2. **New activities have 0% progress**
3. **Overall progress drops** (correct — more work exists)
4. **Planned progress recalculated** with new baseline (requires re-baselining)

The progress service must:
- Include ALL non-cancelled activities in the denominator
- Distinguish "original scope" vs "total scope" if reporting on scope change impact
- Track baseline changes so variance calculations remain meaningful

### Progress Input Rules

| Rule | Current | Recommended |
