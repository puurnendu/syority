## Three-Level Architecture

**[RECOMMENDATION]** SYORITY should implement a three-level activity code system:

```
Level 1: Native iPlan Level Code (Equipment-Specific)
    Ex.RTub, PIP.Wel, AFC.BLD, PSV.REMV
    ↓ maps to ↓
Level 2: Canonical SYORITY Level Code (Equipment-Independent)
    REPAIR.RETUBING, REPAIR.WELDING, ISO.BLINDING, DISMANTLE.PSV_REMOVAL
    ↓ groups into ↓
Level 3: Activity Family
    REPAIR, ISO, DISMANTLE, INSP, TEST, ASSY, ACCESS, CLEAN, REST, ELECTRICAL
```

### Why Three Levels?

| Level | Purpose | P6 Role | Reporting Role | Template Role |
|---|---|---|---|---|
| Native Code | P6 import/export fidelity | ✅ Direct mapping | ❌ Too equipment-specific | ❌ Equipment-specific |
| Canonical Code | Cross-equipment aggregation | ✅ Derivable | ✅ "All welding progress" | ✅ Reusable templates |
| Activity Family | Management dashboard | ❌ Too generic | ✅ "Isolation phase status" | ✅ Template grouping |
