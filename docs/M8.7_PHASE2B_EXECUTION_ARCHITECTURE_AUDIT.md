# M8.7 Phase 2B — Joint Integrity & Blind Execution Architecture Audit

## 1. Current Architecture
- `Event` is the authoritative shutdown entity.
- `Workpack` is the execution container.
- `Activity` is the executable unit.
- `JointIntegrityItem` and `Blind` models exist and natively link to `Workpack` via `workpack_id` and conditionally to `Activity` (e.g., `activity_id`, `construct_operation_id`, `destruct_operation_id` for Joints, and `insert_activity_id` / `remove_activity_id` for Blinds).
- `ProgressLog` handles tracking activity progression.

## 2. Existing Joint Functionality
- **Model:** `JointIntegrityItem` is fully defined in Prisma.
- **Service:** `JointIntegrityService` implements actions `markAssembled`, `markInspected`, `signOff`, `dismantle`.
- **API:** `app/api/workpacks/[id]/joints/[jointId]/route.ts` implements a generic `PATCH` which allows updating joint status directly without going through specific lifecycle actions.
- **UI:** Exists mostly in Workpack planning context (`GenerateJointsModal.tsx` etc.), not in Field Execution (`ExecutionCockpit.tsx`).

## 3. Existing Blind Functionality
- **Model:** `Blind` is fully defined in Prisma.
- **Service:** `BlindService` implements `recordInsert`, `recordPressureTest`, `recordRemove`, and `confirmIsolation`.
- **API:** `app/api/workpacks/[id]/blinds/route.ts` exposes POST actions for `insert`, `remove`, `pressure-test`, `confirm-isolation`.
- **UI:** Exists in planning / overview context, completely absent from `ExecutionCockpit.tsx`.

## 4. Activity Integration Analysis
- The schema links Joints and Blinds to activities, allowing unambiguous associations.
  - `JointIntegrityItem` -> `activity_id`, `construct_operation_id`, `destruct_operation_id`.
  - `Blind` -> `insert_activity_id`, `remove_activity_id`.
- The current Execution logic in `FieldExecutionService` has no awareness of these sub-items.

## 5. Tenant Isolation Analysis
- Both `JointIntegrityService` and `BlindService` methods accept `organizationId` and enforce it in Prisma queries (`where: { id, organization_id: organizationId }`).
- APIs extract `orgId` from session and pass it to services.
- **Result:** Tenant boundaries are securely enforced. No direct-ID access vulnerabilities found.

## 6. Workpack Execution-State Analysis
- **Finding:** Neither `JointIntegrityService` nor `BlindService` checks the `Workpack.status`.
- **Finding:** The API routes (`/joints/[jointId]` and `/blinds`) do NOT verify if the parent `Workpack` is `issued` or `in_execution`.
- **Risk:** A user could execute a Joint or Blind while the Workpack is in `draft` or `approved`. This breaks the Phase 2 execution gate invariants.

## 7. Existing API Inventory
- `GET /api/workpacks/[id]/joints`
- `PATCH /api/workpacks/[id]/joints/[jointId]`
- `GET /api/workpacks/[id]/blinds`
- `POST /api/workpacks/[id]/blinds` (uses action payload for insert/remove/etc.)
- `PATCH /api/systems/[systemId]/blinds/[blindId]`

## 8. Existing UI Inventory
- `SystemBlindList.tsx`, `GenerateJointsModal.tsx`, and Planning-level dashboards display Joints and Blinds.
- `ExecutionCockpit.tsx` does NOT display Joints or Blinds when selecting an Activity.

## 9. Missing Capabilities
- Execution state gate (`Workpack.status` check) for Joint/Blind mutations.
- Surfacing of linked Joints and Blinds in the `ExecutionCockpit`.
- Sub-item completion UI for Field users directly from the Cockpit.

## 10. Architectural Risks
- Allowing Joints/Blinds to be modified outside the `issued`/`in_execution` boundary compromises execution integrity.
- Duplicating API calls in the frontend instead of exposing sub-items within `ExecutionCockpit` could fracture the user experience.

## 11. Recommended Minimum Implementation
1. **Service Hardening:** Inject `Workpack.status` checks into `JointIntegrityService` and `BlindService` mutation methods (similar to `FieldExecutionService.executeActivityAction`).
2. **API Alignment:** Update `/api/workpacks/[id]/joints/[jointId]` to use explicit service actions (like `/blinds` does) rather than a generic PATCH, to ensure audit logging and lifecycle gates are triggered.
3. **Cockpit Integration:** Modify `ExecutionCockpit.tsx` to conditionally render a "Joints" or "Blinds" accordion/sub-panel when the selected activity has linked items, using existing APIs to fetch and mutate them.
4. **Sub-Item Progress:** Keep Joint/Blind execution decoupled from automatic Activity completion. The user will manually update the parent Activity's progress based on sub-item completion, avoiding complex auto-rollup logic in Phase 2B.

## 12. Exact Files Proposed for Modification
- `src/modules/JointIntegrity/Services/JointIntegrityService.ts` (Add execution gate)
- `src/modules/Blinds/Services/BlindService.ts` (Add execution gate)
- `app/api/workpacks/[id]/joints/[jointId]/route.ts` (Refactor to use service lifecycle methods and execution gate)
- `app/api/workpacks/[id]/blinds/route.ts` (Ensure execution gate is enforced via Service)
- `src/components/execution/ExecutionCockpit.tsx` (Add sub-item display/mutation UI)

## 13. Files That Must NOT Be Duplicated
- `prisma/schema.prisma` (Models `JointIntegrityItem`, `Blind` already exist)
- `ExecutionCockpit.tsx` (Extend, do not build a separate sub-item cockpit)
- `FieldExecutionService.ts` (Leave standard Activity execution intact)

## 14. Phase 2B Implementation Order
1. Harden Services with Workpack execution gates.
2. Refactor Joint API route to use structured service methods.
3. Fetch linked Joints/Blinds in `ExecutionCockpit`.
4. Build minimal UI components inside `ExecutionCockpit` for updating Joint/Blind status.
5. Write Security/Runtime tests.

  - JNT-02: Updating a Joint in an Issued Workpack succeeds.
  - BLD-01: Inserting a Blind in a Draft Workpack is blocked.
  - BLD-02: Inserting a Blind in an Issued Workpack succeeds.
  - Cross-tenant updates for Joints/Blinds are blocked.
