# M8.7 Phase 2D.2 — Resource Planning API & Service Layer Walkthrough

Phase 2D.2 implements the core backend logic for managing resource capacity, shift definitions, and calculating resource loading curves.

## 1. ResourcePlanningService (`src/core/resources/ResourcePlanningService.ts`)

The central service layer provides methods for managing the Resource Planning entities while enforcing strict tenant boundaries (`organization_id` and `event_id`).

### Shift Management
- `listShifts`: Lists all `ShiftDefinition` records for an event.
- `createShift`, `updateShift`, `deleteShift`: Modifies shift definitions. Prevents deletion if `ResourceCapacity` records are still linked to the shift.

### Capacity Management
- `listCapacity`: Fetches `ResourceCapacity` records, filtering by optional parameters (dates, resource types, contractors, shifts).
- `upsertCapacity`: Handles creating or updating capacity constraints for a given Resource Type, Shift, Contractor, and Date.
- `updateCapacity`, `deleteCapacity`: Provides standard mutation mechanisms.

### Demand vs Capacity Engine
The `getDemandVsCapacity` method implements the core histogram aggregation logic:
1. **Capacity Aggregation**: Queries existing `ResourceCapacity` records and aggregates them. It automatically creates an aggregate 'daily' bucket (`shift: null`) and maintains shift-specific capacity where defined.
2. **Demand Aggregation**: Queries all `Activity` records and their child `ActivityResource` assignments that have planned start dates and duration.
   - For `labor` resources, it calculates demand as `headcount * crew_size`.
   - For `machine`/`material` resources, it calculates demand as `quantity`.
   - This demand is distributed across the activity's duration days in the `shift: null` bucket (since activities don't have shift assignments yet in Phase 2D).
3. **Variance Calculation**: Merges Capacity and Demand across the timeframe to produce daily utilization metrics:
   - `planned_demand`
   - `available_capacity`
   - `variance` (capacity - demand)
   - `utilization_percent`
   - `is_over_allocated` flag

## 2. API Route Handlers

The following new API routes have been established in `app/api/events/[eventId]/` to expose the service to the frontend:

- `shifts/route.ts`: `GET` (List), `POST` (Create)
- `shifts/[shiftId]/route.ts`: `PATCH` (Update), `DELETE`
- `resource-capacity/route.ts`: `GET` (List), `POST` (Upsert)
- `resource-capacity/[capacityId]/route.ts`: `PATCH` (Update), `DELETE`
- `resource-loading/route.ts`: `GET` (Demand vs Capacity Engine)

All routes are protected via `withTenantGuard` which automatically injects and enforces the session's `organization_id`.

## 3. Legacy Compatibility Maintained

The new `ResourcePlanningService` does **not** override, modify, or delete the existing `app/api/schedule/resource-histogram/route.ts` which uses the legacy `Discipline`-based code. The new Phase 2D architecture runs entirely in parallel, enabling a safe migration path for the frontend UI.

## 4. Verification & Testing

The logic was verified using `scratch/verify_resource_engine.ts`, which tested:
- **Simple Demand**: Correctly aggregates activity headcount/crew size across its duration.
- **Over Allocation**: Successfully flags `is_over_allocated = true` and negative variance when demand exceeds available capacity limits.
- **Multiple Shifts**: Accurately sums multi-shift capacity (e.g., 20 Day + 15 Night = 35 Total Daily Capacity) and evaluates variance properly.
- **Ignored Activities**: Verifies that deleted or cancelled activities (via `status` or `deleted_at`) are excluded from the demand pool.
- **Tenant Security**: Passed all strict cross-tenant contamination assertions, ensuring no data leakage across `organization_id` borders.
- **Build Pass**: `npm run build` completed successfully, ensuring type correctness.
