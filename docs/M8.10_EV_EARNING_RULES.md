# M8.10 EV Earning Rules

> **Status:** LOCKED — Part of M8.10 Architecture Lock

---

## 1. Default Earning Rule: Physical % Complete

All activities earn EV using the formula:

```
EV(activity) = BaselineActivity.budgeted_cost × min(Activity.progress_percent / 100, 1.0)
```

This is the universal default. The `progress_percent` field on `Activity` is the single source of truth for physical progress, entered by supervisors or foremen during shift reporting.

---

## 2. Earning Rules by Activity Type

Industrial turnaround activities fall into distinct categories that warrant different earning behaviors. For M8.10 Phase 1, we define the earning logic per type, but enforce **Physical % Complete** as the single implementation. Future phases may extend this with an `ev_method` enum per activity.

### 2.1 Normal Execution Work (Default)
**Examples:** Piping fabrication, valve replacement, heat exchanger retube, insulation removal.
**Earning Rule:** Physical % Complete.
**Rationale:** These activities have measurable intermediate progress (25% fit-up, 50% welded, 75% NDE complete, 100% hydro-tested). Physical progress is meaningful and observable.

```
EV = BAC × (progress_percent / 100)
```

### 2.2 Milestones (Zero Duration)
**Examples:** "Unit Handover", "Ready for Oil-In", "Mechanical Completion".
**Earning Rule:** 0/100 — EV = 0 until `progress_percent = 100`, then EV = BAC.
**Detection:** `Activity.duration_hours = 0` OR `Activity.duration_hours IS NULL`.
**Rationale:** Milestones represent binary gates. Partial progress is meaningless.

```
If progress_percent < 100: EV = 0
If progress_percent = 100: EV = BAC
```

### 2.3 Engineering & Procurement (Long Lead)
**Examples:** "Engineering design approval", "Long-lead valve procurement", "P&ID review".
**Earning Rule:** Physical % Complete (same as default).
**Rationale:** In turnaround planning, these activities are typically modeled with progress milestones (30% = design issued, 60% = vendor approval, 100% = delivered to site). Physical % is the most practical method.

### 2.4 Level of Effort (LOE)
**Examples:** "Scaffolding standby crew", "Crane on-site availability", "Site safety officer".
**Earning Rule:** Duration % Complete — EV accrues proportionally to elapsed time, regardless of physical deliverables.
**Detection:** For M8.10 Phase 1, LOE activities are identified by `work_category = 'LOE'` on the Activity model.
**Formula:**

```
If actual_start is NULL: EV = 0
elapsed = min(today, actual_end or planned_end) - actual_start
total = planned_end - planned_start (from baseline)
duration_pct = min(elapsed / total, 1.0) × 100
EV = BAC × (duration_pct / 100)
```

**M8.10 Phase 1 Simplification:** Since `work_category` may not be reliably populated, all LOE activities will also fall back to `progress_percent × BAC` in the initial implementation. The LOE duration-based method is defined here for architectural completeness and will be activated when activity categorization is mature.

### 2.5 Turnaround Execution Phases
In practice, a turnaround event has distinct macro-phases:

| Phase | Typical Activities | Recommended EV Method |
|-------|-------------------|----------------------|
| **Pre-Turnaround** | Procurement, engineering, scaffolding pre-build | Physical % Complete |
| **Execution** | Mechanical work, piping, electrical, instrumentation | Physical % Complete |
| **Commissioning** | Leak tests, function tests, oil-in | Physical % Complete (or 0/100 for gates) |
| **Support/LOE** | Crane standby, safety watch, scaffolding crew | Duration % Complete (LOE rule) |

## 3. BAC = 0 or NULL Handling

Activities without a `budgeted_cost` contribute nothing to EVM aggregates:
- PV = 0, EV = 0, AC is still tracked if `actual_cost` is populated.
- These activities are **excluded** from CPI/SPI calculations (they do not distort indices).
- The dashboard will display a "% Cost Loaded" indicator showing what fraction of activities have BAC > 0.

---

## 4. Progress Cap

EV is **hard-capped** at BAC:
```
EV(activity) = min(BAC × progress_percent / 100, BAC)
```
Even if `progress_percent` somehow exceeds 100 (e.g., data entry error), EV will not exceed BAC. Cost overruns are captured exclusively through AC > EV.

---

## 5. Future Extensibility (Not in M8.10 Phase 1)

The architecture must accommodate (without implementing yet):
- **Weighted Milestone:** Activity is decomposed into sub-steps with weights (e.g., Fit-up 20%, Weld 50%, NDE 20%, Hydro 10%). Progress is auto-calculated from milestone completion.
- **Rules of Credit ID:** A future `rules_of_credit_id` FK on Activity pointing to a template defining the weighted decomposition.
- **Per-Activity EV Method Override:** A future `ev_method` enum (`physical_pct`, `zero_hundred`, `fifty_fifty`, `duration_pct`, `weighted_milestone`, `loe`) on Activity.
