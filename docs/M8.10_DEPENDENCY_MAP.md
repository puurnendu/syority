# M8.10 Dependency Map & Protected System Audit

## Phase 0I — Security / Tenancy
The EVM engine will strictly operate within the existing zero-trust architecture.
- **Tenant Isolation:** All EVM aggregation queries must enforce `WHERE organization_id = session.org_id`.
- **API Guard:** The EVM dashboards and endpoints will use `withTenantGuard` and a new `guardApi('nav.cost')` or continue using `guardApi('nav.schedule')` depending on commercial packaging.
- **Financial Data Access:** Introducing cost necessitates role-based field-level security. Schedulers may need access to hours/durations, while only Cost Controllers / PMs see actual dollar rates. (Dependency: M8.10 may require an update to the RBAC matrix).

## Phase 0J — Protected System Audit
The following systems were audited for EVM integration compatibility:
- `src/lib/scheduleEngine.ts`: **SAFE**. The CPM engine handles dates/durations. EVM sits on top as an aggregation layer; no changes to CPM required.
- `ScheduleVarianceService` / `ScheduleForecastService`: **SAFE**. M8.8 uses duration-based SV. EVM will introduce a parallel `CostVarianceService` without mutating the old ones.
- `ScenarioCalculationService`: **SAFE**. Can be wrapped/extended via dependency injection to output EVM metrics alongside SHI metrics.

## Phase 0K — Future Compatibility Dependencies
- **M8.11 Scope Change:** EVM baselines must support dynamic BAC expansion when approved scope is injected.
- **ERP Integration:** `Activity.actual_cost` must remain a writable field for upstream ERP syncs (e.g., SAP timesheet ingestion).
- **Resource Rates:** To calculate cost from hours (for EVM), a future `ResourceRate` table will be required. M8.10 should ideally implement this immediately, or default to generic BAC values.
