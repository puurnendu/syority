## P0 — Security / Data Corruption / Transactional Integrity

### P0-001: Prisma Field Name Mismatch — `total_float_days` vs `total_float`

**Schema**: `Activity.total_float` (Decimal, line 43 of schema.prisma)
**Code**: Every M8.7 service uses `total_float_days`

**Affected files**:
- `ResourceConstraintService.ts` line 86: `select: { total_float_days: true }`
- `ResourceKpiService.ts` line 133: `select: { total_float_days: true }`
- `ResourceRiskService.ts` line 35: `select: { total_float_days: true }`
- `ResourceScenarioComparisonService.ts` line 49: `select: { total_float_days: true }`
- `ResourceLevelingApplyService.ts` line 175: `total_float_days: res.total_float_days`

**Impact**: Prisma will throw `Unknown field 'total_float_days'` at runtime for every Prisma `select` that includes this field. This crashes the constraint engine, KPI engine, risk engine, and scenario comparison.

**Correct field**: `total_float`

---

### P0-002: Prisma Field Name Mismatch — `name` vs `description` on Activity

**Schema**: `Activity.description` (String, line 19 of schema.prisma). There is NO `name` field.
**Code**: `ResourceConstraintService.ts` line 82: `select: { name: true }`

**Impact**: Prisma will throw `Unknown field 'name'` at runtime, crashing `detectConstraints()`, which cascades into crashing:
- `ResourceKpiService.getEventKpis()`
- `ResourceRiskService.getRisks()`
- All constraint-related APIs

**Correct field**: `description`

---

### P0-003: Apply Service writes non-existent Prisma fields `early_end` and `late_end`

**Schema**: Activity has `early_finish` and `late_finish` (lines 40, 42)
**Code**: `ResourceLevelingApplyService.ts` lines 172-174:
```typescript
early_end: new Date(res.early_end),   // schema field is early_finish
late_end: new Date(res.late_end),     // schema field is late_finish
```

**Additionally**: The schedule engine output uses `early_finish` and `late_finish`, so `res.early_end` and `res.late_end` would be `undefined`, and then `new Date(undefined)` produces `Invalid Date`.

**Impact**: Apply transaction will crash. CPM recalculation results will not persist. Transaction rolls back = zero partial writes (good), but Apply is completely broken.

---

### P0-004: Apply Service writes `total_float_days` to Prisma (field is `total_float`)

**Code**: `ResourceLevelingApplyService.ts` line 175: `total_float_days: res.total_float_days`
**Schema field**: `total_float`

**Impact**: Prisma rejects the unknown field. Apply is broken.

### P0-006: Phase 2I API routes use fabricated `withTenantGuard` signature

**Actual signature**: `withTenantGuard((req, ctx, session) => ...)`
- Organization ID accessed via: `session.user.organization_id`

**Phase 2I routes use**:
```typescript
{ params, tenantContext }: { params: { eventId: string }; tenantContext: { organizationId: string } }
```

This destructuring pattern (`tenantContext.organizationId`) does not exist in the actual `withTenantGuard` implementation. Even if the import path were fixed, the routes would fail with `Cannot read properties of undefined (reading 'organizationId')`.

## P1 — Core Scheduling/Resource Calculation Incorrect

### P1-001: ResourceCapacity composite unique constraint with NULLs

**Schema** (line 5970):
```prisma
@@unique([event_id, resource_type_id, contractor_id, shift_id, target_date], name: "unique_capacity_bucket")
```

`contractor_id` and `shift_id` are nullable. In PostgreSQL, `NULL != NULL`, meaning this constraint does NOT prevent duplicate rows where `contractor_id = NULL, shift_id = NULL`. The `upsertCapacity` method uses `findFirst` as a workaround (line 142), which is correct behavior but fragile — any direct INSERT bypassing the service would create duplicates.

---

### P1-002: Demand distribution ignores `planned_end`

`getDemandVsCapacity` calculates duration from `planned_start + (duration_hours / 10)`. It never reads `planned_end`. If the actual schedule has `planned_end` that differs from the computed end (e.g., due to CPM recalculation, calendar effects, or manual edits), the demand distribution will be wrong.

---

### P1-003: Activity `event_id` is nullable and optional

Schema line 14: `event_id String? @db.Uuid` (nullable).

`getDemandVsCapacity` filters by `event_id: eventId`, which will miss activities where `event_id` is null but `workpack.event_id` matches. The LevelingService (line 67) ALSO filters by `event_id: eventId` directly, but the Apply service (line 124) uses `workpack: { event_id: eventId }`. This inconsistency could cause demand to include different activity sets than leveling.

---

### P1-004: Leveling engine `proposedEnd` calculation uses raw milliseconds

`ResourceLevelingService.ts` line 322:
```typescript
const proposedEnd = new Date(newStart.getTime() + targetAct.duration_hours * 3600000);
```

This converts duration_hours directly to milliseconds, which produces a timestamp-based end date, NOT a calendar-based end date aligned with the schedule engine's `HOURS_PER_DAY = 10` assumption. A 30-hour activity would get `proposedEnd = start + 30*3600000 = start + 1.25 days` in wall-clock time, but the schedule engine treats it as 3 working days.

---

### P1-005: `ResourceRiskService` uses `crypto.randomUUID()` for risk IDs

This means the same input produces different `risk_id`s on every call, violating the deterministic output requirement. Risk IDs should be derived from the input data (e.g., hash of date + resource_type_id).

## P2 — Major Functional Gap

### P2-001: No Apply API route with correct tenant guard

The apply route at `level-resources/apply/route.ts` uses the OLD import path `@/lib/withTenantGuard` which IS correct, but the route's functionality depends on `ResourceLevelingApplyService` which has P0-003/P0-004 defects.

### P2-002: Several ConstraintTypes declared but never generated

The `ResourceConstraintService` defines `SHIFT_CAPACITY_IMBALANCE`, `MULTI_RESOURCE_CONFLICT`, `PROJECT_FINISH_RISK`, and `DEPENDENCY_BLOCK` in its type union but never generates them. Actual logic only produces: `HARD_CAPACITY`, `CAPACITY_OVERLOAD`, `HIGH_UTILIZATION`, `CRITICAL_ACTIVITY_CONFLICT`, and `FLOAT_RISK`.

### P2-003: Scenario comparison uses hardcoded heuristic values

`ResourceScenarioComparisonService.ts` lines 93-94:
```typescript
const max_deficit_improvement = constraints_resolved > 0 ? (constraints_resolved * 2) : 0;
const resource_utilization_improvement = constraints_resolved > 0 ? 5.0 : 0.0;
```
These are fabricated numbers, not computed from actual data.

### P2-004: Shift filtering causes demand to disappear

In `getDemandVsCapacity` line 304: `if (filters?.shiftId) continue;` — when filtering by a specific shift, ALL demand is excluded because activities have no shift assignment (`shiftId = 'null'`). The user would see capacity but zero demand for any shift-specific view.
