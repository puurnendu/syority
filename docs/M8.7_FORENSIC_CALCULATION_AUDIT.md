# M8.7 FORENSIC CALCULATION AUDIT

## Demand Calculation

### Algorithm (ResourcePlanningService.getDemandVsCapacity)

```
For each Activity where:
  event_id = eventId
  organization_id = organizationId
  deleted_at = null
  status != 'cancelled'
  planned_start != null
  duration_hours != null AND > 0

  HOURS_PER_DAY = 10  (hardcoded constant)
  durationDays = ceil(duration_hours / HOURS_PER_DAY)  // minimum 1

  For each ActivityResource:
    IF resource_type = 'machine' OR 'material':
      demandPerDay = quantity (default 1)
    ELSE (labor):
      demandPerDay = headcount * crew_size

    Distribute demandPerDay across durationDays starting from planned_start
```

### Issues Found

1. **planned_end is completely ignored** (P1-002)
   - Duration derived solely from `duration_hours / 10`
   - If CPM recalculation moves planned_end without changing duration_hours, demand stays on original dates

2. **HOURS_PER_DAY = 10 hardcoded**
   - No alignment with ShiftDefinition hours
   - Not configurable per event

3. **Activity filtering by event_id directly** (P1-003)
   - `event_id` is nullable on Activity
   - Activities with NULL event_id but valid workpack.event_id are excluded

4. **Shift assignment = 'null' for all demand**
   - Activities have no shift relationship
   - Demand is always shift='null'
   - Shift-specific capacity views show zero demand (P2-004)

## Capacity Calculation

### Algorithm

```
For each ResourceCapacity where event_id, organization_id match:
  Daily aggregate: sum all capacity_limit for same (date, resource_type_id, contractor_id)
  Shift-specific: if shift_id present, also stored as shift-specific entry
```

### Issues Found

1. **Double-counting risk**: Shift-specific capacity is ALSO added to daily aggregate (line 329). If Day shift = 5 and Night shift = 5, daily total = 10, which is correct. But if someone adds a NULL-shift capacity of 10 AND a Day shift of 5, daily total = 15 (NULL + Day).

## Utilization Calculation

```
utilization_percent = (demand / capacity) * 100
  if capacity = 0 and demand > 0: utilization = null
  if capacity = 0 and demand = 0: utilization = null
```

### Issue: Division by zero handled, but null semantics unclear
When `capacity = 0` and `demand > 0`, utilization is null rather than Infinity. This means infinite overallocation is reported as "unknown utilization" rather than a constraint.

**Mitigated**: The constraint engine separately detects `HARD_CAPACITY` when capacity=0 and demand>0.

      + totalDeficit 
      + (downstreamConstraintCount * 10) 
      + float_score

WHERE float_score = float_available - 1000 if float_available <= 2

## KPI Calculations

**BROKEN** — Cannot execute due to dependency on broken `detectConstraints()`.

### Logic (if field names were correct):

- total_demand: Sum of planned_demand across daily aggregates
- total_capacity: Sum of available_capacity across daily aggregates  
- deficit: Sum of abs(variance) where variance < 0
- surplus: Sum of variance where variance > 0
- utilization: (total_demand / total_capacity) * 100
- peak_utilization: max utilization across all data points
- overloaded_days: count of distinct dates where demand > capacity
- Division by zero: Handled (returns 0 when total_capacity = 0)

## Forecast Calculations

### Logic:
```
For each resource type:
  first_shortage_date: first date where demand > capacity
  peak_shortage_date: date with maximum deficit
  max_forecast_deficit: maximum abs(variance) where demand > capacity
  consecutive_shortage_days: longest run of consecutive dates with demand > capacity
  
  Status:
    utilization < 80% → NORMAL
    80-90% → WATCH  
    90-100% → AT_RISK
    > 100% or any deficit → CRITICAL
```

### Correctness: PARTIAL
- Logic is sound
- BUT depends on `getDemandVsCapacity` data which has P1-002 (ignores planned_end)
