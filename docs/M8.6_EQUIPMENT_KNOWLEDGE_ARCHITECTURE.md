# M8.6 Equipment Knowledge Architecture

## 1. Architectural Strategy: The Hybrid Model

Based on the existing SYORITY architecture, which relies on a strictly typed `Asset` table and EAV-style `UdfValues` for activities, the Equipment Knowledge model must balance flexibility (AI proposing new fields dynamically) with strict provenance (tracking confidence, source document, and verification status per field). 

We select a **Hybrid Attribute Model with Field-Level Provenance**.

### Why this model?
- **Not purely JSON:** JSON makes field-level versioning, source tracking, and SQL-level register querying (e.g., "Find all installed 6-inch blinds") very difficult.
- **Not purely typed columns:** Hardcoding "Tube Count" or "Tray Spacing" onto the `Asset` table violates the requirement that AI can propose new fields.
- **Not UDFs:** Equipment Knowledge is reference data, not an activity execution payload. 

## 2. Proposed Data Model

We will introduce three new tables to handle the equipment knowledge lifecycle cleanly:

### A. `EquipmentKnowledgeVersion`
Tracks the lifecycle of an extraction or verification event.
- `id` (UUID)
- `asset_id` (UUID, FK to `Asset`)
- `status` (Enum: `AI_CANDIDATE`, `VERIFIED`, `SUPERSEDED`)
- `created_at` / `created_by` / `verified_by` / `verified_at`
- `extraction_model_version` (String, e.g., "gemini-1.5-pro")

### B. `EquipmentKnowledgeField`
The actual granular facts proposed or verified.
- `id` (UUID)
- `version_id` (UUID, FK to `EquipmentKnowledgeVersion`)
- `asset_id` (UUID, FK to `Asset` for easy querying)
- `field_name` (String, e.g., "Bundle Weight", "Design Pressure")
- `field_type` (Enum: `string`, `number`, `boolean`, `date`)
- `value_string` / `value_numeric` (Data storage)
- `unit` (String, e.g., "MT", "barg")
- `source_document_id` (UUID, FK to `PlantDocument`)
- `source_page` (Int)
- `source_location` (String/JSON, bounding box or text snippet)
- `confidence_score` (Float, 0.0 - 1.0)
- `verification_status` (Enum: `AI_EXTRACTED`, `VERIFIED`, `REJECTED`)

### C. `EquipmentKnowledgeMaster` (Materialized View or Aggregate Table)
For fast consumption by reporting, registers, and the Workpack PDF, we will maintain an active "trusted" view of the fields for an equipment item. This prevents complex self-joins when trying to find the "latest verified" fields.

## 3. Relationships

- **Asset (Equipment):** 1-to-Many `EquipmentKnowledgeVersion`.
- **PlantDocument:** 1-to-Many `EquipmentKnowledgeField` (allowing field-level tracking to specific drawings, e.g. GA Drawing vs Datasheet).
- **Workpack:** The Workpack's `asset_id` provides direct access to the `EquipmentKnowledgeMaster` view.

## 4. Relationship with Activity Code, Number, ID, and UDFs
- **Activity Code:** Standard work template (e.g., `BUNDLE.PULL`). Completely independent.
- **Activity Number / ID:** Execution instances of the work. Completely independent.
- **UDF:** Activity UDFs capture *execution* variances (e.g., "Actual weight pulled: 18.2 MT"). Equipment Knowledge captures *design reference* facts (e.g., "Design Bundle Weight: 18.5 MT"). They will not be merged, preserving the reference vs. execution boundary.
